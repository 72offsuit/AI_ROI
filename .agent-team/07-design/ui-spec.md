# 1. ★ T2.14 — 출처 구분 표현

## 1.1 출처는 어떻게 판정되는가 (화면이 아니라 스키마가 한다)

`src/measurement/sink.py:79-83` 실측:

```python
def event_source(record) -> EventSource:
    """`simulator_version` · `random_seed` 가 모두 없으면 커머스 실측분이다."""
    if record.get("simulator_version") is None and record.get("random_seed") is None:
        return EventSource.COMMERCE
    return EventSource.SIMULATOR
```

**별도 출처 플래그가 없다. 스키마에서 파생된다** — 위조하려면 `simulator_version`·`random_seed`를 조작해야 하고 그러면 재현성 기록이 깨진다.

> **US-12 인수조건 3** — *"출처 판정이 `simulator_version`·`random_seed`의 null 여부에서 파생된 것임이 화면 또는 문서에 설명된다"*
>
> **확정: 화면에 쓴다.** V1 출처 블록 하단 각주 한 줄:
> ```
> 출처는 simulator_version · random_seed 의 null 여부에서 파생됩니다 (별도 플래그 없음).
> ```
> 문서가 아니라 화면을 택한 이유: 읽는 사람이 "이 구분을 신뢰할 수 있는가"를 묻는 순간이 **화면을 보는 순간**이다.

> **US-12 인수조건 4** — *"대시보드가 출처를 재분류하지 않는다"*. `event_source()`를 화면에서 호출하지 않는다. W1 보완점 W-7이 A8 조건 C-2로 해소된 지점이다.

## 1.2 ★ 확정 — 출처는 **색이 아니라 위치**로 구분한다

흔한 설계는 출처에 색을 배정하는 것이다(커머스=보라, 시뮬레이터=핑크). **기각한다.** 근거 셋:

1. **색이 이미 상태에 쓰였다.** `missing-state-spec.md` §4.2가 `warning`·`error`·`info`·`muted`를 상태에 배정했다. 같은 셀에서 출처 색과 상태 색이 경쟁하면 **둘 다 읽히지 않는다.**
2. **`Plan/DESIGN.md`가 금지한다.** *"핑크를 오류, 보라색을 성공으로 임의 대응하지 않는다"* · *"팔레트의 모든 색을 한 화면에 전시하지 않습니다"* · *"10개 브랜드색을 다중 계열에 그대로 배분하지 않습니다"*.
3. **위치는 색맹·흑백 인쇄·스크린샷 축소에서 무료로 살아남는다.** 인수조건이 스크린샷 증명을 요구한다.

> ### 출처 표기 규칙 3종
>
> **S-1 · 고정 2열, 순서 불변.** 출처가 갈리는 모든 블록은 **왼쪽 = 커머스 실측 / 오른쪽 = 시뮬레이터 생성**. 좁아져 세로 적층돼도 **커머스가 위**. 어떤 화면·어떤 정렬에서도 바뀌지 않는다.
> **S-2 · 배지는 글리프 + 문구.** `◼ 실측` / `◇ 생성`. 채운 사각형 = 실제로 일어난 일, 빈 사각형 = 생성된 일. ink는 `text-secondary`, 배경 없음 — **출처는 상태가 아니므로 상태 칩처럼 칠하지 않는다.**
> **S-3 · 합산은 기본이 아니다.** 표시할 때 제목에 `· 합산` 접미사 + `합산` 칩(`text-secondary`). 숫자만 내놓지 않는다 (R-7).

**왜 순서를 고정하는가:** 정렬 가능한 표에서 출처 열이 뒤바뀌면 읽는 사람이 매번 배지를 확인해야 한다. 위치가 고정되면 **배지를 읽지 않고도** 안다. 배지는 확인용 보조다.

## 1.3 ★ 커머스 0건은 오류가 아니다 — 연결 상태 3종

**2026-09-11 현재 커머스는 이벤트를 0건 기록한다** (`Ecommerce #28` 미착수). `kpi-definition-v1.md` §8이 확인했다. **이것이 정상 상태다.**

| 연결 상태 | 판정 | 화면 상태 | 블록 문구 |
|---|---|---|---|
| **미연결** `never_connected` | 첫 수신 기록이 없다 | `unconnected` (**info**) | `○ 아직 연결되지 않음` |
| **수신 중** `connected` | 최근 수신이 있다 | `available` (**success**) | `✓ 수신 중` |
| **정지** `stale` | 수신했었고 최근 끊겼다 | `blocked` (**warning**) | `⚠ 수신 정지` |

> **규칙 S-4 — `미연결`에 `error`·`warning`을 쓰지 않는다.** `info` 계열이다.
> `missing-state-spec.md` F-3과 같은 근거: 정상 상태를 경고로 칠하면 실제 경고가 묻힌다.
>
> **규칙 S-5 — 미연결 출처의 지표는 `—`다. `0`도 아니고 경고도 아니다.** 3분기 구분이 이 화면의 요구다.
>
> **규칙 S-6 — 미연결 출처 블록을 접거나 축소하지 않는다** (V-0). 빈 커머스 열이 **전폭으로 남아 있어야** 프로젝트의 실제 상태가 보인다. 빈 열을 접으면 "시뮬레이터만 있는 시스템"처럼 보이고, 그것이 현재 상태의 오독이다.

**`미연결`과 `정지`를 게시물이 구분해 주는가는 미확정** (`ux-flow-map.md` X-4). 화면이 "첫 수신 null → 미연결"로 판정하면 `DB-012` 경계에 닿는다. C1에는 `정지`가 나타날 수 없으므로(수신 중인 출처가 없다) **`정지`는 구현하되 검증되지 않은 상태로 남는다** — `design-handoff.md`에 한계로 적는다.

> **왜 막대이고 선이 아닌가:** 선 차트는 결손 구간에서 **잇거나 끊어야** 하고, 잇는 순간 없는 값을 만든다. 막대는 각 날짜가 독립이라 결손이 구조적으로 표현된다. V-5를 차트 종류 선택으로 선제 해결한 것이다.

## 2.2 ⑦ `event_type` 16종 매트릭스

| 요소 | 명세 |
|---|---|
| 형태 | **표** (차트 아님 — 0건 행이 차트에서 사라진다, V-5) |
| 행 수 | **항상 16** (`event_type_coverage`의 분모가 16 고정) |
| 열 | `event_type` · ◼ 커머스 · ◇ 시뮬레이터 · 상태 |
| 0건 타입 | 건수 `—` + `unconnected` 칩 `미수신` + 기준 `0 / 16종 중` |
| 정렬 | `event_type` 이름 고정 순서. **건수 내림차순을 기본으로 쓰지 않는다** — 0건 타입이 항상 아래로 밀려 V-0 취지가 약해진다 |
| 커버리지 | `event_type_coverage = 발생 종수 / 16` 을 표 머리에. 0/16이면 `—`가 아니라 **`0 / 16`** (측정된 0, 기준이 분명하다) |

> **`0 / 16`은 왜 `0`이 아니고 `—`도 아닌가:** 16종 목록은 스키마에 고정되어 있으므로 **분모가 확실히 존재한다.** 세어봤고 0이었다 → 측정된 0(V-2). 분모를 함께 쓰는 것이 그 증거다.

| **사유별 대표 샘플** | 사유당 최대 3건. **`event_type`·`partition_date`·`source`·`problems`·`offending_fields`(필드 이름만).** ★ **값을 일절 렌더링하지 않는다** — §3.1 |
| 거부 0건일 때 | `0건` + 기준 `시도 N건 중 0건` — **측정된 0이다.** `—`를 쓰지 않는다 (분모가 있다) |
| 게시물·시도 0건일 때 | `—` + `unconnected` + `기준: 수집 시도 없음` |

> **샘플을 왜 제한하는가:** 원본 이벤트 전량 조회는 이벤트 브라우저이고 A5를 깨뜨린다(`usp.md` §1.7). 3건이면 "왜 거부됐나"에 답하고, 전량은 다른 제품을 만든다.
>
## 3.1 ★ 개정 — 값을 렌더링하지 않는다 (보안 판정 · James가 맞다)

개정 전 이 문서는 샘플을 *"사유 + 필드명 + 받은 값의 타입/형태"* 로 쓰고 예시에 `category="우주선"`처럼 **값을 넣었다. 틀렸다.**

James의 판정(`api-contracts.md` §5.2): `rejected.jsonl`에는 `validate_event()`가 거부한 레코드가 **원문 그대로** 들어 있다(`sink.py:203-206`). 거부 사유 중 하나가 *"측정 계층을 통과할 수 없는 필드"* — 즉 **Hidden Trait·τ·Potential Outcome이 담긴 레코드가 `rejected.jsonl`에 남는다.** 값을 `results/`로 옮기면 **금지 필드가 대시보드까지 도달하는 경로**가 생긴다 — `ISO-003`·`NFR-002` 우회.

> **확정: 화면은 `offending_fields`(필드 **이름**만)를 쓰고 값을 일절 렌더링하지 않는다.**
> 필드 이름으로 거부 사유를 이해하기에 충분하고, 충분하지 않더라도 **누수 경로를 열 근거는 되지 않는다.**
> 계약 스키마의 `additionalProperties: false`가 강제한다.

## 5.3 계산 불가 19개를 어떻게 조용히 두는가

`NEEDS_MODEL_OUTPUT` 15 + `NEEDS_TWO_STRATEGIES` 4 = 19개가 `planned`다. `surface-muted` + `text-muted` + 중점 글리프.

실험 판정 지표 15개는 **한 블록으로 묶어 블록 머리에 사유를 한 번 쓴다**:
```
· 실험 판정 지표 15개 — 계산 불가 · 이후 사이클 (모델 산출물 · 비교 전략 없음)
  정의는 확정되어 있습니다. 계산은 이후 사이클입니다.
```
그리고 **15행을 그대로 펼친다** (V-0). 사유 문구만 블록 머리로 올려 15번 반복을 피한다. 행을 접는 것이 아니라 **문구를 모으는** 것이다.

> **왜 정의를 지금 보여주는가:** `#46` — *"실험 결과를 본 뒤 유리한 지표를 고르는 것은 결과 조작"*. 정의가 결과보다 먼저 **화면에** 있었다는 것이 기록이 된다. `/metrics`가 P-AI 독자에게 주는 것이 이것이다.

# 6. V5 — 데이터 품질 (`/quality`) · V6 — 봉인 상태 (`/seal`)

## 6.0 ★ V5 개정 — `gate_result` 3값 + 규칙 V-12

**게이트 수준 (`gate_result`) — 계약이 3값이다:**

| 값 | 시각 상태 | 문구 | 규칙 |
|---|---|---|---|
| `pass` | `ok` (success) | `통과 N건` | 전건 통과이고 미실행·차단이 0일 때만 |
| `fail` | `violation` (error) | `실패 N건` | 판정 배너 순위 1 |
| **`incomplete`** | **`gap` (warning)** | **`미완 · 통과 N / 미실행 M / 차단 K`** | **`success` 토큰을 일절 쓰지 않고 "통과"를 단독으로 쓰지 않는다** |

`incomplete` = *"실행한 검사는 다 통과했지만 실행 못 한 검사가 있다"*. **초록으로 그리면 안 된다** — AGENTS.md의 *"미실행 검증을 통과로 표시하지 않는다"* 를 계약이 값으로 만든 것이다.

**개별 검사 행 — 규칙 V-12 (공허한 통과):**
`status == "pass"` ∧ `examined_rows == 0` → **`measured`로 그리지 않는다.** `unconnected`(info) + `공허한 통과 · 검사 대상 0행` + `scope` 인라인. **`✓`도 초록도 쓰지 않는다.**
근거와 발견 경위는 `missing-state-spec.md` §3.8.

**각 검사에 `scope` 필수** — *"이 검사가 실제로 무엇을 검사했는가"*. 범위를 적지 않으면 부분 검사가 전체 검사로 읽힌다. `status`가 `not_run`/`blocked`면 `violations`는 `null`이고 **`0`으로 적으면 통과처럼 읽힌다**(계약 스키마가 거부).

> **`PARTIAL`의 범위 문구를 필수로 만든 이유** — US-16: *"부분 Lock은 시간이 지나면 '전체를 Lock했다'로 읽힌다."* 범위 문구 없는 `PARTIAL` 칩은 `LOCKED`와 구별되지 않는다.
> **규칙:** 게시물에 범위 문구가 없으면 `PARTIAL` 칩 대신 **`violation · 범위 한정 문구 누락`** 으로 렌더한다. 여기서도 화면이 자기 입력을 검사한다 (V-3과 같은 장치).

# 7. T2.16 — PRD §71 모니터링 트리거 5종 (`/triggers`)

## 7.1 판정 — C1에서 작동하는 트리거는 **0개**다

PRD §71이 정의한 5종을 C1 계산 가능성과 대조했다.

| # | 트리거 (PRD §71) | 필요한 것 | C1 상태 | 차단 사유 |
|---|---|---|---|---|
| T-1 | `Churn ↑` → Segment Analysis | `churn_rate` **시계열** + Segment View(`DB-007`) | **불가** | `PARAM_UNCONFIRMED`(임계값 미확정) + `NEEDS_MODEL_OUTPUT`(Segment) + **이력 없음** |
| T-2 | `Retention ↓` → Cohort Analysis | `retention_rate` 시계열 + Cohort View(`DB-004`) | **불가** | 동일 + `NEEDS_MODEL_OUTPUT` |
| T-3 | `AI ROI < Rule Baseline` → Strategy Review | 두 전략의 ROI | **불가** | `NEEDS_TWO_STRATEGIES` |
| T-4 | `Marketing Cost ↑` → Target Threshold Review | `marketing_cost` + 임계 `C_rule`·`B` | **부분** | 값은 계산 가능(§5.1). **임계값이 GATE 2 확정 항목** + 이력 없음 |
| T-5 | `Uplift ↓` → Treatment Policy Review | Uplift 지표 | **불가** | `NEEDS_MODEL_OUTPUT` |

## 7.2 공통 차단 요인 — 5종 전부가 **`↑`/`↓`를 전제한다**

가장 중요한 발견이고, 개별 지표의 계산 가능성보다 앞선다.

> **5종 전부 "증가/감소"라는 **변화**를 조건으로 한다. 변화에는 비교 기준이 필요하다.**
> C1 게시물은 **단일 시점 스냅샷**이고 이전 게시물을 보관한다는 계약이 없다.
> `Plan/DESIGN.md`: *"없는 비교값을 생성하지 않습니다."* → `missing-state-spec.md` **V-11**: C1에서 증감을 렌더링하지 않는다.
>
> **따라서 `marketing_cost`(T-4)가 계산되더라도 `↑`를 판정할 수 없다.** 값 하나로는 증가가 아니다.
> → 게시물 이력 보관이 §71의 **선행 조건**이다. James 미해결 항목 X-6.

## 7.3 그러면 C1에 무엇을 만드는가

**껍데기 트리거 화면을 만들지 않는다.** 작동하지 않는 경보 UI는 "있는데 안 울린다"로 읽히고, 그것이 가장 나쁘다.

> ### 확정: `/triggers`는 **계획된 부재 표**다
>
> ```
> 모니터링 트리거 (PRD §71)                                     5종 · C1 작동 0종
> ─────────────────────────────────────────────────────────────────────────────
> · Churn ↑ → Segment Analysis                          계산 불가 · 이후 사이클
>   차단: 이탈 임계값 미확정 · Segment 모델 없음 · 게시물 이력 없음
>
> · Retention ↓ → Cohort Analysis                       계산 불가 · 이후 사이클
>   차단: 이탈 임계값 미확정 · Cohort 산출 없음 · 게시물 이력 없음
>
> · AI ROI < Rule Baseline → Strategy Review            계산 불가 · 이후 사이클
>   차단: 비교 전략 없음 (NEEDS_TWO_STRATEGIES)
>
> ⚠ Marketing Cost ↑ → Target Threshold Review          부분 · 임계값 미확정
>   marketing_cost 계산 가능 · 임계 C_rule·B 는 GATE 2 확정 항목
>   차단: 게시물 이력 없음 → 증가 여부를 판정할 수 없음
>
> · Uplift ↓ → Treatment Policy Review                  계산 불가 · 이후 사이클
>   차단: 모델 산출물 없음 (NEEDS_MODEL_OUTPUT)
> ─────────────────────────────────────────────────────────────────────────────
> 공통 선행 조건: 게시물 이력 보관 — 5종 전부가 시점 간 비교를 전제합니다.
> ```

| 규칙 | 내용 |
|---|---|
| 상태 | T-1·T-2·T-3·T-5 = `planned` · T-4 = `blocked`(조치 가능한 차단) |
| **경보 UI를 만들지 않는다** | 배지·알림·임계 입력·토글 없음. 작동하지 않는 컨트롤은 두지 않는다 |
| 공통 선행 조건 | 하단에 한 번 명시. 5종에 반복하지 않는다 |
| 데이터 출처 | 정적이어도 된다 — §71이 정본이고 차단 사유는 C1에 고정이다. **게시물이 주면 게시물을 쓴다** |
| 이후 사이클 | 차단 사유가 해소된 트리거를 `available`로 전환. 표 구조는 유지 |

**이 화면이 §71 요구를 "C1 범위 밖"으로 버리지 않으면서 거짓 기능도 만들지 않는 지점이다.** 정본이 요구한 5종이 화면에 존재하고, 각각 왜 지금 작동하지 않는지가 사유 코드로 적혀 있다. **USP-1을 모니터링 트리거에 적용한 것**이다.
