## ★ 후속 수정자가 반드시 볼 것 — 명백한 수정이 구멍을 닫지 않는 자리 2건

**리드 오류 2건을 보안 감사가 잡았다. 둘 다 발견 자체는 옳은데 원인 진술이 한 칸 어긋나 있었다.**

**1. M1 트리거** (이슈 `#59`)
리뷰 본문은 원인에 `sink.py:266` 비원자적 쓰기를 포함하는데 틀렸다.
```
① 잘린 JSON '{"rows": 12, "rejec'  →  JSONDecodeError 크래시   (조용한 0-채움 아님)
② rows: null (유효한 JSON)          →  status=ok  value=0       (조용한 0-채움 성립)
```
비원자적 쓰기가 만드는 건 **시끄러운 크래시**다. 조용한 0-채움은 **유효한 JSON 이 키를 빠뜨리거나 `null` 일 때** 생기고, 원인은 **버전 스큐·손편집·다른 생산자**다. `sink.py` 를 원자적으로 고치면 **엉뚱한 것을 고치고 닫혔다고 믿게 된다.**

**2. M4 `lock_items_pending`** (이슈 `#60`)
이 필드는 LOCK_ITEMS 가 아니라 **G-선행조건 미충족 수**를 세며 16종 전부 충족이라 **실측 0** 이다.

| 시나리오 | 결과 |
|---|---|
| 실제 게시 경로 | `SINK_EMPTY` — 경보 없음 |
| **"명백한 수정" — 누락 키만 채움** | **`CHECKS_NOT_RUN` — 여전히 없음** |
| 키 + `lock_items_pending` 조작 | `FREEZE_MISMATCH` |

**"GATE 2 이후에 죽는다"가 아니라 유효 발동 조건이 존재한 적이 없다.** 이름-의미 불일치가 이 겹을 가렸으므로 **필드 이름도 함께 고쳐야** 한다.

## 관통 진단 — 이 사이클이 남긴 가장 값진 것

major 10건 중 4건(M1·M7·M9·M10)이 서로 다른 파일·계층에 있으면서 **같은 모양**이다.

> **이 코드베이스가 잘하는 것은 "값을 계약으로 강제하는 것"이고, 빠뜨린 것은 "그 계약·선언 자체가 실제와 일치하는지 대조하는 상위 장치"다.**
>
> 스스로 만든 **"세 번째 값"** 규율(`vacuous` · `met: null` · `verification: not_run` · 계산 불가)이 **값 계층에서는 철저한데 선언 계층에는 아직 적용되지 않았다.**

처방도 같다 — 넷 다 "값을 다시 계산"하는 수정이 아니라 **"선언 vs 실제"를 자동 대조하는 검사 하나씩**을 추가하면 닫힌다. 이슈 `#59` 가 이 묶음이다.
