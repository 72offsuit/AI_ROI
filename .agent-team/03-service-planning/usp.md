# 1. ★ T2.1 — 가정 A8 판정

## 1.0 판정 대상

charter §8 가정 A8:

> **A8** — "GA형 로그/지표 추적 대시보드"는 PRD §69.1의 AI ROI 결과 대시보드(:3001)와 **별개다**
> 근거: 사용자 표현이 "로그/지표 추적" · 틀렸을 때: 대시보드가 2개가 아니라 1개 → 아키텍처·범위 변경

사용자 원문:

> *"현재 AI ROI issue에 있는 내용들처럼 GA형태의 로그/지표를 추적하는 시스템 대시보드를 만들어야함"*

## 1.1 먼저 — 질문에 두 개가 섞여 있다

"같은 것인가 별개인가"는 실제로 서로 다른 두 질문이다. 섞인 채로는 답이 나오지 않는다.

| | 질문 | 답이 결정하는 것 |
|---|---|---|
| **Q-α** | **화면(요구사항 집합)이 같은가?** | 무엇을 그리는가 |
| **Q-β** | **애플리케이션·포트·데이터 전달 경로가 같은가?** | 몇 개를 만드는가 · Andrew의 작업 경계 |

charter의 A8은 이 둘을 구분하지 않았다. 아래에서 각각 답한 뒤 하나의 결론으로 합친다.

### Q-α — 화면은 **다르다**

PRD §67 · SRS `DB-003`~`DB-010`이 열거하는 화면은 **7종**이다.

| 화면 | 요구 내용 | 산출 주체 | C1 |
|---|---|---|---|
| `DB-003` Churn View | Total Customers · Churn Risk Distribution · At-risk Count · **Model AUC** | `src/decision/models/` | 범위 밖 |
| `DB-004` Cohort View | M1/M3/M6/M12 Retention Curve | `src/decision/analytics/` | 범위 밖 |
| `DB-005` Uplift View | 4분면 · Uplift Distribution | `src/decision/uplift/` | 범위 밖 |
| `DB-006` CLV View | CLV Distribution · Top 20% | `src/decision/clv/` | 범위 밖 |
| `DB-007` Segment View | 6+ Segment · Priority Score | `src/decision/segmentation/` | 범위 밖 |
| `DB-008` Optimization View | Budget · Allocation · Expected ROI | `src/decision/optimization/` | 범위 밖 |
| `DB-009` A/B View | Lift · p-value · 95% CI | `src/decision/experiments/` | 범위 밖 |
| `DB-010` Target List | customer_id · churn_probability · uplift_score · CLV · … | `src/decision/` | 범위 밖 |

**7종 전부가 `src/decision/` 산출물을 그린다. 7종 중 어느 것도 "이벤트가 제대로 쌓이고 있는가"에 답하지 않는다.**
charter §3.1③이 요구하는 세 가지 — 이벤트 수집 현황 · 데이터 품질 · 출처 구분 · 계산 불가 표시 — 는 `DB-003`~`DB-010` 어디에도 없다.

→ **Q-α 답: 화면군은 별개다.** GA형 화면은 PRD §67의 부분집합도 상위집합도 아니고, **추가되는 화면군**이다.

### Q-β — 애플리케이션·포트·전달 경로는 **같다**

| 축 | PRD §69.1 결과 대시보드 | GA형 관측 대시보드 (C1 요구) | 같은가 |
|---|---|---|---|
| 스택 | Next.js + TypeScript (`DB-001`, PRD §69) | 제약 없음 → 같은 것을 쓸 이유만 있다 | **같다** |
| 포트 | `:3001` (`DB-002`) | 3000은 커머스 점유(charter §6.3). 3001 외 근거 없음 | **같다** |
| 전달 경로 | 배치 산출 파일 읽기, API 없음 (`DB-013`) | 배치 산출 파일 읽기로 충분 (아래 §1.3-③) | **같다** |
| 갱신 | 수동 새로고침 (`DB-011`) | 실시간 요구가 어디에도 없다 | **같다** |
| 격리 | `results/` · `data/processed/`만 읽기 (`DB-014`) | 동일 제약을 받아야 안전하다 | **같다** |
| 디자인 토큰 | `Ecommerce_Service` 토큰 파이프라인 재사용 (PRD §69 결정적 근거) | 같은 팀·같은 사용자 | **같다** |
| 저장소 구조 | `dashboard/` **한 개** (SRS §31, `SRS:1915`) | — | **같다** |

→ **Q-β 답: 같다.**

## 1.2 판정 — 결론 하나

> ### 대시보드는 **하나**다. **가정 A8을 기각(REJECT)한다.**
>
> "GA형 로그/지표 추적 대시보드"와 PRD §69.1의 AI ROI 결과 대시보드는 **같은 애플리케이션**이다.
> 같은 스택(Next.js) · 같은 포트(`:3001`) · 같은 전달 경로(결과 파일 읽기) · 같은 격리 제약 · 같은 저장소 경로(`dashboard/`)를 쓴다.
>
> 다른 것은 **화면군(view group)** 이다.
>
> | 화면군 | 무엇을 보여주나 | 산출 주체 | 사이클 |
> |---|---|---|---|
> | **관측 화면군** (Observability) | 이벤트 수집 현황 · 계약 위반 · 필드 충족률 · 계산 가능/불가 · 데이터 품질 · 봉인 상태 | `src/measurement/` | **C1** |
> | **결과 화면군** (Result) | Churn · Cohort · Uplift · CLV · Segment · Optimization · A/B · Target List | `src/decision/` | 이후 |
>
> **C1은 `dashboard/` 애플리케이션을 세우고 관측 화면군을 구현한다.** 결과 화면군은 이후 사이클이 **같은 앱에 라우트를 추가**한다.

### 이 판정을 한 문장으로

**"화면은 둘, 앱은 하나."** — A8은 화면이 다르다는 점에서는 옳게 관찰했고, 그래서 "별개"라고 결론지은 지점에서 틀렸다.

## 1.3 근거 — 왜 앱을 나누지 않는가

**① Next.js를 고른 유일한 결정적 근거가 "토큰 두 벌 관리 금지"였다.**
PRD §69는 Streamlit을 기각한 결정적 근거로 **토큰 이중 정의**를 든다 — *"동일한 값을 UI마다 새로 정의하지 않고 토큰을 한 곳에서 스타일로 연결한다"*(`Plan/DESIGN.md`). 앱을 둘로 나누면 `Ecommerce_Service` 토큰 파이프라인을 **두 벌** 소비하게 되고, Streamlit을 기각한 바로 그 이유를 우리가 스스로 저지른다.

**② 저장소 구조에 `dashboard/`가 하나뿐이다.**
`SRS:1915`의 §31 구조는 `dashboard/`를 단수로 규정한다. 둘로 나누려면 **SRS를 고쳐야 하고, `Plan/` 수정은 이 팀의 권한 밖**이다(charter §5 · AGENTS.md 서브모듈 규약). 권한 밖 변경을 전제로 하는 설계는 채택할 수 없다.

**③ 두 화면군의 데이터 전달 경로가 이미 동일하다 — 그리고 정본이 그렇게 적혀 있다.**
`DB-013`은 `results/*.json` 파일 읽기를 규정한다. 관측 화면군의 데이터도 **정본상 같은 곳에 놓인다**:

- `docs/data_spec.html` §9 — *"모든 검사는 **`src/measurement/validate.py`에서 실행하고 `results/data_quality_report.json`에 결과를 남긴다**"*
- `tests/test_isolation.py:31-36`의 `FORBIDDEN_PATHS` — `src.simulator`만 `results/`가 금지다. **`src.measurement`는 `results/` 쓰기가 허용되어 있다**(실측 확인: `FORBIDDEN_PATHS["src.measurement"] == ("data/hidden", "data/ground_truth")`).

즉 **측정 계층이 `results/`에 게시하고 대시보드가 그것을 읽는 경로는 이미 정본이 승인한 경로**다. 새 전달 경로를 발명할 필요가 없고, API 서버도 필요 없다.

**④ 격리 규약을 두 벌 관리하게 된다.**
`DB-014`는 `dashboard/`에 `AGENTS.md`·`CLAUDE.md`를 두고 `decision`과 동일한 제약을 받게 한다(ISO-004). 앱이 둘이면 이 지침·검사·CI를 두 벌 유지해야 하고, **둘 중 하나만 검사가 헐거워지는 순간이 실제 누수 지점**이 된다.

**⑤ 포트 3002는 근거가 없다.**
charter §6.3과 `DB-002`가 규정하는 것은 "3000은 커머스, 대시보드는 3001 이상"이다. 세 번째 포트를 신설할 근거가 어느 문서에도 없다.

**⑥ 1차 독자가 같다.**
charter §7.1의 C1 대시보드 1차 독자는 **이 팀 · 다음 사이클 시뮬레이터 개발자 · 다음 사이클 AI 개발자**다. §7.2의 제품 전체 독자(리텐션 담당자·데이터 사이언티스트·의사결정자)는 결과 화면군을 본다. **두 독자는 시간축으로 나뉘지 사람으로 나뉘지 않는다** — 같은 사람이 다음 사이클에 결과 화면을 본다. 앱을 나누면 같은 사람에게 링크를 두 개 준다.

## 1.4 판정에 딸린 조건 — 셋 다 지켜야 판정이 성립한다

이 셋 중 하나라도 깨지면 위 판정을 다시 해야 한다. **W2 James(T2.7·T2.10·T2.11)와 W5-C Andrew의 전제다.**

### 조건 C-1 · 대시보드는 `data/raw/`를 읽지 않는다. 측정 계층이 `results/`에 게시한다

`DB-014`의 읽기 허용 목록은 **`results/`와 `data/processed/` 뿐이다. `data/raw/`가 없다.**
그런데 관측 화면군이 필요로 하는 원천은 Event Sink의 `manifest.json`이고, 그것은 Sink root(= `data/raw/`) 아래에 있다(`sink.py:220-245`).

→ **측정 계층이 관측 산출물을 `results/` 아래에 게시하고, 대시보드는 그것만 읽는다.**
`DB-013`·`DB-014`를 **한 글자도 고치지 않고** 성립한다. `data_spec` §9가 이미 같은 방향(`results/data_quality_report.json`)을 규정하므로 새 규칙이 아니라 **기존 규칙의 확장 적용**이다.

> **이 산출물 계약을 소유한 이슈가 현재 없다.** `#48`이 품질 리포트만 규정하고, 수집 현황·KPI 산출물의 게시 경로는 어느 이슈에도 없다.
> → 신규 이슈 초안 **`AIROI-M8`(측정 산출물 게시 계약)** 이 필요하다. `issue-priority.md` §4에 기록했다. **발행은 사용자 지시 후.**

### 조건 C-2 · 대시보드는 계산하지 않는다 (`DB-012`)

출처 분류·계산 불가 판정·집계는 **게시 시점에 측정 계층이 끝낸다.**
이 조건이 W1의 보완점 **W-7**(출처가 저장 레코드에 남지 않아 대시보드가 전량 재분류해야 한다, `sink.py:282-294`)을 **해소한다** — 대시보드가 재분류하지 않고, 측정 계층이 `event_source()` 결과를 집계해 게시하면 된다.
Sink는 이미 `manifest.sources`에 출처별 건수를 집계한다(`sink.py:139, 168, 237`). **게시만 하면 된다.**

### 조건 C-3 · `dashboard/`는 격리 검사의 사각지대다 — 덮어야 한다

W1 보완점 **W-8**: `tests/test_isolation.py:51-55`의 `_iter_source_files()`는 `SRC_ROOT`(= `src/`) 하위 `*.py`만 순회한다. **`dashboard/`는 `src/` 밖이고 TypeScript다 — 현재 검사가 한 줄도 보지 않는다.**

`DB-014`는 `dashboard/`가 `data/hidden/`·`data/ground_truth/`·`src/simulator/`에 접근하지 않을 것을 요구하지만, **강제하는 코드가 없다.**

→ **경로 문자열 검사를 `dashboard/**/*.{ts,tsx,js,json}`까지 확장할 것을 권고한다.** 설계는 W2 James(T2.11), 구현은 봉인 규칙상 **W6 Matthias + 사용자 승인**(task-graph §4 봉인 파일 표).
**C1에서 이 확장을 하지 않기로 결정할 수도 있다. 그 경우 "격리 검사는 대시보드를 보지 않는다"를 `docs/gate1_checklist.md`에 명시적 한계로 적는다** — 검사하지 않은 것을 통과로 적지 않는다(AGENTS.md).

## 1.7 가정 A5 재판정 — A8과 함께 판정하도록 charter가 지정했다

charter §8 **A5** — *"대시보드가 결과 파일 읽기만으로 충분"* (근거 PRD §69.1, 검증: A8과 함께)

> **판정: ✅ 유지. 단 조건 C-1이 지켜지는 한에서.**

- 관측 화면군이 필요로 하는 것은 **집계된 수치와 목록**이다 — 총 건수, 일자별·타입별·출처별 분포, 거부 사유별 건수, 필드 충족률, 계산 불가 지표 목록, 품질 검사 결과, 봉인 해시. 전부 **파일 한 벌로 표현 가능**하다.
- 원본 이벤트를 행 단위로 조회하는 요구는 charter §3.1③에 없다. **"이벤트 브라우저"는 C1 범위 밖이다.**
- 갱신 주기 요구도 없다(`DB-011` 수동 새로고침).

## 2.2 확정 USP

### USP-1 — **계산 불가를 계산 불가로 말하는 측정 계층** *(C1에서 증명한다)*

> **"근거 이벤트가 없거나 필드가 결손된 지표를 0으로 채우지 않는다. 계산 불가 상태를 사유와 함께 화면에 표시하고, 그 목록을 코드가 자동으로 산출한다."**

**왜 이것이 USP인가 — 제1원리**
기여이익 계산에 원가가 없을 때 0으로 채우면 **이익이 매출과 같아진다**(SRS `MEA-003` 근거 문단). 숫자는 나오고, 화면은 채워지고, 아무도 이상하다고 느끼지 않는다. **잘못된 결론이 조용히 만들어지는 것**이 이 도메인의 실제 실패 양식이다.
이 프로젝트는 지금 정확히 그 상황에 있다 — 커머스에 `unit_cost`가 없다(`Ecommerce #24`). 0으로 채우면 오늘 당장 대시보드가 그럴듯해진다.

**C1에서 증명하는 방법**
1. 빈 Sink가 Observable 16개 전부를 계산 불가로 표시한다 — **이미 코드로 존재**(`sink.py:240-256`, `tests/test_sink.py:198-203`)
2. 원가 근거가 없는 주문에 대해 COGS·기여이익이 **계산 불가로 산출된다** (`economic-rule-v1.md` §3)
3. 대시보드 V4·V5가 계산 불가를 **0과 다른 시각 상태 + 사유**로 렌더링한다 (스크린샷으로 증명)

**시장 근거** — `market-report.md` T1.9: GA4 Data Thresholding이 임계치 미만 데이터를 **0으로 채우지 않고 숨기며 경고 아이콘을 붙이는** 실제 사례. 원칙 자체는 새롭지 않다. **"그로서리 리텐션 AI ROI 검증"이라는 카테고리에서 1차 화면에 이를 구현한 선례는 조사되지 않았다**(한정형 문장으로만 사용).

**한계 — 정직하게** 이것은 "기능"이라기보다 **규율**이다. 경쟁 우위로 팔리는 종류의 것이 아니다. 그러나 C1이 증명할 수 있는 것 중 이것이 가장 실질적이고, **이 프로젝트 전체의 신뢰가 여기에 걸려 있다.**

### USP-2 — **정직성을 코드로 강제하는 실험 환경** *(C1에서 부분 증명한다)*

> **"'결과를 본 뒤 환경을 고치지 않았다'를 주장이 아니라 검사로 증명한다 — 파트 격리 AST 검사 + CI 자동 실행 + 재현 해시 + 봉인 커밋 대조."**

**C1에서 증명되는 부분**
- 파트 격리가 **실패하는 테스트**로 강제되고 CI가 매 PR에서 돈다 (`test_isolation.py:86-139` · `isolation.yml:36-41`) — **이미 존재·실행 확인**
- 동일 seed·config 재실행 시 파일 해시 일치 (`test_sink.py:216-225`) — **이미 존재**
- GATE 1 Lock 절차와 `simulator_commit` 대조 규약 문서화 (`#49` / M-7)

**C1에서 증명되지 않는 부분 — 명시한다**
- `events.parquet` SHA-256 재현성(`NFR-001`)은 **pyarrow 미설치로 `BLOCKED`** (W1 B-1). 의존성 도입(T2.9) 후에야 검증된다
- 격리 검사가 **`dashboard/`를 보지 않는다** (§1.4 C-3)
- **가장 위험한 누수 — "결과를 본 뒤 시뮬레이터를 고치는 것" — 은 원리상 이 테스트로 막을 수 없다**(`measurement-map.md` §2.3). 막는 것은 GATE 절차와 사람의 규율이다

**우위 주장 금지 규칙** 이 USP를 **상용 도구와 비교해 서술하지 않는다.** 비교 대상이 다른 것을 다루므로 비교 자체가 성립하지 않는다.

### USP-3 — **정책 수준 Incremental Profit 비교** *(이후 사이클 — C1은 전제만 Lock한다)*

> **"동일 시뮬레이션 환경·동일 홀드아웃·동일 경제 규칙 하에서, Full AI 리텐션 전략이 Rule-based Baseline 대비 만들어낸 순이익 증분을 원화(₩)로 산출한다."**

**C1이 하는 일 — 이것뿐이다**

**C1이 하지 않는 일** Incremental Profit을 **계산하지 않는다.** 두 전략이 없고 시뮬레이터가 없다. 값이 나오는 것은 이후 사이클이다.

**차단 조건 — 지금 해소되지 않으면 이 USP는 성립하지 않는다**
- `unit_cost` 부재(`Ecommerce #24`)가 남아 있는 한 **커머스 실측분에는 기여이익이 성립하지 않는다.** 해소책과 유효 범위는 `economic-rule-v1.md` §3에서 판정했다
- Caleb의 발견 — **환불/취소 이벤트 부재**가 기여이익 과대평가를 낳는다. `economic-rule-v1.md` §6에서 판정했고 **사용자 결정이 필요하다**(§4 D-2)

**서술 규칙** "업계 최초"라고 쓰지 않는다. `competitive-landscape.md`가 조사한 것은 5개 도구이며, **"조사된 5개 도구 중 발견되지 않았다"** 는 한정형으로만 쓴다.
