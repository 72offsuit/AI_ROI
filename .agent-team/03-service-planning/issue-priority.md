## 2.1 `ECOM-E10` — 검색 · 구매이력 · 상품목록 · 세션

**초안 요지:** `Ecommerce #28`이 커머스에 `search`·`return_visit` 포함 12종 이벤트 기록을 요구하는데 **그 이벤트를 발생시킬 기능이 존재하지 않는다.** 검색 화면 없음 · 구매 이력 화면 없음 · 세션 개념 없음 · 상품 목록 전용 라우트 없음.
`page_type` 8종 중 **3종(`list`·`search`·`history`)이 발생하지 않는다.**

### 판정 — **가장 시급하다. 그리고 4건으로 쪼갠다.**

**시급한 이유는 "크기"가 아니라 "숨어 있음"이다.**
`#28`(이벤트 기록)은 **이미 발행되어 있고 겉보기에 착수 가능해 보인다.** 그러나 실제로는 E10이 선행이다.
→ **누군가 `#28`을 착수하면 영원히 0건인 이벤트를 기록하는 코드를 쓴다.** E10이 발행되지 않은 채로 있으면 이 함정이 보이지 않는다.

### 4건 분할 — **초안의 제안을 수용하되 순서를 바꾼다**

초안은 `검색 → 구매이력 → 목록 → 세션` 순으로 나열했다. **의존 관계로 다시 배열하면 세션이 마지막이다.**

| 분할 | 내용 | 차단 | 발행 |
|---|---|---|---|
| **E10-a 검색** | 검색 입력·결과 화면·`catalog.ts` 조회 · `page_type=search` | **없음** | **즉시 가능** |

## 2.2 `ECOM-E11` — Treatment T4 Repurchase Reminder

**초안 요지:** `#24` 대조표가 `T4 … 없음 ❌` 로 기록했으나 **하위 이슈 `#25`~`#30` 어디에도 T4가 없다.** `#27`이 *"T4는 #E-4·별도 논의"* 로 넘겼는데 `#28`(=E-4)의 이벤트 목록에 `push_sent`·`campaign_exposed`가 **빠져 있다.** → **T4가 어느 이슈에도 속하지 않은 채 남았다.**

### 판정 — **발행 순서는 2순위. 그러나 필요한 것은 발행이 아니라 결정이다.**

**T4를 이번 과제 사이클에서 제외하는 결정이 정당하다.** 근거 셋:

| 근거 | 출처 |
|---|---|
| `data_spec` §6.2가 T4를 **"확장"**, T3를 **"사용"** 으로 표시한다 | `docs/data_spec.html` §6.2 |
| SRS `COM-005` Uplift MVP는 `Control = T0`, `Treatment = 선택된 단일 처치` | 초안 인용 |
| `data_spec` §4.2가 배정 규칙을 **`W=1 → T3`, `W=0 → T0`** 로 확정했다 — **T4가 실험 설계에 없다** | `docs/data_spec.html` §4.2 |

**세 번째가 결정적이다.** 실험 설계 정본이 이미 T3/T0만 쓴다. T4는 처치 공간의 완결성 문제이지 실험 수행의 차단점이 아니다.

### 그런데 완전히 빼면 안 되는 것이 하나 있다

**`push_sent` 이벤트는 T4가 없어도 필요하다.**
`data_spec` §6.2의 회계 규칙: `message_cost = 30원 / 발송 — 처치군 전원에게 발생(반응 여부 무관)`.
**T3 쿠폰을 보내는 행위 자체가 발송이다.** `push_sent`를 기록할 수 없으면 **발송 시점 비용을 셀 수 없고**, 그것은 *"반응하지 않은 고객에게 쓴 돈이 사라져 ROI가 과대평가된다"* 는 바로 그 상황이다.

> **판정 정정:** 초안은 `push_sent`·`campaign_exposed`를 **T4의 부속물**로 다뤘다. 그것이 정확하지 않다.
> **`push_sent`·`coupon_exposed`는 T3(MVP 처치)의 비용 회계에 필수다.** T4를 빼더라도 이 이벤트들은 남아야 한다.
> → **E11을 발행한다면 "T4 제외 결정 + `push_sent`/`coupon_exposed`는 `#28`에 편입"이 내용이 되어야 한다.**

**`#28`의 이벤트 목록에 `push_sent`·`campaign_exposed`가 빠져 있다는 W1의 발견(G-8)이 T4와 무관하게 실재하는 갭이다.**

## 2.3 `ECOM-E8` — 식별자 형식과 시각 표기

**초안 요지:** AI_ROI가 식별자 정규식 9종과 타임존 규약을 정본으로 갖는데 **커머스의 값 4종이 전부 형식을 벗어난다.** `product_id`(`dummyjson-16`) · `order_id`(`randomUUID()`) · `coupon_id`(`fixed-3000`) · 주문 시각(`…Z` UTC). 기존 이슈는 `session_id`(`#28`)와 `customer_id`(`#29`)만 다룬다.

### 판정 — **3순위. AI_ROI 쪽이 먼저 닫혀야 한다.**

**초안 스스로 이유를 적었다:** *"AI_ROI 쪽 식별자 형식이 아직 임의값입니다. `#43` 코멘트가 '근거 문서에 규정이 없어 임의로 정한 값'이라고 자인했고 `#49`(GATE 1)에서 Lock 예정입니다. → **Lock 이후에 착수하는 편이 재작업이 없습니다.**"*

**이것이 옳다.** 지금 발행하면 **커머스가 맞춰야 할 형식이 아직 확정되지 않은 상태**에서 작업 지시가 나간다. 형식이 Lock 과정에서 바뀌면 두 번 고친다.

### 차단 해소 시점

```
AI_ROI #54 (식별자 형식 검사 활성화 + 어휘 확정)
        ↓
AI_ROI #49 (EVENT SCHEMA v1 부분 Lock — events 테이블 한정)
        ↓
        E8 발행 가능 · E10-d(세션) 발행 가능
```

### 초안에 없는 보완 — 타임존은 AI_ROI 쪽도 아직 안 정했다

E8은 커머스에 *"모든 시각이 KST 오프셋(`+09:00`)을 포함한다"* 를 요구한다.
그런데 **AI_ROI `#53` D1-3의 미확정 항목이 정확히 이 정책이다** — ⑴ KST 오프셋만 허용하고 나머지 거부 ⑵ 어떤 오프셋이든 받아 KST로 변환. **`#53`이 ⑵를 제안했다.**

**⑵를 택하면 E8의 요구가 달라진다** — 커머스가 UTC로 써도 되고, 측정 계층이 변환한다. **E8을 지금 발행하면 ⑴을 전제한 수용 기준이 그대로 나간다.**
→ **`#53`의 타임존 정책 결정이 E8의 선행이다.** 초안에 없는 의존이다.
