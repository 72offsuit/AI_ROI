# 1. ★ 먼저 — **리드 판정 ⑵ 가 옳고 내 제안이 틀렸다**

리드가 물은 자리다. 답은 명확하다.

## 1.1 내가 틀린 이유

2차 리뷰 §1.3 에서 나는 두 가지를 같이 적었다:
> *"① `MetricValue` dataclass 에 `value_formatted` 필드 추가 … ② 포맷 주체 ⑵ `contracts.py` 직렬화(권장)"*

**①과 ②는 양립하지 않는다.** ②를 택하면 ①은 **두 번째 정본**을 만든다 — 호출자가 필드를 채울 수 있게 되고, 채운 값과 직렬화가 만든 값이 갈라진다.
**내가 결론(②)은 맞게 짚고 그 결론이 ①을 무효로 만든다는 것을 놓쳤다.** Matthew 가 ②를 택하고 ①을 버린 것이 맞다.

## 1.2 그리고 판단 근거를 실측으로 확인했다 — ⑵ 가 성립한다

`value_formatted` 는 **`(status, unit, value)` 의 순수 함수**여야 직렬화 시점 생성이 성립한다. 성립한다:

```
allOf[0]  status=="ok"          → required ["value","unit","basis"]     ← unit 보장
allOf[1]  status=="unconfirmed" → required ["value","unit","basis",…]   ← unit 보장
allOf[2]  계산 불가 3종          → value_formatted 금지 (unit 도 불필요)
```

**`ok`·`unconfirmed` 에서 `unit` 이 계약으로 보장된다** → 직렬화 함수가 항상 만들 수 있다.
§4.16.1 의 *"`unit` 이 없으면 `value_formatted` 도 없다 — 계산 불가 상태이므로 정상"* 도 이 구조와 정확히 맞는다.

**포맷 표가 `unit` enum 8종을 전수 덮는지 확인했다 — 덮는다:**
```
계약 enum: count · krw · krw_per_customer · ratio · days · percentage_point · text · datetime   (8종)
§4.16.1 표: krw · krw_per_customer · count · ratio · percentage_point · days · text · datetime  (8종)
                                                                        → 누락 0
```

**`toLocaleString()` 을 금지하고 명시적 포맷을 요구한 것**도 옳다 — 로케일은 환경마다 다르고 `NFR-001` 재현성이 걸린다.

## 1.3 ★ `limit_note` 를 **반대로** 처리한 것이 이번 수정에서 가장 좋다

이번 라운드에서 내가 가장 날카롭게 볼 자리로 잡았던 곳인데, 이미 정확하게 갈라져 있었다.

m-03 §4.7 에 이 대비표가 그대로 있고, `limit_note` 만 dataclass 필드로 뒀다.
**두 필드를 "계약에 새로 넣는 두 개"로 묶어 같이 처리했으면 틀렸을 자리다.** 유도 가능성이 기준이라는 것을 정확히 잡았다.

# 4. 🟢 F-E — 닫혔다. 독립 재현했고 *교체*가 정답이다

## 4.1 독립 재현 (순수 논리)

```
현행 allOf[2].then.required = ["examined_rows", "reason_code", "reason_detail"]

레코드                 현행 allOf[2]   추가하려던 절    최종(AND)
reason_code 있음          통과           거부           ★거부
reason_code 없음          거부           통과           ★거부
```

**두 경우 다 거부 — `vacuous` 가 만족 불가능해진다.** 리드 재현과 일치한다.

```
교체안 (required 에서 reason_code 제거 + not 추가)
  reason_code 없음  → 통과 ✅
  reason_code 있음  → 거부 ✅   (의도한 대로)
```

## 4.2 왜 이것이 NR-1 의 거울상인가 — 원인이 같다

| | NR-1 | F-E |
|---|---|---|
| 편집 | `not.required` 배열에 이름 **추가** | 새 `allOf` 절 **추가** |
| 잘못 | 막아야 할 것을 **통과**시킨다 | 통과시켜야 할 것을 **전부 막는다** |
| **원인** | **`allOf`·`not` 이 이미 점유된 자리를 "빈 칸"으로 보고 더한다** | **동일** |

**둘 다 *"기존 절이 무엇을 이미 강제하는지 읽지 않고 더한 것"* 이다.**
그래서 AC-4d 의 *"읽어서 판단하지 않는다 — validator 로 확인한다"* 가 **정확히 옳은 처방**이다. §7.

**`vacuous` 만 교체이고 `blocked`·`not_run` 은 추가가 맞다**는 구분도 확인했다 — 현행 `allOf` 에 그 둘에 대한 `reason_code` 제약이 없으므로 추가가 맞다.

# 6. 🟢 NR-3 — 닫혔다. **내가 낸 두 안 중 어느 쪽도 아닌 셋째 안이고, 더 낫다**

## 6.1 ★ 그리고 내가 못 본 구멍을 하나 더 막았다

AC-4c 도 함께 확인했다 — `choose_headline_code()` **단일 함수**(화면·테스트가 같은 것을 쓴다) · 픽스처 2벌 재계산 단언 · **표본 밖 8종 단위 테스트**.

# 7. 🟢 AC-4d — 충분하다. **이것이 이번 사이클에서 가장 값진 산출물이다**

리드가 *"충분한지 판단하라"* 고 물었다. **충분하다.** 이유 셋:

**① 실패 양식을 정확히 겨눈다.** NR-1 과 F-E 는 *"고쳤다"* 와 *"고친 것이 의도대로 동작한다"* 사이에서 났다.
AC-4d 가 그 틈을 **실행으로** 닫는다. 두 사고가 실물 근거로 붙어 있어서 다음 사람이 이유를 안다.

**② 양방향을 강제한다.** `vacuous` 항목이 *"통과하는 것과 거부되는 것을 **둘 다** 확인한다 — 하나만 보면 만족 불가능해진 것을 못 잡는다"* 로 적혔다.
**F-E 는 정확히 "한쪽만 보면 안 잡히는" 결함이었다.** 재발 경로가 막혔다.

# 9. 남은 것 — noncritical 2 + 경미 1

## NF-1 (noncritical) · ★ `vacuous` 교체가 만드는 **픽스처 실패 7건**이 §4.14 목록에 없다

**F-E 수정의 부수 효과를 계산했다:**

```
$ python3 -c "교체안(required 에서 reason_code 제거 + not 추가)을 empty-sink 의 vacuous 7건에 적용"

DQ-01  reason_code=NOT_RUN → ★거부      DQ-02b reason_code=NOT_RUN → ★거부
DQ-04  reason_code=NOT_RUN → ★거부      DQ-07  reason_code=NOT_RUN → ★거부
DQ-08  reason_code=NOT_RUN → ★거부      DQ-10  reason_code=NOT_RUN → ★거부
DQ-11  reason_code=NOT_RUN → ★거부
                                        ─────────────────
                                        7건 전부 거부
```

**`empty-sink` 의 `vacuous` 7건이 전부 `reason_code: "NOT_RUN"` 을 갖고 있다** — m-07 §7.2 가 *"Q-2 와 똑같은 종류의 결함"* 이라고 지적한 바로 그것이다.
**즉 이 수정은 의도대로 작동하는데, 그 결과가 픽스처 7건 실패다.**

**그런데 `INTENDED_FIXTURE_FAILURES` 4항목 어디에도 없다** (Q-2 / Q-3 / C-1-missing / Q-4).

AC-4d 가 *"`empty-sink` 픽스처의 `vacuous` 7건이 수정 후 스키마에서 어떻게 되는지 **확인하고 §4.14 목록과 대조한다**"* 로 **예고는 했다.**
**그런데 목록에 항목이 없고, §4.14 규칙은 *"목록에 없는 실패 = 회귀. 즉시 실패"* 다.**
→ W5 는 등록되지 않은 의도된 실패 7건을 만나고, **C-3 이 막으려던 세 도피로가 다시 열린다** (제약을 뺀다 / 픽스처를 고친다 / 예외 처리한다).

**답은 지금 계산된다. 등록하면 끝난다:**

```python
("empty-sink", "data_quality_report", "vacuous:reason_code"):
    "F-E/Matthias 항목2 — vacuous 7건(DQ-01·02b·04·07·08·10·11)이 전부 reason_code:NOT_RUN 을 "
    "갖고 있다. '실행했는데 0행'과 '실행 안 함'이 한 행에 섞인 것으로, allOf[2] 교체가 "
    "이것을 거부한다. 이 실패가 교체가 작동한다는 증거다.  판별: validator == 'not'",
```

> **C-3 과 같은 부류가 한 번 더 나온 것이다.** 다만 이번엔 **AC 가 그 자리를 가리키고 있어서** 성격이 다르다 —
> *"모르고 지나갈 결함"* 이 아니라 *"알고 있는데 등록만 안 한 것"* 이다. **그래서 noncritical 이다.**

## NF-2 (noncritical) · *"의도된 실패 **3종**"* 표기가 실제와 어긋난다

```
AC-4b:107   "★ 픽스처의 의도된 실패 3종을 목록으로 명시"
T5:1104     "★ 의도된 실패 3종이 실제로 실패하는지"

실제 INTENDED_FIXTURE_FAILURES  =  4항목   (Q-2 · Q-3 · C-1-missing · Q-4)
NF-1 을 등록하면              =  5항목
```

**T5 가 *"3종이 실제로 실패하는지"* 를 확인하면 4번째·5번째는 검사되지 않는다.**
*"통과해 버리면 제약이 안 걸린 것이다"* 가 이 AC 의 요점인데, **세지 않은 항목은 통과해도 모른다.**

→ **숫자를 빼고 *"목록의 **모든** 항목이 실제로 실패하는지"* 로 쓴다.** 항목이 늘 때마다 숫자를 고치는 자리를 없앤다.
Q-4 를 추가할 때 3→4 를 놓친 것이 그 증거다.

## 경미 · m-03 §4.7 불변식 표에 `ok`·`unconfirmed` → **`unit` 필수**가 없다

§4.16.1 이 *"`unit` 을 빠뜨리면 `value_formatted` 를 만들 수 없다 — `unit` 은 표시용 장식이 아니라 **필수 입력**이다"* 라고 적었고,
m-03 §4.7 도 *"`unit` 을 정확히 넣는 것이 이 스토리의 몫"* 이라고 적었다. **그런데 `__post_init__` 불변식 표에 그 행이 없다.**

계약은 이미 강제한다 (`allOf[0]`·`allOf[1]` `required` 에 `unit`). §4.7 자신의 원칙이 *"계약이 강제하는 불변식을 dataclass 가 그대로 담아야 한다"* 이므로 **표에 있어야 일관된다.**

→ 한 행 추가: `status ∈ {ok, unconfirmed} → unit 필수`.
**`unit` 없는 `MetricValue` 가 만들어지면 직렬화가 `value_formatted` 를 못 만들고, 게시물이 자기 계약을 어긴다.** 그 사슬을 `__post_init__` 이 첫 자리에서 끊는다.
