# [발행됨 → Ecommerce_Service#33] fix: 주문의 경제값을 저장한다 — 배송비·할인이 조용히 0으로 채워진다

> **발행 완료 (2026-09-11):** https://github.com/72offsuit/Ecommerce_Service/issues/33 · 상위 Issue: #24 · label: `bug`

## 문제와 목적

- **현재 문제:** `orders` 테이블이 `id, user_id, created_at, total_krw` **4개 컬럼뿐**입니다(`src/lib/server/commerce/schema.ts:49-54`). 상품 합계·할인·배송비는 저장되지 않고, **쿠폰 스냅샷이 있을 때만** 역산해 복원합니다(`orders.ts:56-77`). 쿠폰을 쓰지 않은 주문은 이렇게 처리됩니다:

  ```ts
  // orders.ts:58-66
  return { ...record, subtotalKrw: record.totalKrw, discountKrw: 0, shippingKrw: 0, ... }
  ```

  지금은 배송비가 실제로 0이라 우연히 맞습니다. **#26이 배송비 정책을 도입하는 순간, 쿠폰 없는 모든 주문의 배송비가 조용히 0으로 보고됩니다.**

- **작업으로 달성할 결과:** 주문 시점의 경제값이 사실대로 남아, 기여이익 계산(PRD §62-64)이 사후에 재현 가능해집니다.

## 왜 "조용한 0"이 특히 위험한가

AI_ROI PRD §10.1과 SRS MEA-003은 **없는 값을 0으로 채우지 말고 결손으로 기록하라**고 규정합니다.
*"원가가 없는데 0으로 채우면 기여이익이 매출과 같아져 잘못된 결론이 조용히 만들어진다"* (`AI_ROI/src/measurement/sink.py:11-14`).

지금 구조는 정확히 그 패턴입니다 — **값이 없다는 사실이 소실되고 0이라는 주장으로 바뀝니다.** 나중에 "배송 보조금이 0원이었다"는 잘못된 결론이 조용히 만들어집니다.

## 요구사항 대조

| 요구 | 근거 | 현재 | 판정 |
|---|---|---|---|
| 주문 금액 구성요소 보존 | PRD §62 `Contribution = Revenue − COGS − 할인 − 배송보조 − 캠페인비` | `total_krw`만 저장 | ❌ |
| 배송비 스냅샷 | #26 수용 기준 | 컬럼 자체가 없다 | ❌ |
| 할인 스냅샷 | — | `order_coupon_snapshots`에만, **쿠폰 사용 시에만** | ⚠️ |
| 결손 비은폐 | AI_ROI SRS MEA-003 | 0으로 대치 (`orders.ts:62-64`) | ❌ |

`saveOrder()`(`orders.ts:100-113`)는 `subtotalKrw`·`discountKrw`·`shippingKrw`를 **인자로 받아 합계 검증까지 하고도**(`orders.ts:108-110`) 저장하지 않습니다 — 정보가 그 자리에서 버려집니다.
