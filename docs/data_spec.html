1. 목적과 예측 정의

예측 기준일 T0까지 관측된 행동만으로, 각 고객에 대해 ①이탈 확률·②처치 시 이탈이 바뀌는 정도(Uplift)·③12개월 기여이익(CLV)을 산출하고, 주어진 예산 안에서 개입했을 때 행동이 바뀌는 고객을 선별해 Rule-based 대비 증분 기여이익을 증명한다.

세 예측 과제는 목적·대상 모집단·정답 관찰기간이 서로 다르다. 하나의 표로 고정한다.

과제대상 모집단 (T0 기준)결과변수 Y정답 관찰기간모델
Churn 예측가입 60일 경과 · 누적 구매 ≥ 1 · 마지막 구매 ≤ 42일향후 42일 구매 0건 = 1T0+1 ~ T0+42Tree ML 2종 + DL + Ensemble
Uplift (CATE)가입 60일 경과 · 누적 구매 ≥ 1 · 마지막 구매 ≥ 14일 경과Retention = 향후 42일 구매 ≥ 1건T0+1 ~ T0+42T-Learner · X-Learner
CLV가입 90일 경과 · 누적 구매 ≥ 1향후 365일 누적 기여이익T0+1 ~ T0+365BG/NBD + Gamma-Gamma 또는 GBM

결과변수를 Retention으로 두는 이유

Uplift의 Y를 이탈(1=이탈)이 아니라 유지(1=유지)로 정의하면 Qini Curve의 세로축이 “추가로 유지시킨 고객 수”가 되어 부호 해석이 직관적이고, Incremental Profit과 방향이 일치한다. Churn 모델의 라벨과는 churn = 1 - retained 관계이므로 동일 데이터에서 파생된다.

Churn 대상과 캠페인 대상이 다르다

Churn 예측은 아직 이탈하지 않은 고객의 위험을 재는 과제이고, Win-back 캠페인은 이미 구매가 끊긴 고객까지 포함한다. 두 모집단을 같은 것으로 두면 라벨이 동어반복이 되거나 캠페인 대상이 잘려 나간다. 위 표대로 분리한다.

문제 정의의 핵심: 이 시스템은 이탈 확률이 가장 높은 고객을 찾는 것이 목적이 아니다. 이탈 확률이 높아도 무엇을 해도 떠나는 고객(Lost Cause)과, 개입하면 남는 고객(Persuadable)은 다르다. 따라서 최종 타게팅 기준은 Churn Probability가 아니라 Uplift × CLV − Cost다.

2. 시간축 — 예측 기준일과 관찰기간

시간축은 고정된 기간이 아니라 파라미터다. 시뮬레이터는 요구하는 만큼 시간을 진행시킬 수 있으므로(1개월·6개월·12개월·24개월 …), 이 절이 확정하는 것은 총 기간의 값이 아니라 구간들 사이의 관계다. 아래 Reference Run은 그 관계를 만족하는 하나의 인스턴스이며, 다른 기간으로 바꿔도 규칙은 그대로 성립한다.

기간을 바꿀 때 지켜야 할 것

  • warmup_days는 가장 긴 Feature 윈도우(180일)보다 커야 한다. 작으면 해당 Feature가 전부 결측이 된다.
  • label_window_days는 프로파일 간에도 고정한다(42일). 바뀌면 런끼리 Incremental Profit을 비교할 수 없다.
  • 관측하려는 라벨의 기간만큼 런이 실제로 진행되어야 한다. 그 외에는 제약이 없다.

프로파일 간 비교 규칙

  • 고객 생성 seed가 같으면 같은 고객이 더 오래 산 것이다. 프로파일을 바꿔도 고객 모집단은 유지된다.
  • 따라서 short에서 얻은 결론을 reference에서 재확인하는 방식이 성립한다.
  • 단 warmup_days가 다르면 T0 시점 고객 상태가 달라지므로, 성능 수치는 프로파일 안에서만 비교한다.

3.4 일별 행동 생성 규칙 (Tick = 1일)

# ① 방문
p_visit(i,t) = clip( base_visit_frequency_i / 7
                     × s_weekday(t) × s_season(t)
                     × decay_i(t) × treat_boost_i(t),  0, 1 )

s_weekday  = {월 .95, 화 .95, 수 1.00, 목 1.05, 금 1.20, 토 1.15, 일 .85}
s_season   = 명절 직전 7일 1.40 / 연말 12월 1.20 / 그 외 1.00
decay_i(t) = exp( −λ_i · max(0, t − t_decay_i) )        # 이탈 진행 감쇠
             λ_i = 0.004 + 0.020 · base_churn_propensity_i
             t_decay_i : P5는 Day 0, 그 외는 Bernoulli(base_churn_propensity_i)로
                         진입 여부를 뽑고 Uniform(60, 500)에서 시점 샘플링

# ② 구매 (방문한 경우에만)
p_buy(i,t) = clip( base_purchase_probability_i
                   × cycle_factor(i,t) × price_factor(i,t)
                   × coupon_factor(i,t) × ship_factor(i,t), 0, 1 )

cycle_factor = 1 − exp( −days_since_last_purchase / purchase_cycle_i )
price_factor = 1 − price_sensitivity_i · (basket_price_index − 1)
coupon_factor= 1 + coupon_sensitivity_i · active_discount_rate(i,t)
ship_factor  = 1 − shipping_fee_sensitivity_i · 1{basket < 40,000원} · 0.35

# ③ 장바구니 / 세션
basket_size    ~ Poisson(λ = 3 + 6 · (AOV_i / 45,000))     범위 [1, 18]
order_amount   = Σ unit_price × quantity                    (AOV_i 중심으로 수렴)
page_views     ~ Poisson(4 + 9 · search_propensity_i)
session_duration ~ Gamma(shape=2, scale=110초) × (1 + search_propensity_i)
cart_abandon   ~ Bernoulli(cart_abandonment_propensity_i)   # 담고 미구매

# ④ 부수 행동
review     ~ Bernoulli(review_propensity_i)      구매 후 1~5일 내
cs_contact ~ Bernoulli(cs_contact_propensity_i / 30)  일 단위

3.5 시간에 따른 행동 변화 (PRD §26 필수)

감쇠 decay_i(t)가 걸린 고객은 다음 5개 지표가 동시에 움직인다. 이 변화가 곧 Behavioral Change Feature(§8)가 잡아내야 할 신호다.

↑ purchase_interval — 구매 간격 증가
↓ visit_count_recent_2w — 방문 빈도 감소
↓ session_duration — 체류시간 감소
↑ cart_abandonment_rate — 담고 안 사는 비율 증가
↓ search_to_purchase_conversion — 탐색 대비 전환 하락
↓ repurchase_probability — 재구매 확률 하락
설계 의도: 감쇠는 연속적이고 시점이 고객마다 다르다. 특정 날짜에 일괄 스위치가 꺼지는 방식이면 모델이 날짜 하나만 학습해 AUC가 비현실적으로 높아진다(PRD Risk 2 “Unrealistically Easy Model”). 감쇠 시작 시점은 Uniform(60, 500)에서 개별 샘플링한다.

4. 처치군·통제군 정의와 결과 생성 규칙

Uplift 모델은 관측 데이터만으로는 검증할 수 없다. 무작위 배정된 처치군과 통제군, 그리고 처치가 결과를 어떻게 바꾸는지에 대한 명시적 생성 규칙이 있어야 Qini가 의미를 갖는다. 이 절이 그 규칙을 확정한다.

4.1 Eligible Population

eligible(i) = (T0 − signup_date_i ≥ 60일)
            AND (lifetime_order_count_i ≥ 1)
            AND (days_since_last_purchase_i ≥ 14일)

조건의 근거

  • 가입 60일 — 행동변화 Feature(최근 2주 vs 직전 2주)를 계산할 최소 이력.
  • 구매 ≥ 1 — 구매 이력이 없으면 재구매 유도 캠페인의 대상이 아니다(온보딩은 별도 전략 S6).

4.3 처치 효과 생성 규칙 교수자 피드백 반영

처치는 모든 고객에게 같은 크기로 작동하지 않는다. 고객별 효과 τi를 Hidden Trait에서 결정론적으로 계산한 뒤, 관찰기간 동안 구매 확률에 승법으로 적용한다.

# 고객별 처치 효과 (T0에서 1회 결정)
τ_i = 0.55 · coupon_sensitivity_i · recency_gain_i          # 긍정 성분
      − 0.45 · max(0, marketing_fatigue_i − 0.6) / 0.4       # 부정 성분(Sleeping Dog)

recency_gain_i = clip( days_since_last_purchase_i(T0) / 28,  0.3, 1.5 )

# 관찰기간 중 구매 확률 부스트 (Treatment군에만 적용)
treat_boost_i(t) = 1 + τ_i · exp( −(t − T0) / 7 )      for  T0 ≤ t ≤ T0+13
                 = 1                                    for  t > T0+13

# 쿠폰 사용 조건: order_amount ≥ 50,000원 인 주문에 한해 7,000원 차감
# 최소주문금액 미달 시 쿠폰 미사용 → 할인 비용 미발생, 메시지 비용만 발생

이 식이 만드는 4분면

  • Persuadables — coupon_sensitivity 높고 fatigue 낮음 → τ > 0, 기저 유지확률 중간
  • Sure Things — 기저 구매확률이 이미 높아 처치 없이도 유지 → Y(0)=Y(1)=1
  • Lost Causes — 감쇠가 깊게 진행 → 처치해도 Y(1)=0
  • Sleeping Dogs — marketing_fatigue > 0.6 → τ < 0, 처치가 역효과

강도 가드레일 필수

PRD Risk 4 “Treatment Too Strong”에 대응해 생성 결과가 아래 범위를 벗어나면 GATE 1 이전에 τ_base = 0.55를 조정한다. GATE 1 이후에는 조정하지 않는다.

  • 전체 ATE(유지율 차이): 3.0 ~ 6.0 %p
  • 쿠폰 사용률: 25 ~ 40%
  • Sleeping Dog 비율: 8 ~ 15%

4분면 목표 분포

Persuadables · 20 ~ 30%Y(1)=1, Y(0)=0 — 처치가 유지를 만들어낸 고객. Qini가 잡아내야 할 대상.
Sure Things · 30 ~ 40%Y(1)=Y(0)=1 — 처치 없이도 유지. 쿠폰은 순수 손실.
Lost Causes · 20 ~ 30%Y(1)=Y(0)=0 — 처치해도 이탈. 비용만 발생.
Sleeping Dogs · 8 ~ 15%Y(1)=0, Y(0)=1 — 처치가 이탈을 유발. 반드시 제외해야 할 대상.

4.4 Potential Outcome 이중 실행 추가 제안

시뮬레이터이므로 같은 고객의 반사실(counterfactual)을 실제로 관측할 수 있다. 이 이점을 버리지 않는다.

for W in (0, 1):
    rng = PCG64(seed = customer_seed_i)        # ← Common Random Numbers
    Y_i(W) = simulate(customer_i, treatment=W, days = T0+1 .. T0+42)

true_uplift_i = Y_i(1) − Y_i(0)                # Ground-truth CATE

관측 데이터셋에는 W_i 에 해당하는 결과만 남긴다:  Y_i^obs = Y_i(W_i)
반사실은 data/ground_truth/ 에 분리 저장한다.

처치 여부를 제외한 모든 난수를 동일 스트림에서 뽑기 때문에(Common Random Numbers), Y(1)과 Y(0)의 차이는 오직 처치에서 온다. 이 설계로 두 가지를 얻는다.

얻는 것 ①

Qini 지표 자체를 검증할 수 있다. 무작위 실험으로 추정한 Qini와 Ground-truth CATE 기준 이론적 최대 Qini(Qinioracle)를 비교하면, 모델의 개선 여지가 얼마나 남았는지 정량적으로 말할 수 있다.

얻는 것 ②

Uplift 모델의 직접 평가 지표(PEHE, corr(τ̂, τ))를 산출할 수 있다. Qini는 순위 품질만 보지만 이 지표는 CATE 추정 오차를 본다.

사용 금지 규칙 엄수 — data/ground_truth/는 다음에 절대 사용하지 않는다: 모델 학습 입력, Feature 생성, 하이퍼파라미터 튜닝, Threshold 선택, 타게팅 의사결정, 대시보드 타게팅 근거. 최종 리포트의 사후 진단 지표로만 쓴다. 이 경로를 읽을 수 있는 모듈은 src/diagnostics/ 하나뿐이며, src/decision/이 이 경로나 src/diagnostics를 참조하면 tests/test_isolation.py가 실패한다 (§17.3 · §17.4).

5. 이탈 정의

이탈은 서비스 운영 상태와 모델 학습 라벨 두 가지로 쓰이며, 둘은 다른 개념이다. 혼용하면 라벨 누수가 발생한다.

① 운영 상태 (Derived State Event)

Active   : 마지막 구매 후 ≤ 27일
At Risk  : 마지막 구매 후 28 ~ 41일
Churn    : 마지막 구매 후 ≥ 42일

대시보드 표시·코호트 분석·Rule-based Baseline 조건에 사용한다. 후향적(backward-looking) 정의다.

② 모델 라벨 (Prediction Target)

churn_label_i =
  1  if  count(purchase | T0 < t ≤ T0+42) == 0
  0  otherwise

retained_i = 1 − churn_label_i

전향적(forward-looking) 정의다. T0 시점의 recency 상태와 독립적으로 계산되므로 Feature와 라벨이 동어반복이 되지 않는다.

왜 분리하는가: 운영 상태 정의를 그대로 라벨로 쓰면 days_since_last_purchase ≥ 42라는 Feature가 라벨을 거의 완전히 결정한다. AUC는 0.99가 나오지만 학습된 것은 아무것도 없다(PRD Risk 7 “Churn Label Leakage”). 전향적 window 라벨은 이 문제를 구조적으로 차단한다.

5.1 임계값 확정 절차

28일 / 42일은 현재 가설값이다(PRD §28은 [PROJECT-DECISION]·미확정으로 명시). GATE 1 이전에 다음 절차로 확정한다.

1. Warm-up 구간(Day 0–272)의 고객별 구매 간격 분포를 산출한다.
2. 전체 구매 간격의 P75 / P90 분위수를 구한다.
3. at_risk_days ≈ P75,  churn_days ≈ P90  근방인지 확인한다.
4. 확정값으로 재생성했을 때 Generated Churn Rate 가 15 ~ 25% (SIM-005) 안에 드는지 확인한다.
5. 두 조건을 만족하면 config/simulator_config.yaml 에 기록하고 GATE 1 에서 Lock 한다.
churn:
  at_risk_days:    28      # 확정 대기 — 위 절차 4단계 통과 후 Lock
  no_purchase_days: 42
  no_login_days:    60
  rule_operator:   OR
  label_window_days: 42    # 모델 라벨 관찰기간 (운영 정의와 별개로 고정)

주의: label_window_days는 운영 정의가 바뀌어도 42일로 고정한다. 라벨 관찰기간이 바뀌면 Baseline과 AI 전략의 비교 기준이 달라져 Incremental Profit을 비교할 수 없다.

10.4 다중 T0 런에서의 시점 분할

rolling 프로파일은 같은 고객 모집단 위에서 캠페인을 여러 시점에 반복 집행한다. 이때 Uplift 모델도 “과거 캠페인에서 학습 → 미래 캠페인에서 평가”가 가능해져, 실제 운영과 같은 형태의 검증이 성립한다.

campaign_index_dates = [T0¹, T0², T0³, …]      # 간격 ≥ label_window_days + cooldown_days
cooldown_days = 28                              # 직전 캠페인 대상 고객의 재노출 금지 기간

각 T0ᵏ 마다:
    - Eligible 재평가 → 층화 무작위 재배정 (배정은 캠페인마다 독립)
    - Feature Cutoff = T0ᵏ − 1일,  라벨 = (T0ᵏ, T0ᵏ + 42]
    - 직전 캠페인에서 처치받은 고객은 cooldown 기간 동안 배정 대상에서 제외

분할:
    학습  = T0¹ … T0ᵏ⁻¹ 의 캠페인 데이터
    평가  = T0ᵏ 의 캠페인 데이터            ← 가장 미래 시점
    고객 분할은 그대로 유지 (동일 고객이 학습·평가에 동시에 들어가지 않게)

이 설계로 답할 수 있는 질문

  • T0¹에서 학습한 Uplift 모델이 T0³에서도 통하는가 — 시점 일반화
  • 같은 고객에게 캠페인을 반복하면 효과가 감쇠하는가 — marketing_fatigue 누적 효과
  • 계절(명절·연말) 구간의 T0에서 Uplift 순위가 뒤집히는가
  • 모델을 언제 재학습해야 하는가 — Retrain Trigger 근거

주의

  • 캠페인 간격이 label_window_days보다 좁으면 라벨 구간이 겹쳐 효과가 섞인다. 간격 ≥ 70일(42+28)을 지킨다.
  • 반복 노출은 marketing_fatigue를 실제로 누적시키므로, 후반 T0의 ATE가 낮아지는 것은 버그가 아니라 설계된 현상이다.
  • 각 T0의 결과를 평균내지 않는다. 시점별로 따로 보고해야 감쇠 추세가 보인다.

  • 전략 비교(§13)의 “동일 고객·동일 기간” 전제가 깨져 Incremental Profit을 같은 잣대로 비교할 수 없다.

12. Rule-based Baseline (S1) 규칙

Incremental Profit의 기준선이므로 AI보다 먼저, 그리고 AI 결과를 보기 전에 확정한다(SRS BASE-003).

12.1 선정 규칙

S1_Rule_based(i) at T0:

  SELECT   i
  WHERE    eligible_flag = 1
    AND    28 ≤ days_since_last_purchase_i ≤ 90
    AND    lifetime_order_count_i ≥ 2
  ORDER BY days_since_last_purchase DESC          # recency가 나쁜 순
  LIMIT    예산 소진 시점

  ACTION   T3 Win-back Coupon (50,000원 이상 7,000원 할인, 유효 14일)

각 조건의 근거

  • 하한 28일 — 운영 정의상 At Risk 진입 시점. 그 전에 보내면 살 고객에게 쿠폰을 낭비한다.
  • 상한 90일 — 90일을 넘기면 실무적으로 회수 확률이 급감한다. 무한정 보내지 않는다는 현실적 제약.
  • 구매 2회 이상 — 1회 구매 후 이탈은 온보딩 실패이며 Win-back 대상이 아니다.
  • Recency 내림차순 — 실무 CRM이 가장 흔히 쓰는 우선순위. “가장 위험한 고객부터”라는 직관을 그대로 구현한다.

이 Baseline이 좋은 비교 대상인 이유

S1은 고위험 고객을 정확히 겨냥한다. 즉 Churn 예측만 잘하는 AI(S2)는 S1을 크게 이기기 어렵다.

차이가 나는 지점은 “위험하지만 개입해도 안 바뀌는 고객(Lost Cause)”과 “개입하면 역효과인 고객(Sleeping Dog)”을 S1은 걸러내지 못한다는 데 있다. 이 프로젝트의 가설이 정확히 그 지점을 겨냥하므로, S1은 약한 상대가 아니라 정직한 상대다.

13. 전략 비교 프로토콜

Rule-based와 AI를 동일 고객 · 동일 예산 · 동일 기간에서 비교한다. 이 세 가지가 어긋나면 어떤 성능 차이도 근거가 되지 않는다.

동일 고객

  • 모집단: Test 20% 고객 (그리고 최종 1회는 Final Holdout)
  • 동일 customer_seed · 동일 Hidden Trait
  • 전략별로 재생성하지 않는다

동일 예산

  • B = Crule (S1의 실집행 비용, §12.2)
  • 모든 AI 전략은 이 상한을 넘길 수 없다
  • 추가로 50% / 100% / 200% What-if를 별도 산출

동일 기간

  • 집행: T0 (2025-10-01) 1회
  • 반응 관찰: T0 ~ T0+13
  • 성과 관찰: T0+1 ~ T0+42

13.4 기간별 지표 개선 오케스트레이션

시뮬레이터는 시간을 임의로 진행시킬 수 있는 상태 엔진이므로(PRD v2.1 §25, SRS SIM-012), §13.2의 1회 비교를 기간을 바꿔 가며 반복할 수 있다. 최종 완성 상태의 운영 형태다.

sim = Simulator.init(seed=42, num_customers=26000, profile="rolling")
sim.advance(warmup_days)                                  # 이력 축적

for k, T0 in enumerate(campaign_index_dates):             # 1M / 6M / 12M … 자유
    snap = sim.snapshot()                                 # 전략 비교의 분기점
    features = build_features(sim.events(until=T0 - 1d))  # Feature Cutoff
    for strategy in [S0, S1, S2, S3, S4, S5]:
        sim.restore(snap)                                 # 동일 시점 · 동일 난수
        sim.apply_treatment(strategy.select(features, budget=C_rule))
        sim.advance(label_window_days)                    # 42일 진행
        report(k, strategy, sim.metrics(T0, T0 + 42))
    sim.restore(snap)
    sim.advance(campaign_interval_days)                   # 다음 T0 로 (≥ 70일)

이 루프가 보장하는 것

  • snapshot/restore로 모든 전략이 같은 시점·같은 고객 상태에서 출발한다 — “동일 고객·기간”이 코드로 강제된다.
  • advance(a)+advance(b) ≡ advance(a+b) 분할 불변성 덕에 반복 횟수·간격을 바꿔도 결과가 재현된다.
  • 기간별 결과를 시점 순으로 나열하면 모델 노후화 추세와 Retrain Trigger 근거가 나온다 (§10.4).

루프 안에서 하면 안 되는 것

  • 중간 결과를 보고 시뮬레이터 파라미터를 바꾸는 것 — GATE 1 이후 금지 (§11.2).
  • 중간 결과를 보고 S1 규칙이나 C_rule을 바꾸는 것 — GATE 2 이후 금지.
  • Final Holdout 모집단을 루프에 넣는 것 — 확정 전략 1회 평가에만 쓴다 (§10.2).

전략 간 시뮬레이션 잡음이 비교를 흐린다전략 실행에도 Common Random Numbers 공유 + snapshot/restore로 동일 시점 분기. 차이가 타게팅에서만 오도록 고정§13.2 · §13.4
시뮬레이터 담당과 시스템 담당이 서로의 작업을 보면 과적합된다 — 어떻게 막나격리 아키텍처 3층(파트별 AGENTS.md+CLAUDE.md · test_isolation.py · simulator_commit 기록). .gitignore·삭제는 채택하지 않음 — 런타임 접근을 막지 못하고 재현성을 죽인다. 파트 배정보다 GATE 봉인 순서가 더 결정적§17
측정 계층과 시뮬레이터의 구축 순서측정 계층 먼저. 스키마·KPI·경제 규칙이 시뮬레이터의 목표가 된다. 단 “측정되지 않는 행동을 만들지 않는다”이지 “예측 불가능한 잡음을 없앤다”가 아니다 — 잡음 제거는 Risk 2(비현실적으로 쉬운 모델)로 직결§7 · §15

16.4 유보

항목판단
Multi-treatment Uplift (T1·T2·T4 동시 비교)MVP 범위 밖으로 유지. PRD §15.1이 Binary Treatment(T0 vs T3) 우선을 명시했고, 처치가 늘면 각 팔의 표본이 쪼개져 Qini 신뢰구간이 넓어진다. Binary에서 Incremental Profit을 증명한 뒤 확장한다.
Propensity Score Matching 배정사용하지 않는다. 시뮬레이터에서는 완전 무작위 배정이 가능하므로 PSM은 불필요한 편향 위험만 추가한다. PRD §29가 허용한 두 방식 중 Random Assignment를 택한다.
Redis Feature Store보류. CPU 단일 노드 환경에서 File-based(Parquet)로 충분하며, 운영 복잡도만 늘어난다(PRD §37 [PROJECT-DECISION]과 동일 결론).
실시간 스코어링범위 밖. 캠페인은 각 T0에서 배치로 집행되고 시뮬레이터 시간도 advance() 단위로 진행되므로 배치 스코어링으로 충분하다.

17. 파트 격리 아키텍처

지금까지의 Leakage 규칙(§11)은 무엇을 보면 안 되는지를 정했다. 이 절은 그것을 코드 구조로 강제하는 방법을 정한다.

Simulator는 고객 행동의 정답을 만들어내고, Decision은 그 행동 기록만 보고 정답을 맞혀야 한다. 시험으로 치면 출제자와 수험생이다. 수험생이 답안지를 보면 점수는 높지만 실력은 0이다.
가장 위험한 누수는 파일 접근이 아니다. AI 성능이 낮다는 이유로 시뮬레이터를 고치는 것이 진짜 위험이다(PRD §80 Risk 1). 파일을 아무리 숨겨도 사람 머릿속에는 결과가 남아 있고, 코딩 에이전트는 도움을 주려다 “이탈 감쇠 파라미터를 조정할까요”라고 제안한다. 그래서 선의에 기대지 않고 구조와 검사로 막는다.

③ 들키게 한다

17.4 데이터 경로 경계 (ISO-003)

경로내용접근 가능
data/raw/ · data/processed/고객 행동 기록 · Feature전체
data/hidden/Hidden Trait 15종simulator · diagnostics
data/ground_truth/Potential Outcome · 참 CATEdiagnostics 전용
results/모델 성능 · 전략 결과decision · orchestration — simulator는 읽지 않는다
.gitignore와 삭제를 격리 수단으로 쓰지 않는다.
  • .gitignore는 런타임 접근을 막지 못한다. 저장소에 안 들어갈 뿐 로컬에는 파일이 그대로 있고, read_parquet("data/hidden/…")은 그냥 성공한다. 어겨도 아무 일이 일어나지 않으므로 방어선이 아니다.
  • 삭제는 재현성을 죽인다. Hidden Trait이 없으면 같은 seed로 재현할 수 없고(NFR-001 · SIM-011), Ground-truth가 없으면 §4.4의 PEHE·Qinioracle 진단이 사라진다.
  • 민감 산출물은 생성물이므로 data/ 전체를 ignore하면 저장소에는 자연히 들어가지 않는다. 별도 규칙이 필요 없다.

봉인 후에는

  • 한 사람이 양쪽을 다 담당해도 이 순서만 지키면 결과는 유효하다.

  • 수정이 불가피하면 simulator_version을 올리고 Baseline부터 전부 재실행한다.

현실적 기대치

  • 소규모 팀에서 완전한 격리는 불가능하다. 그것이 정상이다.
  • 목표는 누수 0이 아니라 누수가 드러나게 하는 것이다.
  • 리포트에 simulator_commit · data_version · config 해시를 남기면 사후에 누구든 검증할 수 있다.
  • 학술 실험도 같은 방식으로 운영한다.
파일 격리보다 중요한 것: 시뮬레이터를 전혀 건드리지 않아도, Test 성능을 보며 하이퍼파라미터를 반복 조정하면 그 자체가 과적합이다. §10.2 Final Holdout이 이 문서에서 가장 강한 방어선인 이유다.
