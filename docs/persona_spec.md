## 1. 쉬운 개요

### 1.1 3층 구조

가상 고객은 세 층으로 만든다(`docs/data_spec.html` §3, PRD §17~§21).

```
① Persona        "어떤 부류의 고객인가"            — 6종 중 하나 (S2)
      │  페르소나마다 Trait 분포의 중심이 다르다
      ▼
② Hidden Trait   "그 고객 고유의 성향 수치 16개"     — 쿠폰 민감도, 이탈 성향 … (S2)
      │  행동 규칙이 Trait 을 읽어 확률을 정한다
      ▼
③ 관측 행동       방문·장바구니·구매·쿠폰 사용 이벤트  — 측정 계약 형식 (S1 골격, S4 가 Trait 과 연결)
```

- ①과 ②는 **실제 서비스에서는 절대 알 수 없는 값**이다. 실제 커머스는 고객의 "쿠폰 민감도 0.73"을 모른다. 행동 기록(③)만 남는다.
- 같은 페르소나 안에서도 Trait 은 고객마다 다르다(분포에서 뽑는다). 페르소나를 맞혀도 Trait 을 맞히지는 못한다(4.2절 겹침).

### 1.2 왜 숨기나

이 저장소는 **출제자(시뮬레이터)** 와 **수험생(의사결정 시스템)** 으로 나뉜다(`src/AGENTS.md`).

- 시뮬레이터는 정답을 안다. Trait 이 곧 정답의 재료다. 예를 들어 처치 효과 τ 는 `coupon_sensitivity` 와 `marketing_fatigue` 로 계산된다(S6).
- 수험생이 Trait 을 보면 점수는 100점이지만 실력은 0점이다. 그래서 Trait 은 측정 계약(`src/measurement/schema.py` `FORBIDDEN_FIELD_NAMES`)을 통과하지 않고, 이벤트에 실리지 않고, `data/hidden/` 밖으로 나가지 않는다.
- 반대 방향의 누수도 막는다. **AI 성능을 보고 Trait 분포를 고치면 안 된다**(PRD §80 Risk 1). 8절 변경 절차를 따른다.

### 1.3 S2 의 범위 (사용자 확정 U1~U5)

| # | 결정 |
|---|---|
| U1 | **생성·저장만.** `engine.py`·`behavior.py` 는 그대로다. Trait → 행동 연결은 S4, P6 중도 가입 일정은 S3 가 맡는다. S2 에서는 전원 Day 0 에 가입한다 |
| U2 | config 는 `config/simulator_config.yaml`, **내용은 JSON 문법**. 표준 `json` 으로 읽어 의존성 없는 Python 3.10 에서도 돈다. PyYAML 이 있으면 `yaml.safe_load == json.loads` 를 테스트로 대조한다 |

### 2.1 표

- **상태에는 id(CFG-001 키)를 저장한다.** `P1` 같은 두 글자는 격리 테스트의 지문 검색에서 우연히 일치하기 쉬워서 쓰지 않는다. 별칭 P1~P6 은 문서용이다.
- `ratio_bp` 는 1/10000 단위다. 합은 정확히 10000 이어야 하고 로더가 검사한다(이슈 완료 조건 "구성비 합 1.0" 을 부동소수 없이 정확히 검사한다).
- **구성비에는 외부 근거가 없다.** `docs/data_spec.html` §3.2 초안 값이다. 국내 온라인 식료품의 행동 세그먼트 비중은 공개 자료를 찾지 못했다. 근거 대신 민감도 표가 `DR-S2-persona-mix` 「민감도」에 있다.

### 2.2 왜 6종인가 (리뷰 질문 "5종이면 무엇이 안 되나?")

1. **요구사항이다.** SRS SIM-001·PRD §17 이 6종을 MUST 로 정했다. 5종은 요구사항 위반이다.
2. **5종이면 실제로 무언가가 사라진다.** 결합 방식(4.2절)에서 Trait 사이의 상관과 꼬리는 **전부 페르소나 혼합에서만 나온다.** 한 페르소나를 빼면 그 성분이 만들던 꼬리가 없어진다.

| 뺀 페르소나 | 가장 크게 사라지는 것 (해석해, `DR-S2-persona-mix`) |
|---|---|
| P1 VIP | 객단가 꼬리 — P(`base_order_value` > 10만 원) 3.94% → 2.26% |
| P2 일반 충성 | 기준 질량 — 빠지면 모든 꼬리가 부푼다 |
| P3 가격민감 | 쿠폰·가격 동반 민감 — Persuadable 후보 질량 33.8% → 15.8% |
| P4 탐색형 | 장바구니 이탈 꼬리 — P(`cart_abandonment_propensity` > 0.6) 17.3% → 6.6% |
| P5 이탈진행 | Sleeping Dog 후보 — P(`marketing_fatigue` > 0.6) 6.18% → 0.70% |
| P6 신규가입 | Trait 꼬리가 아니라 **시간**(이력 길이). S3 의 중도 가입에서 드러난다 |

배송민감·프로모션피로는 **페르소나가 아니다.** PRD §19 대로 Trait 상위 분위로 표현한다(`shipping_fee_sensitivity > 0.7`, `marketing_fatigue > 0.6`).

### 2.3 배정과 가입

- **배정은 고객별 독립 가중 추첨이다.** `Stream(seed, customer_id, "persona", -1).weighted(ratio_bp…)`, config 배열 순서가 곧 추첨 순서다.
  - 열쇠에 `num_customers`·`profile` 이 없다. 그래서 15명 세계는 16명 세계의 앞 15명과 같다.
  - 실현 구성비는 선언값에서 표본 오차만큼 벗어난다(n=26,000 에서 P2 표준편차 27.5 bp). 구성비 자체의 불확실성(±20% 면 P2 ±540 bp)보다 훨씬 작다. S3 는 층(페르소나 × recency) 안에서 정확한 1:1 로 나누므로 처치·통제 균형에는 영향이 없다.
  - 비중을 바꾸면 누적 경계를 넘는 고객만 페르소나가 바뀌고, 그 고객의 Trait 분위는 그대로다(짝지은 민감도 분석의 전제).
- **가입은 S2 에서 전원 Day 0(`calendar_start`)이다.** P6 의 Day 1~272 가입 일정(data_spec §3.2)은 S3 가 이벤트 변경·판 상향과 함께 맡는다.

| 1 | `base_visit_frequency` | 같음 | 기준 방문 빈도(회/주) | Gamma k=4 | 밀리회/주 (`milli_per_week`) — 1.4회/주 = 1400 | S4 방문 `p_visit` (data_spec `:261`) |
| 2 | `base_purchase_probability` | 같음 | 방문당 기준 구매확률 | Beta κ=12 | ppm (0 … 1,000,000) | S4 구매 (`:273`) |

| 4 | `purchase_cycle` | 같음 | 기준 구매 간격 | LogNormal σ=0.45 | 밀리일 (`milli_day`) — 6일 = 6000 | S4 `cycle_factor` (`:277`) |

| 16 | `review_propensity` | 같음 | 리뷰 작성 성향 | Beta κ=12 | ppm | S4 (`:290`) |

- **왜 `base_order_value` 인가.** `average_order_value` 는 관측 가능한 측정 KPI 이름이다(`src/measurement/kpi.py`, PRD §21). 숨은 값이 같은 이름을 쓰면 사람의 읽기와 격리 지문 검사 모두에서 관측값과 섞인다.
- **정수만 저장한다.** 시뮬레이터는 결과에 들어가는 값에 float 을 쓰지 않는다(`DR-S1-rng`). S4 는 [0,1] Trait 을 `Stream.bernoulli(값, 1_000_000)` 로 바로 쓸 수 있다.
- **분포족을 고른 이유.** 고객 간 이질성을 Gamma(빈도)와 Beta(확률)로 두는 것은 NBD·베타-이항·Pareto/NBD·BG/NBD 계열이 60년 동안 써 온 표준 부품이다. **분포족은 근거가 있고, 모수 값은 근거가 없다**(`DR-S2-hidden-trait-dist` 「조사한 것」).
- **Uniform 이 아닌 이유.** Uniform 이면 P(`marketing_fatigue` > 0.6) 이 40% 가 되어 Sleeping Dog 가드레일(8~15%)과 양립할 수 없고, 누가 Persuadable 인지가 페르소나와 무관한 동전 던지기가 된다.

| `review_propensity` | beta | kappa_milli 12000 | ppm | 300000 | 200000 | 150000 | 200000 | 100000 | 250000 |

**읽는 법.**

| 분포 | 모양 모수 | 페르소나 칸 | 뜻 |
|---|---|---|---|
| `beta` | `kappa_milli 12000` = κ 12 | `mu_ppm` — 420000 = 평균 0.42 | Beta(α = μκ, β = (1−μ)κ). 분산 μ(1−μ)/(κ+1) |
| `lognormal` | `sigma_ppm 450000` = σ 0.45 | `median` — 정수 단위의 중앙값 | X = 중앙값 · e^(σZ), Z ~ N(0,1). 평균 = 중앙값 · e^(σ²/2) |
| `gamma` | `shape_milli 4000` = k 4 | `mean` — 정수 단위의 평균 | Gamma(형상 k, 평균 = 칸 값). 변동계수 1/√k = 0.5 |

- κ 는 Trait 마다 칸이 있다(지금은 전부 12). 표적 민감도 분석을 하려는 칸이지 값을 바꾸려는 칸이 아니다.
- 로더는 수치 엔진이 정확도를 검증한 범위만 받는다: Beta α·β ∈ [0.3, 100], κ ∈ [1, 100], σ ∈ (0, 1], Gamma k ∈ [1, 100], LogNormal 중앙값·Gamma 평균 ∈ [1,000, 10¹²] 정수 단위. 지금 가장 작은 값은 P1 `base_churn_propensity` 의 α = 0.04 × 12 = 0.48, P5 방문 빈도 평균 1,400 이다.
  - 중앙값·평균 하한 1,000 은 정수 1 단위가 척도의 0.1% 이하가 되게 한다(DR 해상도 근거). 그보다 작은 척도는 값이 몇 개 정수로 뭉개지는데도 반올림 띠가 오차를 흡수해 정확도 관문이 잡지 못한다.
  - **퍼짐 하한 100 단위.** 척도 하한만으로는 σ·k 가 작을 때 분포가 몇 개 정수로 뭉개지는 것을 막지 못한다(σ = 1 ppm 이면 전원이 중앙값 한 값인데 관문은 통과한다). 해상도는 척도가 아니라 퍼짐 대비로 정해지므로 LogNormal 은 σ·중앙값, Gamma 는 평균/√k(표준편차)가 100 단위 이상이어야 한다. 정수 1 단위가 표준편차의 1% 이하라 ±3 표준편차 안에 서로 다른 값이 수백 개 남는다. 지금 config 의 최솟값은 LogNormal 2,700(`purchase_cycle` P1 = 0.45 × 6,000), Gamma 700(P5 방문 = 1,400 / 2)이다. Gamma 는 지금 범위(k ≤ 100, 평균 ≥ 1,000)에서 늘 성립하고, 범위를 넓힐 때를 대비한 검사다.
  - **이 범위는 GATE 1 전 조정 공간을 좁힌다.** 예: κ=12 에서 Beta μ 는 0.025 아래로 내릴 수 없다(α ≥ 0.3). S5 가 이탈률을 맞추다 이 벽에 닿으면 정확도 테스트로 새 모양을 먼저 검증하고 범위를 넓힌다.

### 4.2 결합과 겹침 (J2)

- **페르소나를 먼저 뽑고, Trait 마다 그 페르소나의 분포에서 독립으로 한 번씩 뽑는다.** 페르소나 안에서 Trait 사이 상관은 0 이다.
- 그래서 모집단에서 보이는 Trait 상관은 **전부 페르소나 혼합에서 나온다.** 예: corr(coupon, price) = +0.65, corr(coupon, brand_loyalty) = −0.52, corr(fatigue, churn) = +0.38 (해석해, `DR-S2-hidden-trait-dist`).
- **페르소나를 완벽히 맞혀도 Trait 을 맞히지 못한다.** 페르소나가 설명하는 분산 비율 η² 는 `coupon_sensitivity` 0.68, `cs_contact_propensity` 0.19 ~ `brand_loyalty` 0.75 다. 쿠폰 민감도 분산의 32% 는 개인차로 남는다. 페르소나 자체도 관측되지 않는다.
- 페르소나 안 상관(copula)은 근거 없는 모수 120개가 필요해 두지 않았다. S4·S6 의 실현 분포가 필요하다고 보여 주면 다시 연다.

## 5. 표집·재현성·저장·config 결속

### 5.1 표집 — 정수 역CDF 매듭표 (`DR-S2-trait-sampling` S-B)

```
페르소나   p = Stream(seed, customer_id, "persona", -1).weighted([ratio_bp …])
Trait t    u = Stream(seed, customer_id, "trait:" + t, -1).next_u64()      # 64비트 한 번, 거부 표집 없음
           i = u >> 52                          # 셀 번호 0 … 4095
           f = u & (2⁵² − 1)                    # 셀 안 위치
           값 = Q[p,t][i] + ((Q[p,t][i+1] − Q[p,t][i]) · f + 2⁵¹) >> 52   # 셀 안 보간 뒤 반올림
```

- **매듭표 Q** 는 (Trait, 페르소나)마다 정수 4097 개다. 안쪽 매듭은 Q[i] = round(F⁻¹(i/4096)), 양끝 매듭은 끝 셀 안 선형 보간의 평균이 실제 조건부 평균과 같게 고른다: Q[0] = max(하한, 2·E[X | X ≤ Q[1]] − Q[1]), Q[4096] = 2·E[X | X ≥ Q[4095]] − Q[4095] (Beta 는 1,000,000 이하로 자른다).
- **매듭표는 로드 시 config 에서 만든다.** config 가 유일한 원천이다 — μ 하나를 바꾸면 표가 자동으로 다시 만들어진다. config 다이제스트로 프로세스 안에 캐시한다. 같은 모양은 Trait 사이에서도 한 번만 푼다(지금 고유 Beta 모양 22개 + 정규 1 + Gamma 1).
- **수치는 정수 고정소수점(2⁶⁴ 척도)이다** (`fixedpoint.py`). ln·exp·lgamma·불완전 감마·불완전 베타(연분수)를 정수로 구현했다. 판·플랫폼마다 달라질 수 있는 libm 을 쓰지 않는다.
- **구현 세부.** 4095 개를 모두 Newton–Halley 로 풀면 시간 예산을 넘긴다. 양 꼬리 64개씩과 가운데 16칸마다(표당 375개)만 정확히 풀고, 그 사이는 분위함수의 1·2차 도함수(Q′ = 1/f, Q″ = −(ln f)′·Q′², 초월함수 없이 유리식)를 쓴 5차 Hermite 로 채운다. 반올림 전 고정소수점 매듭의 오차 |F(x_i) − i/4096| 는 config 모양에서 Beta 4.98×10⁻⁹ · 정규 4.28×10⁻⁹ · Gamma(4) 5.17×10⁻⁹ 가 최대다(부록 A 첫 줄, 관문 10⁻⁶).
- **반올림.** DR 공식은 셀 안 보간값을 내림(`>> 52`)했다. 사용자 결정(2026-10-11)으로 반올림(`+ 2⁵¹`)으로 바꿨다. 내림이면 값이 평균 최대 0.5 단위 아래로 치우친다. 반올림 뒤 뽑힌 정수의 정확한 기댓값과 참 평균의 차이는 Trait 별 최대 0.91 단위(상대 2.3×10⁻⁵ 이하)로, 매듭표 꼬리 처리와 보간에서 오는 크기다(부록 A 정밀도 표).
- **u 에 단조다.** 같은 고객은 모수를 바꿔도 같은 분위에 머문다. μ 를 올리면 같은 고객의 값은 줄지 않는다(테스트로 확인). 페르소나가 바뀐 고객도 Trait 분위는 그대로다.
- **α < 1 인 칸**은 P1 `base_churn_propensity`(α=0.48) 하나다. P1 안에서 **0.330%** 가 0 ppm 으로 저장된다(매듭표에서 정확히 계산한 값, 참조 P(X < 0.5 ppm) = 0.341%, DR 의 0.34% 와 같은 크기). 분포 그대로가 맞으므로 1 로 올려 잡지 않는다. S4·S5 가 이 값을 `bernoulli(0, …)` 로 쓰면 그 고객(26,000명 중 약 7명)은 그 사건이 결정적으로 일어나지 않는다.

### 5.3 저장

상태 JSON 의 고객 항목에 두 필드가 생긴다. 상태 파일은 `data/hidden/simulator/states/` 아래에만 있다(구조 예시이며 값은 자리표시자다).

```json
{
  "generation": {"config_version": "sim-gen-v1", "config_digest": "<생성 부분 sha256>"},
  "customers": [
    {
      "customer_id": "C00000001",
      "persona": "<페르소나 id>",
      "hidden_traits": {"base_order_value": "<정수 원>", "coupon_sensitivity": "<정수 ppm>", "…": "…"},
      "…": "S1 필드(cart · session · rfm · assignments …)"
    }
  ]
}
```

- 상태를 읽을 때(`decode`) 검사하는 것: 페르소나가 config 에 있는 id 인가, Trait 이름 집합이 config 와 정확히 같은가, 값이 정수(bool 제외)이고 **그 페르소나 매듭표의 [Q[0], Q[4096]] 안**인가. Trait 을 다시 생성하지 않는다 — `advance` 마다 도는 검사라서다.
- **범위 안의 위조는 계보가 잡는다.** 이어받을 계보의 첫 상태는 같은 seed 로 새로 만든 세계의 다이제스트여야 한다.
- **공개 오류 메시지 정책 — 이름도 값도 싣지 않는다.** 공개 예외(`StateFormatError`·`SimulatorError` 등) 메시지에는 숨은 필드의 이름(`persona`·`hidden_traits`·Trait 16종), 페르소나 id, Trait 값을 싣지 않는다. 위치는 고객 순번과 Trait 번호(3절 `#`)로 가리킨다(예: `customers[0]: Trait #1 값이 그 페르소나가 낼 수 있는 범위 밖이다`). config 오류의 자세한 사유(키·모수·페르소나 id)는 원인 예외(`__cause__`)에만 둔다. `tests/test_isolation.py` 가 대표 오류 경로 15개의 메시지를 같은 지문으로 검사한다.
  - **원인 예외는 예외다.** `__cause__` 의 config 오류 문구에는 Trait 이름·페르소나 id·모수 값이 들어가고, 호출자가 트레이스백을 로그로 남기면 함께 찍힌다. 이 경로를 막을지(`raise … from None` + 숨김 영역 기록)는 시스템 팀 읽기 경계에 대한 리드 결정을 기다린다(7절).
- `hidden_traits.parquet` 표 산출물(data_spec §15.1)은 **만들지 않는다.** 읽는 쪽이 생기는 S6·S8 이 상태에서 유도한다.
- 크기: 26,000명 상태 파일이 6.47 MB → 19.18 MB 로 는다(고객당 +489 B, 부록 B).

## 6. 후속 태스크 인계

### S3 (#77) — 규모·배정

- **P6 가입 일정.** data_spec §3.2 의 P6 Day 1~272 균등 가입은 S3 몫이다. 이벤트가 바뀌므로 `SIMULATOR_VERSION` 을 올리고 골든을 새로 고정한다. Trait 열쇠에 가입일이 없으므로 가입일을 바꿔도 Trait 은 그대로다.
- 층 = 페르소나(6) × recency(4). 페르소나 배정이 고객별 독립이라 실현 구성비가 ±수십 bp 흔들린다. 층 안 1:1 분할이면 영향이 없다.

### S4 (#78) — 행동 규칙

- **Trait → 행동 연결.** 3절 "읽을 태스크" 열의 data_spec 식들이 Trait 을 읽는다. [0,1] Trait 은 `bernoulli(값, 1_000_000)` 로 쓴다.
- **S2 당시 소비처가 없던 Trait 3종(지금은 셋 다 소비처가 있다)** — `brand_loyalty`, `marketing_responsiveness`(S6 와 함께), `repurchase_propensity`. 당시 지시는 "쓸 곳을 정하거나 '쓰지 않는다'고 DR 에 적는다. 그러지 않으면 GATE 1 에 죽은 값으로 봉인된다"였다. 현재 소비처:
  - `brand_loyalty` — 재주문 비중(엔진 별칭 `loyalty`, `DR-143-sim-sprint`).
  - `marketing_responsiveness` — 처치 반응 민감도의 절반(별칭 `responsiveness`, `treatment.py`).
  - `repurchase_propensity` — T4 처치 민감도(`behavior.arms.T4.sensitivity`), #183 부터 관측 중 가입 고객의 첫 구매 뒤 재구매 게이트(`DR-183-purchase-calibration`).
- **`repurchase_propensity` × `base_churn_propensity` 이중 계산.** 둘 다 그대로 쓰면 이탈을 두 번 센다(Pareto/NBD 는 시간 기반, BG/NBD 는 거래 기반 — 문헌은 둘 중 하나를 고른다). 합성 규칙이나 한쪽만 쓰는 이유를 S4 DR 에 적는다.
  - #183: 재구매 게이트는 생애 첫 구매라는 사건에 한 번만 걸리고, 그 뒤 이탈은 `base_churn_propensity` 의 시간 기반 hazard 만 쓴다 — 같은 이탈을 두 번 세지 않는다(`DR-183-purchase-calibration`).
- 실현 구매 빈도·객단가를 국내 자릿수(컬리 이용자 월 2.5회, 44,800원 — 오픈서베이 2023)와 다시 대조한다. 생성 모수만으로는 월 2.53회(상한)·45,889원이다.
- `BEHAVIOR_BASELINE` 항목을 지운다(행동이 바뀌므로).

### S5 (#79) — 이탈

- `base_churn_propensity` 가 감쇠 진입과 λ 를 정한다(data_spec `:268-270`). 생성 이탈률 15~25%(SIM-005)가 이 분포와 P5 비중(1500 bp)에 걸린다. 범위를 벗어나면 GATE 1 전에 이 분포·비중을 다시 연다 — 근거는 가드레일뿐이다.

### S6 (#80) — 처치 반응

- **Sleeping Dog 상한 신호.** data_spec τ 식에서 τ < 0 이려면 `marketing_fatigue > 0.6` 이어야 한다. 그 질량이 **6.18%(해석해) · 6.13%(n=26,000 표본)** 로 가드레일 하한 8% 보다 낮다. 실제 Sleeping Dog 는 Y(0)=1 까지 요구해 더 작다.
  - S2 에서 고치지 않은 이유: 가드레일은 Eligible 모집단의 실현값에 대한 것이고, 손잡이가 여럿이다(P5 fatigue μ, κ, 임계 0.6, P5 비중). data_spec 이 지목한 `τ_base` 는 양 성분 계수라 이 상한을 올리지 못한다.
  - 가장 민감한 손잡이는 fatigue μ 다(±20% 에 2.16~11.92%). 조정이 필요하면 GATE 1 전에 `DR-S2-hidden-trait-dist`·`DR-S2-persona-mix` 를 번복하고 **근거로 가드레일만 적는다.**
- Persuadable 후보 질량 P(coupon > 0.6, fatigue ≤ 0.6) = 33.81%(해석해) · 33.72%(표본). 4분면 목표 Persuadables 는 **11~21%** 다(2026-10-22 교정, 사용자 확정 — `docs/research/data_grounding.md` §3-2. PRD 원문 20~30% 에서 내림. 근거: `docs/decisions/DR-143-sim-sprint.md`).
- `hidden_traits.parquet`(data_spec §15.1)가 필요하면 상태 JSON 에서 유도하는 파생물로 만든다(원천을 둘로 만들지 않는다).

## 7. 알려진 한계

- **구성비·모수에 외부 근거가 없다.** 분포족만 문헌 근거가 있다. 국내 온라인 식품 커머스의 고객 단위 이질성 추정치가 공개되면 해소된다.
- **정밀도는 두 가지로 나눠 잰다**(`tests/test_simulator_trait_distribution.py`, 사용자 결정 2026-10-11 — 단위는 그대로 둔다).
  - **(a) 매듭표 오차 — 저장 단위 양자화를 뺀다. 관문이다.** 매듭값 |F(Q[i]) − i/K| ≤ 10⁻⁶(±0.5 단위 반올림 띠를 뺀 초과분), 정수 매듭 사이 연속 보간값 y 에 대해 sup dist(u, [F(y−0.5), F(y+0.5)]) ≤ 10⁻⁴. 실측 최대는 2.75×10⁻⁹ · 4.05×10⁻⁵ 다.
  - **(b) 저장 단위 해상도 포함 오차 — 관문이 아니라 회귀 상한이다.** 실제로 뽑히는 정수 v 로 sup dist(u, [F(v−0.5), F(v+0.5)]) 를 잰다. 매듭 반올림(±0.5)과 추첨 반올림(±0.5)이 겹쳐, 단위가 거친 Trait 은 원리상 10⁻⁴ 를 보장할 수 없다. 실측은 `base_visit_frequency`(밀리회)·P1 `base_churn_propensity`(0 근처 ppm) 1.22×10⁻⁴(= 셀 절반 0.5/4096), `purchase_cycle`(밀리일) 6.1×10⁻⁵, 나머지 4.05×10⁻⁵ 이하다. Trait 별 실측에 20% 여유를 둔 값을 `RESOLUTION_CEILINGS` 로 고정했다. 셀 폭이 16 단위 이하인 셀(양자화가 큰 곳)은 정수 수준마다 정확히 계산하고, 넓은 셀은 표본점으로 잰다.
  - DR 문구 "F(v ± 0.5 단위)로 감싼다"는 (a)·(b) 를 구분하지 않았다. 정수 매듭 + 정수 추첨 구조에서 ±0.5 띠의 10⁻⁴ 는 (b) 에서 원리상 달성할 수 없어 이렇게 나눴다. DR 보완 절에 기록할 항목이다.
- **꼬리 절단.** 매듭표 최댓값 위의 질량은 Trait 당 약 3.3×10⁻⁵ 다(n=26,000 에서 기대 0.86명).
- **격리 검사의 원리상 한계 — 이름 없이 숫자만 새는 누수는 잡지 못한다.** `tests/test_isolation.py` 는 Trait 사전 JSON, 페르소나 id(식별자 경계 — 따옴표 없이 `seg-<id>-v1`·`C00000001,<id>`·`segment=<id>` 로 붙어도 잡는다), Trait 이름과 생성 라벨을 출력 루트의 파일 내용·경로 이름, Sink 실행 기록, 공개 반환값, 대표 오류 메시지, 검사 프로세스의 stdout·stderr 에서 찾는다. stdout·stderr 를 UTF-8 로 읽을 수 없으면(대체 문자·NUL — 예: UTF-16 으로 쓴 id) 검사하지 못하므로 실패로 본다. 출력 루트의 파일은 최상위까지 모두 파싱되는 `.json`·풀리는 `.gz` 여야 한다. 그러나 `session_duration = 812345` 처럼 **Trait 값 하나가 이름 없이 숫자로만** 실리면 잡지 못한다. Trait 값은 평범한 정수라 이벤트의 수량·시간·금액과 구분할 수 없고, 값을 지문으로 쓰면 우연 일치로 거짓 실패가 난다. S4 이후에는 Trait 에서 관측값을 정당하게 만들기 시작해 구분이 더 어려워진다. 이 경로는 코드 리뷰가 맡는다(후속 이슈 후보: 고객별 값 일치 건수 상한 같은 통계적 검사).
- **격리 검사가 보지 않는 것.** 대문자·base64·순번·경계 없는 연결(`segmentvip_loyal`) 같은 부호화 누수, 출력 루트 밖 경로, 피검 코드가 탐침의 자기 보고를 위조하는 경우는 범위 밖이다(우발 누수 방어용 장치다). **페르소나 별칭(`P1`~`P6`)은 지문에 넣지 않는다**(사용자 결정 2026-10-11). 측정 코드의 정당한 문자열(`src/measurement/publish.py` 가 게시하는 분모 정의 `(P1)`, 지표 배지 `[P1]`, `economics.py` doctest 의 상품 id `"P1"`)과 겹쳐 거짓 실패 위험이 있기 때문이다. 상태에는 별칭이 아니라 id 를 저장하므로(2.1절) 별칭이 새는 경로는 config 를 읽어 바꿔 쓰는 코드뿐이고, 그 경로는 코드 리뷰가 맡는다.
- **원인 예외(`__cause__`)의 config 상세.** 공개 메시지는 고정 문구지만 `__cause__` 에는 Trait 이름·페르소나 id·모수 값이 남아 트레이스백 로그에 찍힐 수 있다. 시스템 팀 읽기 경계(리드 결정 대기)에 따라 막을지 정한다 — 지금은 사용자 결정으로 그대로 둔다.
- **성능.** 26,000명 상태가 6.47 MB → 19.18 MB 로 커졌고 `encode`·`decode` 가 약 2.5~3배다(부록 B). `advance` 1회에 약 +0.17 s(3.12) 가 붙어, S3 에서 365회 일 단위로 부르면 약 +60 s 다. S3 가 `advance` 안의 상태 재검증(`_Identity`)을 상태 적재 시점으로만 한정할지 검토한다.

   2. `config/simulator_config.yaml` 을 고치고 `config_version` 을 올린다.
   3. `tests/test_simulator_persona.py` 의 `CONFIG_PINS` 에 새 다이제스트를 **줄로 더한다. 기존 줄의 값은 고치지 않는다** — 같은 판 이름의 해시를 바꿔 쓰면 테스트가 통과해 버린다. 리뷰에서 `CONFIG_PINS` 기존 줄 diff 가 0 인지 확인한다.

   5. 정확도 테스트(`tests/test_simulator_trait_distribution.py`)가 새 모양에서 통과하는지 본다. 로더의 검증 범위를 넓혀야 하면 정확도부터 확인한다. 관문 (b) 의 `RESOLUTION_CEILINGS` 는 `report` 로 다시 재서 고친다.
   6. 생성 골든(`GENERATION_GOLDEN`)과 상태 골든을 새로 고정한다. 옛 상태·계보는 거부된다 — 새로 생성한다.

3. **AUC·Qini·Incremental Profit 이야기가 나오면 멈추고 보고한다.** "성능이 낮으니 쿠폰 민감도 분포를 넓히자" 같은 제안을 하지 않는다. 이 문서의 어떤 값도 AI 성능 지표를 근거로 정하지 않았다.
