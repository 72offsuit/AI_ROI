## 무엇을 정하는가

시뮬레이터 주문의 품목·주문 시점 원가·할인·배송비를 측정 계층에 **어떤 형식으로** 넘기나. 시뮬레이터의 **상품 카탈로그는 어디서** 오나. 시뮬레이터가 배송비를 매길 때 **무료배송을 무엇으로 판정**하나. 이 결정으로 바뀌는 **정본 문구를 언제** 고치나.

## 정하지 않으면 무엇이 막히나

`purchase` 는 주문 단위 1행이라 품목·원가가 없고, 측정 계층이 품목을 받는 길은 커머스 교환 파일(#100)뿐이었다. 그래서 시뮬레이터 분할의 `cogs`·`contribution_profit` 이 **계산 불가**였다. 실험 판정은 시뮬레이터 생성분만 쓰므로(`MEA-002`) **증분이익·AI ROI 가 계산될 길이 없었다.** `S4`(#78)가 구매 이벤트를 만들기 전에 정하지 않으면 생성 형식을 다시 만들어야 한다.

## 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| ① 교환 계약 v1 재사용 | 시뮬레이터가 같은 형식의 묶음을 `data/simulator_exchange/` 에 낸다 | 로더·`DQ-02/03/05/09`·COGS 배선이 그대로 선다. 두 출처가 한 계약 — "커머스와 같은 환경" 전제와 맞는다 | 로더를 출처별 묶음으로 넓혀야 한다 |
| ② 시뮬레이터 전용 계약 | 새 형식·경로 | 시뮬레이터에 맞춤 | 같은 개념의 계약이 두 벌 — 갈라진다 |
| ③ 측정 계층이 원가율로 추정 | `order_amount × 원가율` | 가장 쉽다 | **금지**(EC-1) — 기여이익이 매출의 상수배가 되어 가드레일이 원리적으로 죽는다 |
| ④ `purchase` 에 품목 필드 | 이벤트 계약 변경 | 한 곳 | GATE 1 정본 변경 · SRS DATA-003 개정 |

카탈로그: ⓐ 정본 설정 `product_margin` 으로 생성 · ⓑ 커머스 카탈로그 스냅샷 고정 · ⓒ 시뮬레이터 팀이 정함.
무료배송: ㉮ 커머스 정책(할인 전 합계) · ㉯ 측정 계층 D-3 규칙(할인 후 금액).
정본 개정: ㉠ `S7` 봉인 때 함께 · ㉡ 지금 재봉인.

## 조사한 것

| 출처 | 무엇을 말하나 | 우리 맥락에 얼마나 맞나 |
|---|---|---|

| 봉인 기록 가정 `A-DISCOUNT` | "시뮬레이터는 처치를 배정하므로 유도가 정의상 정확하다" | 시뮬레이터가 할인액을 **처치 단가 그대로** 쓰면 관측값과 유도값이 같다 — 묶음이 생겨도 이 가정은 거짓이 되지 않는다 |
| `src/measurement/AGENTS.md` 판단 기준 | "실제 서비스에서 로그로 남을 수 있는 것만 통과한다" | 원가·가격·할인·배송비는 실제 커머스도 아는 값이라 측정 계층으로 흘러도 된다. Hidden Trait 과 다르다 |

## 결정

**① 교환 계약 v1 재사용 · ⓐ 정본 설정으로 생성 · ㉮ 커머스 정책 · ㉠ `S7` 봉인 때 정본 개정.**

```
시뮬레이터  →  data/simulator_exchange/  (manifest.source = "simulator")
커머스      →  data/commerce/            (manifest.source = "Ecommerce_Service")
측정 계층   →  출처마다 자기 묶음을 읽고, 그 출처의 이벤트에만 붙인다
              다른 출처 자리에 놓인 묶음은 거부한다
```

구현: `exchange.ExchangeBundle`(출처 필드) · `read_exchange(root, source)` · `default_roots()` · `publish` 가 출처별로 KPI 를 자기 묶음으로 계산하고 품질 검사에 (묶음, 같은 출처 이벤트) 쌍을 넘긴다 · CLI `--simulator-exchange`. 시뮬레이터가 지킬 규칙은 계약 README §11.

**근거:** 같은 개념에 계약을 두 벌 두면 갈라진다 — ① 이 이미 선 배선을 그대로 쓴다. 카탈로그는 이 용도로 봉인된 설정이 있고 원가율이 커머스와 같으므로 ⓐ 가 재봉인 없이 일관된다. 무료배송은 "커머스와 같은 환경" 원칙대로 커머스 정책을 따르고, 시뮬레이터가 실제 배송비를 묶음에 실으므로 측정 계층의 D-3 은 묶음 없는 주문의 대체 규칙으로만 남는다. 정본 문구는 시뮬레이터 묶음이 실제로 생기기 전까지 사실과 어긋나지 않고, `S7` 이 어차피 사람 서명으로 재봉인하므로 그때 한 번에 고친다.

## 기각한 안과 기각 사유

| 안 | 왜 택하지 않았나 |
|---|---|
| ② 전용 계약 | 로더·검사·COGS 배선을 한 벌 더 만들고, 두 계약이 서로 다른 속도로 바뀐다 |
| ③ 원가율 추정 | EC-1 금지. 가드레일 `revenue_up_profit_down` 이 발동할 수 없게 된다 |
| ④ 이벤트에 품목 | GATE 1 정본과 SRS 를 바꾸는 비용에 비해 얻는 것이 없다 — ① 이 같은 것을 비이벤트로 준다 |
| ⓑ 커머스 카탈로그 고정 | 설정의 풀 240·중앙가격이 읽는 곳 없는 값이 되어 정본 개정·재봉인이 필요하다. 원가율은 이미 같다 |
| ⓒ 시뮬레이터 팀에 위임 | 카탈로그는 경제 규칙(봉인 대상)과 맞물린다. 팀 결정으로 두면 봉인된 설정과 다른 원천을 고를 수 있다 |
| ㉯ D-3 규칙 | 커머스와 다른 배송 정책이 된다. 같은 주문이 출처에 따라 다른 배송보조를 낸다 |
| ㉡ 지금 재봉인 | 시뮬레이터 묶음이 아직 없어 지금 문구가 틀리지 않다. 서명을 두 번 할 이유가 없다 |

## 이 결정이 틀렸다면 어떻게 드러나나

- 시뮬레이터 분할의 COGS 가 **다른 출처의 품목으로** 계산되면 짝짓기가 새고 있다 — `tests/test_exchange_sources.py` 가 같은 `order_id` 충돌 장면으로 막는다
- 시뮬레이터 묶음의 할인액이 처치 단가와 다르면 `A-DISCOUNT` 가 거짓이 된다 — `S6`·`S7` 이 봉인 전에 실측한다
- 시뮬레이터 카탈로그의 카테고리별 원가율이 설정과 다르면 ⓐ 를 지키지 않은 것이다 — `S4` 의 증거로 남긴다
- `S7` 봉인 기록에 아래 "남은 불확실성"의 정본 문장이 그대로 들어가면 ㉠ 을 놓친 것이다

## 민감도

카탈로그 ⓐ·ⓑ 는 원가율이 같아 기여이익률 수준에서는 차이가 작다. 차이는 상품 수(240 vs 41)와 가격 분포에서 나오며, 객단가·장바구니 크기에 영향을 준다 — 이것은 `S4` 의 행동 규칙이 정한다. 무료배송 ㉮·㉯ 는 할인 전 합계가 40,000원 근처인 쿠폰 주문에서만 갈리고, 그 주문의 배송보조 3,000원 차이다.

## 남은 불확실성

**`S7` 봉인 전에 고칠 정본 문장** (시뮬레이터 묶음이 생기면 커머스만 전제한 서술이 부정확해진다):

- `docs/measurement_contract.md` — §1 `purchase` 절("커머스 교환 파일이 싣는다"), §4("둘 다 커머스 교환 파일로 온다"), §6 판정 주석("커머스 교환 파일이 실제 값을 싣게 되어"), §6.3 표("시뮬레이터 생성분 — 규칙 유도가 정확하다")
- `config/economic_config.yaml` — `A-DISCOUNT` 주석("커머스 교환 파일에 실제 할인액이 있는 주문은")
- `src/measurement/freeze.py`(봉인 기록에 옮겨지는 가정) — `A-DISCOUNT`·`A-SHIPPING` 의 "커머스 교환 파일" 서술

묶음 생성 시점·주기(창마다 전량인가)는 `S1`·`S4` 가 정한다.
