# DR-108-coupon-cost-basis — 쿠폰 비용은 주문마다 실제 할인액을 먼저 쓴다

|---|---|

| 상태 | 확정 (사용자 결정 2026-09-28) |

## 무엇을 정하는가

ROI 분모(`marketing_cost`)에 들어가는 쿠폰 비용(`coupon_cost`)의 근거를 무엇으로 하는가. 그리고 커머스의 운영 쿠폰(AI 처치가 아닌 캠페인 쿠폰) 할인을 AI_ROI 의 마케팅 비용으로 보는가.

## 정하지 않으면 무엇이 막히나

`coupon_cost` 는 처치 단가에서만 유도했다(D-16: `Σ treatment_cost[t] for t in (처치 ∩ {T2, T3})`). 커머스 주문에는 처치 ID 가 없어 유도가 아무것도 세지 못하고 **0 원이 `ok` 로 게시됐다.** 실제 커머스 표본(`tests/fixtures/commerce_exchange_v1/`)에서:

```
실제 할인 합계 (교환 파일 orders.discount)   6,910
coupon_cost                                    0   status=ok  derived=true
marketing_cost                           300,000   (캠페인 고정비만)
```

커머스 ROI 분모가 조용히 작아지고 ROI 가 과대로 나온다. 기여이익은 순매출 기준이라 영향이 없고(DR-101), 실험 판정은 시뮬레이터 생성분만 쓰므로 영향이 없다(MEA-002).

## 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| ① 관측값 우선 + 근거 없으면 계산 불가 | 교환 파일 `discount` 가 있으면 그 값, 없으면 D-16, 둘 다 없는데 쿠폰을 썼으면 `unavailable` | 실제 할인을 쓰고 0 원 게시를 막는다. `shipping_subsidy` 가 #100 에서 택한 방식과 같다 | 정본(`economic_config.yaml` · `measurement_contract.md` §6.3)이 D-16 을 유일한 규칙으로 적은 것과 어긋난다 → 재봉인 필요(#109) |
| ② 관측값 우선, 근거 없으면 현행 | ①과 같되 둘 다 없으면 0 원 | 교환 파일이 있으면 맞는 값 | 교환 파일 없이 돌리면 0 원 게시가 그대로 남는다 |
| ③ 유도만, 근거 없으면 계산 불가 | 실제 할인을 쓰지 않고 처치 ID 없는 쿠폰 사용 주문이 있으면 `unavailable` | 정본 규칙을 바꾸지 않는다 | 교환 파일이 실제 할인을 싣는데도 커머스 ROI 분모를 영영 계산하지 못한다 |

## 조사한 것

| 출처 | 무엇을 말하나 | 우리 맥락에 얼마나 맞나 |
|---|---|---|
| `src/measurement/economics.py` `coupon_cost()` (수정 전) | 처치 ID ∩ `coupon_treatments` 가 비면 아무것도 더하지 않고 `ok` 를 낸다 | 결함의 위치. 설정에 없는 처치는 `PRECONDITION_MISSING` 으로 막으면서, 처치가 **아예 없는** 경우는 막지 않았다 |
| `Ecommerce_Service` `event-tracking.ts` `recordPurchase` | `coupon_use`·`purchase` 에 `treatment_id` 를 싣지 않는다. 쿠폰 스냅샷은 할인이 0 보다 클 때만 저장한다 | 커머스에서 `coupon_use` 가 있으면 실제 할인이 있다는 뜻이다 |
| `Ecommerce_Service` `marketing_cost_entries` · `economics:report` | 시드 쿠폰마다 캠페인 고정비 100,000 원을 기록하고, 기여이익에서 할인을 비용으로 뺀다 | 커머스는 운영 쿠폰을 마케팅 지출로 본다 |
| AI_ROI `campaign_fixed_cost()` (현행) | 이벤트의 `campaign_id` 수로 고정비를 센다 — 커머스 운영 캠페인 3건의 300,000 원이 이미 분모에 있다 | 고정비는 넣고 할인은 빼면 같은 캠페인의 지출을 반만 센다 |
| `tests/fixtures/commerce_exchange_v1/` | 쿠폰 주문 2건, 할인 합계 6,910 원(커머스 `couponDiscountKrw` 와 같다) | 실제 산출물이므로 결정의 효과를 숫자로 확인할 수 있다 |

## 결정

**① 관측값 우선 + 근거 없으면 계산 불가.** 그리고 **커머스 운영 쿠폰 할인은 마케팅 비용이다.**

```
coupon_use 가 있는 주문마다:
  교환 파일 discount 가 있다        → 그 값                      (관측)
  쿠폰 처치(T2·T3)가 적용됐다       → Σ treatment_cost[t]        (D-16 유도)
  둘 다 없다                        → coupon_cost 계산 불가 (MISSING_FIELD, blocked_by discount)
유도가 하나라도 섞이면 derived: true
```

**근거:** 0 원을 `ok` 로 내는 경로는 이 저장소가 막아 온 모양(0 채우기) 그대로다. 실제 할인이 있으면 그것이 유도보다 정확하고, 판정 기준을 출처가 아니라 **값이 있는가**로 두면 `economics.py` 가 출처를 모른다는 설계(EC-2)를 지킨다. 커머스 운영 캠페인의 고정비를 이미 분모에 넣고 있으므로 같은 캠페인의 할인도 넣는 것이 일관된다.

## 기각한 안과 기각 사유

| 안 | 왜 택하지 않았나 |
|---|---|
| ② 근거 없으면 현행(0 원) | 교환 파일 없이 돌리면 #108 이 그대로 남는다. 결함을 절반만 고친다 |
| ③ 유도만 | 교환 파일(#100)이 실제 할인을 싣게 된 뒤에도 쓰지 않는 것은 "읽는 곳 없는 필드"를 만드는 것과 같다. 커머스 ROI 분모가 영구히 계산 불가가 된다 |
| 운영 쿠폰을 마케팅 비용에서 뺀다 | 그러면 같은 캠페인의 고정비도 빼야 일관되고, 커머스 `economics:report` 와 분모 구성이 달라진다. 범위가 커지는데 얻는 것이 없다 |
| 교환 파일 없는 주문의 할인을 `order_amount` 로 역산 | 이벤트에는 할인 전 금액이 없다(#106 이후 `order_amount` 는 할인 후). 역산할 재료가 없다 |

## 이 결정이 틀렸다면 어떻게 드러나나

- 같은 주문 묶음에서 AI_ROI `coupon_cost` 와 커머스 `economics:report` 의 `couponDiscountKrw` 가 **다르면** 근거 선택이 어긋난 것이다 — `tests/test_coupon_cost.py` 가 실제 표본으로 대조한다
- 시뮬레이터 주문(처치 ID 있음, 교환 파일 없음)의 `coupon_cost` 가 바뀌면 이 결정이 범위를 넘은 것이다 — 같은 파일이 막는다
- 쿠폰을 쓴 주문이 있는데 `coupon_cost` 가 `0 · ok` 로 나오면 #108 이 되살아난 것이다

## 민감도

실제 표본에서 쿠폰 비용이 0 → 6,910 원이 되고 `marketing_cost` 는 300,000 → 306,910 원(+2.3%)이 된다. 이 표본은 캠페인 고정비가 지배적이라 영향이 작지만, 쿠폰 주문이 많아질수록 차이는 할인 총액만큼 선형으로 커진다. 처치 단가(T2 3,000 · T3 7,000)와 실제 할인(예 1,570)이 크게 다르므로, 관측값이 있는 주문에 유도값을 쓰면 오차가 주문마다 수천 원 단위다.

## 남은 불확실성

- **정본이 아직 D-16 을 유일한 규칙으로 적는다** (`config/economic_config.yaml` `discount_derived_from_treatment` · `docs/measurement_contract.md` §6.3 · `freeze.py` 가정 `A-DISCOUNT`). 고치려면 봉인 재기록(사람 서명)이 필요해 #109 에서 한 번에 한다
- 커머스가 한 주문에 여러 쿠폰을 쓰게 되면 주문 단위 `discount` 만으로는 캠페인별 귀속을 할 수 없다. 오늘은 주문당 쿠폰 1장이다
- `coupon_cost` 는 캠페인을 가리지 않고 주문 전체를 합산한다(`CampaignView` 가 하나다). 캠페인별 ROI 가 필요해지면 따로 다룬다
