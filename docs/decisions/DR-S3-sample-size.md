# DR-S3-sample-size — 고객 수·기간을 검정력으로 정한다

## 무엇을 정하는가

`reference`·`small` 두 규모의 **생성 고객 수와 시뮬레이션 기간**, 그리고 그 규모로 **검출할 수 있는 최소 효과 크기(MDE)**를 정한다. 고객 수는 "SRS 하한이니까"가 아니라 T0 시점 Eligible 고객을 1:1 로 나눈 뒤 ATE 하한(3%p)을 검정력 0.8 로 잡을 수 있는가로 정한다.

## 정하지 않으면 무엇이 막히나

- `DR-S3-assignment` — 무엇을 몇 명 나눌지 모르면 배정 규칙과 SRM 기준을 정할 수 없다.
- S6(#80) — 처치 강도 가드레일(ATE 3~6%p)을 실측해 판정하려면 그 크기를 잡을 수 있는 군 크기가 먼저 있어야 한다. 군이 작으면 가드레일을 통과·실패로 가를 수 없다.
- S7(#81) — 규모가 GATE 1 봉인 대상(`CUSTOMER_PERSONA_v1` 의 모집단)에 들어간다.
- 성능 측정 — `advance` 시간·상태 크기(persona_spec §7)는 규모에 비례한다. 규모 없이 잴 수 없다.

| data_spec §3.1 | 26,000명 → Eligible ≈ 78% ≈ 20,400 → 군당 ≈ 10,200 | 78% 는 **행동 규칙이 없을 때의 설계 추정**이다. 실측은 S4(구매)·S5(이탈)가 생긴 뒤에야 가능하다 |
| data_spec §2.2 | 프로파일 smoke·short·reference·long·rolling, warmup > 180일, label 42일 고정 | `src/simulator/_internal/profiles.py` 에 이름 5개는 있지만 **기간 값은 아직 없다** — S3 가 채운다 |
| data_spec §4.2 · §16.4 | 처치는 이진(T3 vs T0), 다중 처치는 MVP 밖 | 팔이 2개뿐이라 표본을 나누지 않는다. 다중 처치를 넣으면 이 계산을 다시 한다 |
| 두 비율 비교 표본 크기 공식 (정규근사, Fleiss·Levin·Paik *Statistical Methods for Rates and Proportions* 3판 4장) | n = (z₁₋α/₂·√(2p̄q̄) + z₁₋β·√(p₀q₀+p₁q₁))² / d² | 결과변수가 42일 유지 여부(이진)라 그대로 맞는다. 군당 수천 명이라 정규근사 오차는 무시할 수준이다 |
| 층화 배정의 분산 (Imbens & Rubin 2015 *Causal Inference* 9장) | 층 안 완전 무작위 + 층별 분석이면 분산이 단순 무작위 이하 | 아래 계산은 **층을 무시한 검정** 기준이라 보수적이다 — 층화가 검정력을 낮추지 않는다 |

**검정력 계산** — 결과변수 Y = Label Window 42일 유지(1) / 이탈(0). 통제군 유지율 p₀ = 1 − 이탈률, ATE d = p₁ − p₀. 양측 α = 0.05, 검정력 0.8, 1:1. 재현: `statistics.NormalDist` 로 계산했다(정수 결과 경로가 아니므로 float 사용 무방).

- **SRS 하한(군당 10K)은 ATE 3%p 를 잡는 데 필요한 양의 약 2.5~5배다.** 하한은 ATE 검출에는 충분하다. 왜 10K 인지는 SRS 에 근거가 적혀 있지 않다 — 검정력 외 용도(D4 하위집단·Qini 신뢰구간 등 시스템 팀 몫)로 짐작되지만 **확인하지 못했다.**

## 이 결정이 틀렸다면 어떻게 드러나나

- **`reference` 실측에서 Eligible 군이 한쪽이라도 10,000명 미만** → SIM-004 위반. 필요 고객 수 = 20,000 / 실측 Eligible 비율 로 다시 계산해 번복한다. 이 검사는 S4(구매 이벤트)가 생겨야 돌 수 있으므로 **그때까지 `BLOCKED`** 다(Eligible 조건이 구매 이력을 요구한다).
- **실측 Eligible 이탈률이 35% 를 넘음** → 위 MDE 표 밖이다. 다시 계산한다(10K 에서도 MDE 는 2%p 안팎이라 결론이 바뀔 가능성은 낮다).
- **`small` 1회가 "몇 분" 안에 끝나지 않음** → 이슈 완료 조건 위반. 고객 수가 아니라 성능(persona_spec §7)부터 고친다.

## 남은 불확실성

- **Eligible 비율 78%** — data_spec 의 설계 추정이다. P6 가입 일정(이 태스크)과 S4 구매 규칙이 생겨야 실측된다.
- **Eligible 이탈률** — S5 전에는 근거가 없다. 위 표가 15~35% 를 덮는 이유다.
- **SRS 가 군당 10K 를 정한 이유** — 문서에 근거가 없다. ATE 검출에는 과하다. 하위집단 분석용이라면 그 요구는 시스템 팀 쪽에 있고, 시뮬레이터 팀은 그 문서를 읽지 않는다 — 리드에게 묻는다.
- **이벤트 총량** — 640일 × 26,000명의 이벤트 수와 상태 크기·실행 시간은 S4 규칙이 나와야 안다. 성능 실측은 `DR-S3-assignment` 와 별개로 S3 구현 단계에서 기록한다.

## 구현 전 실측 (2026-10-22, 사용자 결정 P4)

규모를 정한 뒤 구현에 들어가기 전에 잰 값이다. **행동은 S1 의 검증용 최소 규칙(구매 없음)** 이라 이벤트·시간은 하한이다. S4 뒤에 다시 잰다.

환경: macOS arm64 · Python 3.12.0 · `sim-0.2`(main `fa698d2`) · seed 42 · profile `reference` · 출력·숨김 루트는 저장소 밖.

| | 5,000명 | 26,000명 |
|---|---:|---:|
| `init` | 0.47 s | 1.35 s |
| `advance` 1회 고정비 (≈ 첫 `advance(1)`) | ≈ 0.16 s | ≈ 0.70 s |
| 하루 진행 비용 (`advance(10)` 1회에서 고정비를 뺀 값 / 9) | ≈ 0.12 s | ≈ 0.71 s |
| 하루 이벤트 | ≈ 4,900 | ≈ 25,000 |
| 숨김 상태 + 계보 (10일 뒤) | 4.9 MB | 25.5 MB |
| 최대 RSS | 258 MB | 679 MB |

- **추정 (한 번에 `advance`)**: `small` 5,000명 × 275일 ≈ 33 s — 이슈 "몇 분 안" 충족. `reference` 26,000명 × 640일 ≈ 7.6 분, 이벤트 ≈ 1,600만 건, 출력 ≈ 0.9 GB.
- **`advance` 를 잘게 부르면 호출마다 느려진다.** 26,000명에서 `advance(1)` 10회가 1.41 → 1.90 s(호출당 ≈ +0.054 s). 640일을 하루씩 부르면 ≈ 3.3 시간. 원인은 확정하지 못했다 — PR #120 「남은 위험」 M6(계보 재해시) 또는 상태 증가. 사용자 결정 P3 로 Issue #139 에 기록하고 S3 에서 고치지 않는다.
- **고정비의 절반 이상이 상태 전체 재검증**(`world._validate`)이다. 그 안에서 `session_id` 정규식을 고객마다 문자열로 만들어 re 캐시(512)를 넘겨 매번 컴파일했다 → **고정 패턴으로 바꿨다**(사용자 결정 P1, 결과 불변 — 이벤트 수·골든 동일). 수정 후 26,000명 첫 `advance(1)` 1.33 s, 10회 증가 폭 1.33 → 1.66 s.
- **검증을 적재 시점으로만 줄이는 것**(persona_spec §7)은 안전 검사를 빼는 결정이라 S4 뒤 실측으로 다시 판단한다(사용자 결정 P2).
- 측정 스크립트는 저장소에 넣지 않았다. 같은 측정은 `api.init` → `advance(1)` × 10 → `save_state` → `events(until=끝)` 와 별도 세계의 `advance(10)` 1회로 재현한다.
