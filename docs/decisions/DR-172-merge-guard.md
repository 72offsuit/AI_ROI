## 무엇을 정하는가

두 가지다.

1. 브랜치 보호를 켤 수 없는 저장소에서 **"전 체크 통과 + 승인 1건" 을 무엇으로 강제하는가**, 그리고 그 강제가 무엇을 통과로 치는가(SKIPPED · 진행 중 · 오래된 승인).
2. git worktree 에서 `Plan` 서브모듈 gitdir 이 깨져 `tests/test_team_boundaries.py` 가 BLOCKED 되는 문제를 **어느 층에서 고치는가** — 테스트 · 저장소 설정 · 작업 절차.

## 정하지 않으면 무엇이 막히나

- 병합: `#141` 이 `Tests (with deps)` FAILURE 상태로 병합됐다. 같은 사고를 막는 장치가 없으면 Sprint 3 의 GATE 1·2 봉인 PR 도 같은 길로 나갈 수 있다 — 봉인 해시 대조가 실패한 채 병합되면 FREEZE-003 재실행 범위를 판단할 근거가 사라진다.
- worktree: 팀 경계 검사가 skip 으로 빠지면 **한 브랜치가 두 팀 경로를 건드려도 초록**이다. 에이전트마다 `GIT_CONFIG_* … submodule.Plan.ignore=all` 을 붙여 돌렸고, 그것을 잊은 실행은 아무것도 대조하지 않았다.

**승인 판정**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| R1 | `reviewDecision == APPROVED` | 간단 | 보호 규칙이 없으면 **늘 빈 문자열**이다 — 영원히 막힌다 |
| R2 | `reviews` 에서 리뷰어별 마지막 판정(APPROVED · CHANGES_REQUESTED · DISMISSED)을 센다 | GitHub 의 판정 규칙과 같고 보호 없이도 계산된다 | 직접 구현해야 한다 |
| R3 | R2 + 승인 커밋 ≠ head 면 막는다 | 리뷰 뒤 커밋까지 강제 | 리뷰 반영 커밋마다 재승인이 필요하다 |

**worktree**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| W1 | 테스트의 `git status` 에 `--ignore-submodules=dirty` | 어떤 worktree 상태에서도 경계 검사가 돈다 | `git status` 를 직접 치는 사람의 문제는 남는다 |
| W2 | `.gitmodules` 에 `ignore = all` | 모든 체크아웃에서 증상이 사라진다 | `Plan` 포인터 변경까지 `git status` 에서 숨긴다 |
| W3 | 문서화된 worktree 절차(복사 금지 · 필요하면 worktree 안에서 `git submodule update --init`) | 원인 자체를 피한다 | 절차를 안 읽으면 그대로 깨진다 |
| W4 | `GIT_CONFIG_*` 우회를 공식화 | 지금 하던 그대로 | 잊으면 BLOCKED 로 조용히 빠지고, `ignore=all` 이 포인터까지 숨긴다 |

## 결정

**병합 — 안 C + R2.** `scripts/safe_merge.py` 가 아래를 전부 만족할 때만 `gh pr merge --squash --match-head-commit` 을 실행한다.

- PR 이 OPEN 이고 초안이 아니다
- `.github/workflows/*.yml` 중 `pull_request` 로 도는 워크플로우의 잡이 **전부 보고**됐다(아직 안 뜬 체크는 통과가 아니다)
- 보고된 체크가 **전부 `SUCCESS`** — `SKIPPED` · `NEUTRAL` · `CANCELLED` · 진행 중은 통과가 아니다
- 작성자가 아닌 리뷰어의 마지막 판정 중 `APPROVED` 1건 이상, `CHANGES_REQUESTED` 0건
- `CONFLICTING` 이 아니다

우회 옵션은 두지 않는다(`test_options_are_exactly_repo_and_dry_run`). 승인 커밋 ≠ head 는 막지 않고 `[주의]` 로 알린다.

리뷰 R1~R4(PR #238) 반영:

- **필수 목록에서 빼는 사유는 `pull_request` 이벤트 자신의 `paths` · `paths-ignore` 필터뿐이다.** `push.paths` 같은 다른 이벤트의 필터는 보지 않는다. 기존 제외 정책(PR 경로 필터가 있으면 PR 마다 돈다는 보장이 없으니 필수에서 뺀다)은 유지한다. 뺀 워크플로우는 `excluded_workflows()` 가 사유와 함께 내고 `[주의]` 로 출력한다. `tests/test_safe_merge.py` 는 지금 저장소의 제외 목록이 비어 있음을 고정한다. 그래서 제외가 생기면 테스트가 실패하고, 사람이 이 DR 과 함께 본다. 개수 검사도 같은 정책을 따른다(필수 ∪ 제외 = PR 워크플로우 전부).
- **필수 Actions 잡은 정확한 `(workflow, job)` 쌍으로만 충족된다.** 잡 이름만 같은 다른 워크플로우의 체크나 StatusContext 는 대신하지 못한다. 외부 상태는 ③(보고된 것 전부 `SUCCESS`)으로 따로 본다.
  - **그 쌍을 내는 잡은 하나여야 한다(체크 이름 중복).** 이 스크립트가 받는 보고(`gh pr view --json statusCheckRollup`)에는 잡 ID 가 없어 같은 쌍을 내는 잡이 둘이면 한 잡의 보고가 다른 잡의 미보고를 가린다. 그래서 잡 `name`(없으면 잡 ID)까지 적용한 최종 `(workflow, check name)` 이 필수 쌍과 같은 잡이 **모든 워크플로우 파일을 통틀어** 둘 이상이면 `WorkflowError` 로 막고, 메시지에 그 쌍과 잡(파일 · 잡 ID)을 적는다. 경로 필터로 필수에서 뺀 워크플로우와 `pull_request` 가 아닌 워크플로우의 잡도 센다 — 그 잡도 같은 head 에 보고될 수 있다. 그래서 잡은 트리거와 무관하게 모든 파일에서 읽는다 — 잡 자리의 줄을 못 읽거나 잡을 하나도 읽지 못하면(4칸 들여쓴 잡 등) 그 파일이 PR 워크플로우가 아니어도 `WorkflowError` 다. 비교는 보고 대조와 같이 정확한 문자열이다 — 대소문자만 다른 이름은 서로 다른 체크로 보고되므로 막지 않는다. 필수가 아닌 쌍끼리 겹치는 것은 판정에 쓰이지 않으므로 막지 않는다.
  - **이름은 정해진 문법으로만 읽는다(이름 해석).** 겹침 판정은 이름을 정확히 읽어야 성립한다. 그래서 필수 여부와 관계없이 모든 워크플로우에 같은 문법을 쓴다.
    - **받는 값**: 워크플로우 · 잡 `name:` 의 한 줄 평범한 스칼라 · 작은따옴표 · 이스케이프 없는 큰따옴표, 끝 주석.
    - **막는 값**(`WorkflowError`): 빈 값 · null, 앵커 · 별칭 · 태그 · 블록 스칼라(`|` · `>`) · 흐름 · 예약 표시, 큰따옴표 이스케이프(`\u0020` 등 — 어디서든), `${{ }}` 식(실행 때 정해진다), 따옴표 없이 쓴 숫자 · 참거짓 · null · 날짜 모양, 다음 줄로 이어지는 값, 대소문자가 다른 `name` 키.
    - **위치**: 워크플로우 `name` 은 파일 어디에 있든(`jobs:` 뒤도) 읽는다.
    - **공백은 스페이스 · 탭뿐이다**(YAML 1.2.2 §5.5). 줄 · 키 · 주석 · 값을 다듬을 때 파이썬의 인자 없는 `strip()` · 정규식 `\s` 를 쓰지 않는다 — 유니코드 공백(U+00A0 · U+3000 등 16자)을 벗겨, 주석이 아닌 줄을 주석으로 · 다른 키를 `name` 으로 · 다른 이름을 같은 이름으로 읽었다(적대 검증, 아래 조사 행).
    - **파일 수준**: 워크플로우 파일은 이름 끝(`.yml` · `.yaml`, 대소문자 무관)으로 고른다 — `.YML` 도, 점으로만 된 이름(`.yml` · `..yml`)도 읽는다. `Path.suffix` 는 맨 앞 점을 확장자로 보지 않고 그 규칙이 파이썬 판(3.12 · 3.14)마다 달라, 같은 가드가 실행 판에 따라 다른 파일을 읽었다. 대소문자만 다른 이벤트 이름(`Pull_Request`)은 PR 여부를 정할 수 없어 막는다. 맨 앞 BOM 은 벗기고, UTF-8 이 아니면 `WorkflowError` 다. `\n` · `\r` 이 아닌 줄바꿈 후보(U+0085 · U+2028 · U+2029 등)가 든 파일은 막는다 — 파서마다 줄로 나누는지가 다르다. 첫 내용 줄은 0열이어야 한다(들여쓴 최상위 매핑은 막는다).
    - **GitHub 의 이름 규칙**: 이름 없는 워크플로우는 GitHub 처럼 저장소 루트 기준 파일 경로(예: `.github/workflows/x.yml`)를 이름으로 쓴다. 잡 ID 는 GitHub 규칙(문자나 `_` 로 시작, 영숫자 · `-` · `_`)만 받는다 — 이름 없는 잡은 ID 가 체크 이름이다. matrix(`strategy`) · 재사용 워크플로우 호출(`uses`) 잡은 보고 이름이 `이름 (값, …)` · `호출 / 피호출` 로 바뀌어 막는다. 그런 잡을 넣을 때 가드를 함께 고친다.
    - **잡 본문**: 칸은 첫 내용 줄이 정한다(4칸 고정이 아니다). 그 칸의 줄은 전부 속성 키이거나, 값이 빈 키 바로 아래의 같은 칸 목록 항목이어야 한다. 읽지 못한 키(이스케이프 · 복합 키 `?` · 병합 키 `<<`) · 겹친 속성 키 · 잡 자리와 본문 칸 사이의 줄 · 본문 없는 잡은 막는다. 키를 놓친 채 잡 ID 로 조용히 대체하지 않기 위해서다.
- **필수 목록이 비었거나 만들지 못하면 막는다.** 워크플로우 파일 없음 · PR 워크플로우에서 잡을 못 읽음 · 인라인 매핑 `on: {…}` 같이 읽지 않는 형태는 `WorkflowError` 로 종료 2, 빈 목록은 판정에서 막힘(종료 1)이다. 둘 다 `gh pr merge` 를 부르지 않는다.
- **목록 전체가 아니라 일부만 잃어도 막는다(R4 · N1 · P3 · 중복 키).** 읽는 표기를 정해 두고 그 밖의 줄은 `WorkflowError` 다. 읽는 것: `on:` 한 줄 값(이벤트 하나 · 한 줄 `[…]` 목록), 블록 목록 `- 이벤트`, 블록 매핑 `이벤트:`, 그리고 잡 자리(`jobs:` 아래 2칸)의 `잡ID:`. 키와 목록 항목은 따옴표(`"…"` · `'…'`)와 끝 주석을 허용한다. 읽지 않는 것: 인라인 매핑 `{…}`, 여러 줄 `[…]`, `jobs:` 뒤에 놓인 `on:`, 복합 키 `?`, 병합 키 `<<`, 값이 붙은 잡 줄, 2칸이 아닌 잡 자리 들여쓰기, 겹친 키(아래). 이런 줄을 "PR 워크플로우가 아니다" · "잡이 아니다" 로 넘기면 그만큼 필수 목록이 사유 없이 줄기 때문이다.
  - **블록의 끝도 확인한다(N1).** `on:` · `jobs:` 블록은 다음 0열 줄에서 끝나는데, 그 줄이 최상위 키(`키:`)가 아니면 끝을 확인하지 못한 것이라 `WorkflowError` 다. 그리고 파일 어디에 있든 **여러 줄에 걸친 따옴표 스칼라 · 흐름 컬렉션(`[…]` · `{…}`)은 여는 줄에서 막는다** — 들여쓰기가 맞아 YAML 로 유효한 것도 막는다. 연속 줄이 0열이면 `B: "2"}` 처럼 최상위 키 모양이 될 수 있어서, 끝 줄 검사만으로는 막지 못하기 때문이다.
  - 따옴표 · 괄호는 토큰 자리에 있을 때만 표시로 본다. 토큰 자리는 줄 처음, `- ` · `? ` · `: ` 뒤, 흐름 안의 `[` · `{` · `,` 뒤, 앵커 · 태그 뒤다. 흐름 안에서는 **따옴표 · 괄호 바로 뒤의 공백 없는 `:`** 도 값 표시라 그 뒤가 토큰 자리다(P3 — `{"A":"…"}`). 평범한 스칼라 속 문자는 글자다(`${{ … }}` · `don't` · 흐름 안의 `a"b` · `a:b` · `a#b`). 평범한 스칼라는 `: ` · ` #` 에서, 흐름 안에서는 `,[]{}` 에서도 끝난다. 블록 스칼라(`키: |` · `- |`, `>` · chomping 표시 포함)의 내용은 검사하지 않는다 — 셸 코드의 `{` · `'` 가 열린 표기로 오인되면 정상 PR 이 막힌다.
  - **파서마다 토큰을 다르게 나누는 표기는 한 줄이어도 막는다(P3).** 흐름 안에서 YAML 1.2 와 PyYAML 의 판정이 갈리는 것 — 따옴표 · 괄호 뒤가 아닌 공백 없는 `:`, 공백 없는 `?`, 앵커 · 별칭 · 태그, `- ` 등 그 밖의 표시 문자 — 와, 토큰 자리에 공백 없이 붙은 `#`(`"a"#` · `[a,#` — PyYAML 만 주석으로 읽는다)다. 어느 쪽을 따라도 다른 쪽에서는 여러 줄 따옴표 · 흐름 표기가 열릴 수 있어 끝을 확인할 수 없다.
  - **겹친 키를 막는다(중복 키).** 최상위 키, `on:` 아래 이벤트 키, 잡 ID 가 두 번 나오면 `WorkflowError` 다. PyYAML 은 마지막 값을, 이 스크립트는 첫 블록을 읽어서 뒤 블록의 트리거 · 잡이 오류 없이 빠지기 때문이다. 비교는 따옴표를 벗긴 키를 대소문자 구분 없이 한다(`on` · `"on"` · `'on'` 은 같은 키, `jobs` · `JOBS` 도 같은 키). `true:` 는 `on:` 과 같은 키로 본다(`on:` 을 찾을 때와 같은 규칙). 끝 주석은 키에 들어가지 않는다. 겹침을 빠짐없이 보려고 **0열 줄은 전부 최상위 키여야 한다** — 맨 앞의 문서 시작 표시 `---` 하나만 예외이고, 두 번째 `---`(문서 여러 개) · 0열 복합 키 `?` 등은 막는다.
- **검사의 기대값은 파서와 따로 정한다(R4).** 지금 저장소의 필수 4종은 `tests/test_safe_merge.py` 의 `REQUIRED_TODAY` 에 직접 적었다. 의존성 설치 잡에서는 PyYAML(`BaseLoader`)로 따로 읽은 결과와 (워크플로우, 잡) 쌍까지 대조한다. 표기만 바꾼 사본(트리거 6가지 · 둘째 잡 키 4가지 · 0열 연속 줄 9가지 — N1 3 · P3 6 · 중복 키 3가지)은 "필수 체크를 전부 유지하거나 `WorkflowError`" 여야 한다. 그 체크가 미보고이면 실제 파서를 쓴 배선에서도 `gh pr merge` 호출이 0회다. 체크 이름 중복 사본 5가지(A~E)는 `WorkflowError` 여야 하고, 겹친 쌍이 SUCCESS 1건으로만 보고된 PR 은 배선에서 병합 호출이 0회다. 이름 표기 사본 17가지 × 트리거 2(= 34사례)도 같다. 의존성 설치 잡에서는 각 사본을 PyYAML 이 정말 같은 쌍으로 읽는지 먼저 확인한다.
- 필수 목록은 **스크립트가 놓인 체크아웃**의 정의에서 읽는다. 최신 `main` 에서 실행해 PR 이 자기 필수 목록을 줄이지 못하게 한다. 워크플로우 · 잡 이름을 바꾸는 PR 은 막히며, 그 처리(리뷰 승인 뒤 PR head 체크아웃에서 판정)는 `docs/GIT_WORKFLOW.md` §5.1 에 적는다.

**worktree — W1 + W3.** 경계 검사는 `git status --porcelain --ignore-submodules=dirty` 로 변경 목록을 얻고, `docs/GIT_WORKFLOW.md` §11 에 "복사하지 않는다 · 필요하면 worktree 안에서 `git submodule update --init`" 절차를 적는다.

**근거:** 병합 쪽은 서버 강제(A)가 불가능하므로 저장소에 남고 테스트할 수 있는 C 가 남는 안 중 가장 강하다. 판정 논리를 테스트로 묶어야 "스크립트가 있다" 가 "막는다" 와 같은 뜻이 된다. 승인은 R1 이 원리적으로 불가능해(조사 2행) R2 다. worktree 쪽은 원인이 복사된 gitfile 이라는 재현 결과에 따라, 검사는 어떤 상태에서도 돌게(W1) 하고 사람은 원인을 피하게(W3) 한다. `Plan/**` 은 어느 팀 소유도 아니므로 서브모듈 안을 보지 않아도 경계 판정은 바뀌지 않는다.

## 기각한 안과 기각 사유

| 안 | 왜 택하지 않았나 |
|---|---|
| A 브랜치 보호 | 플랜 제한으로 불가. 플랜이 바뀌면 이 결정을 번복하고 A 로 옮긴다 — 그때 스크립트는 남겨도 해가 없다 |
| B 개인 별칭 | 저장소에 남지 않아 다음 사람·다음 에이전트가 모른다. 판정 논리를 검사할 수 없다 |
| D 사후 감시 워크플로우 | 막지 못한다. 막는 장치(C)가 먼저고, 웹 버튼 병합까지 잡아야 할 사고가 다시 나면 그때 더한다 |
| R1 `reviewDecision` | 보호 규칙 없이는 계산되지 않는다 — 모든 PR 이 영원히 막힌다 |
| 겹친 필수 쌍을 `set(required)` 로 합치기 | 반례 A~C 를 그대로 통과시킨다 — 두 잡의 요구가 한 쌍으로 줄어 한 보고로 충족된다(리뷰 지적) |
| 이름의 이스케이프 · 블록 표기만 따로 거부 | 같은 원인의 다른 표기 — 키(이스케이프 · 복합 키) · 들여쓰기(6칸) · 이어짐(여러 줄 평범한 스칼라) · 앵커 · 별칭 · 태그 · `jobs` 뒤의 `name` — 가 남는다(리뷰 지적, 변이 검사로 확인) |
| YAML 을 정확히 해석해 이름을 읽기 | 표준 라이브러리만 쓰는 원칙(ISO-005)상 이스케이프 · 접기 · 앵커 해석기를 직접 구현해야 한다. 파서마다 갈리는 표기(1.1 · 1.2 타입 등)도 하나로 정해야 한다. 정해진 문법 밖을 막는 쪽이 단순하고, 틀릴 때 막는 쪽으로 틀린다 |
| 보고 개수로 서로 다른 잡을 세기 | `gh pr view` 가 주는 보고에 잡 ID · 이벤트가 없어, 개수가 서로 다른 잡의 수라는 근거가 없다. 같은 잡이 다른 이벤트(`workflow_dispatch` 등)로 같은 head 에 한 번 더 보고될 수도 있다 |
| 같은 파일의 명시적 `name` 끼리만 비교 · 필수 잡끼리만 비교 | 앞의 것은 B(ID 폴백) · C(다른 파일)를, 뒤의 것은 D · E(필수가 아닌 워크플로우의 잡)를 놓친다. 변이 검사로 확인했다 |
| R3 오래된 승인 차단 | 리뷰 반영 커밋마다 재승인이 필요해져 이번 스프린트 일정(광진 1인 리뷰)에 비해 비용이 크다. GitHub 기본값도 새 커밋이 승인을 무효화하지 않는다. 대신 `[주의]` 로 드러낸다 |
| W2 `.gitmodules` `ignore = all` | 모든 체크아웃에서 `Plan` 포인터 변경을 `git status` 에서 숨긴다 — "포인터를 커밋하지 않는다"(AGENTS.md) 를 사람이 확인하는 수단을 없앤다 |
| W4 `GIT_CONFIG_*` 우회 공식화 | 잊은 실행이 BLOCKED skip 으로 **조용히 초록**이 된다. 이 저장소가 계속 잡아 온 결함 모양이다 |
| 심볼릭 링크 `Plan → 본 체크아웃` | `T Plan` 이 변경으로 잡혀 `git add -A` 한 번에 포인터 자리에 링크가 커밋될 수 있다 |

## 이 결정이 틀렸다면 어떻게 드러나나

- 병합: 스크립트를 거쳐 병합된 PR 의 head 에 `SUCCESS` 가 아닌 체크가 있으면 틀린 것이다 — `gh pr view N --json statusCheckRollup` 으로 사후 확인할 수 있다. 반대로 정상 PR 이 계속 막히면(예: 워크플로우에 `if:` 조건 잡이 생겨 `SKIPPED` 가 정상이 되면) 판정이 너무 좁은 것이다.
- 스크립트를 거치지 않은 병합(웹 버튼)은 이 결정이 **막지 못한다.** 그런 병합이 생기면 안 C 의 한계가 드러난 것이고 D 를 더한다.
- worktree: `--ignore-submodules=dirty` 로도 rc≠0 인 서브모듈 상태가 나오면 W1 이 틀렸다 — 경계 검사가 다시 `BLOCKED` skip 사유를 내므로 skip 수에 드러난다. `TestBoundaryCheckSurvivesBrokenSubmoduleGitdir` 의 대조군이 git 버전 변화로 재현을 잃어도 그 테스트가 실패해 알린다.

## 민감도

- 필수 체크 목록은 숫자가 아니라 워크플로우 파일에서 매번 읽는다. 워크플로우가 하나 늘거나 줄어도 스크립트를 고칠 필요가 없다 — `paths` 필터 · `if:` 조건 잡이 생기는 경우만 판정 규칙을 다시 본다. 다만 테스트의 `REQUIRED_TODAY` 는 일부러 직접 적은 값이라 사람이 함께 고친다(R4).
- 승인 기준 1건을 2건으로 올리면 시스템 팀은 2인 팀이라 작성자 외 승인자가 1명뿐이다 — 병합이 불가능해진다. 1건은 팀 규모가 정한 값이다.

## 남은 불확실성

- 웹 UI 의 병합 버튼은 여전히 열려 있다. 사람의 규율(§5.1 "스크립트로만")에 맡긴다.
- worktree 쪽 검증은 범위가 셋으로 나뉜다. 실제 linked worktree 생성 · 복사 · 서브모듈 초기화는 작성자 로컬 재현(git 2.43) 1회다. CI 회귀 테스트 2건은 일반 임시 저장소에 끊긴 gitfile 을 둔 **등가 상태**다(리뷰 기록상 CI git 2.55.0). `--ignore-submodules=dirty` 는 검사 옵션이지 복구 명령이 아니다. CI 가 worktree 절차(W3)까지 검증한 것은 아니다 — `docs/GIT_WORKFLOW.md` §11 에 같은 구분을 적었다.
- `pull_request` 에 `branches` · `types` 필터가 있어 PR 에서 돌지 않는 워크플로우는 필수로 남아 **영원히 막힌다**. 막는 쪽으로 틀리지만, 그런 필터가 생기면 판정 규칙을 다시 본다.
- `required_checks()` 는 YAML 파서 없이(ISO-005) 이 저장소 워크플로우의 들여쓰기 모양만 읽는다. 위에 적은 표기 밖은 `WorkflowError` 로 막는다. 행렬(matrix) 잡이나 재사용 워크플로우가 들어오면 체크 이름이 달라져 "보고되지 않았다" 로 막힌다. 둘 다 막는 쪽으로 틀리므로 위험하지는 않지만, 그때 파서를 고친다.
- 워크플로우 · 잡 `name:` 은 정해진 문법만 읽고 그 밖은 `WorkflowError` 다(「결정」 이름 해석).
  - 예전에는 여기에 "이름이 틀리면 필수 쌍이 보고되지 않으니 병합되지 않는 쪽이다" 라고 적었다. 필수 워크플로우에는 맞지만, 필수에서 뺀 워크플로우의 겹침 판정에는 성립하지 않았다 — 이름을 잘못 읽으면 같은 쌍을 다른 쌍으로 세어 겹침을 놓친다(PR #238 리뷰 이름 해석). 그래서 같은 문법을 모든 워크플로우에 적용하고, 못 읽으면 막는다.
  - 타입 모양 판정은 YAML 1.1 · 1.2 의 null · 참거짓 · 숫자 · 날짜를 따른다. 한 글자 `y` · `n` 은 YAML 1.1 명세에만 참거짓이고 PyYAML · YAML 1.2 는 문자열로 읽어 넣지 않았다. GitHub Actions 가 어떤 파서로 이름을 읽는지는 확인하지 못했다.
  - 이름 문자열은 정규화하지 않는다(유니코드 NFC/NFD · 특수 공백을 그대로 비교한다). 보고 대조도 정확한 문자열이므로, 바이트가 다른 이름은 서로 다른 체크다. 다만 GitHub 이 이름 앞뒤의 유니코드 공백을 다듬는지는 문서에 없고 확인하지 못했다 — 다듬는다면 끝에 U+3000 이 붙은 따옴표 이름 `X` 와 붙지 않은 `X` 가 실제로는 같은 체크인데 가드는 다르게 본다.
  - 재사용 호출의 보고 형식은 GitHub 문서에 있다 — 문서는 재사용 워크플로우의 이름 형식을 '호출 잡 이름 / 재사용 잡 이름'(job name / reusable job name)으로 적는다(https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules). matrix 의 `이름 (값, …)` 은 관찰 기준이고 형식을 적은 문서는 찾지 못했다. 둘 다 정확히 읽지 않고 막는다.
  - 이 결정의 전제는 GitHub 문서도 권한다 — "make sure that job names are unique across all workflows. Using the same job name in multiple workflows can cause ambiguous status check results"(https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
  - 탭: 가드는 YAML 1.2 처럼 탭을 구분 공백으로 보고 들여쓰기는 스페이스만 센다. PyYAML 은 토큰 자리의 탭을 거부해 오라클로 판정하지 못했다(적대 검증의 '판정 불가'). libyaml 은 읽는다.
  - 대소문자를 가리지 않는 파일 시스템(macOS APFS 기본)에서는 `x.yml` 과 `x.YML` 이 한 파일로 체크아웃된다. git · GitHub 에서는 서로 다른 워크플로우라, 그런 체크아웃에서 가드는 하나만 읽는다(적대 검증 확인). 체크아웃 환경의 한계다.
  - 알려진 과잉 차단(막는 쪽으로 틀림): 따옴표 키 `"jobs":` · 콜론 앞 공백 `jobs :`(잡을 찾지 못함), `jobs:` 뒤의 `on:`, 문서 끝 `...` · 지시자 `%YAML`, 별칭 없는 잡 앵커 `a: &j`, 큰따옴표 이스케이프 · 작은따옴표 `''` 가 든 고유한 이름, 워크플로우 `name` 의 `${{ }}`(GitHub 은 최상위 `name` 의 식을 평가하지 않는다).
- 이 스크립트가 받는 보고(`gh pr view --json statusCheckRollup`)에는 잡 ID · 이벤트가 없다. 리뷰의 독립 검수는 GraphQL `checkSuite.workflowRun { event file { path } }` 로 이벤트 · 워크플로우 파일 경로를 조회할 수 있다고 보고했다(작성자 · 리뷰어 모두 재실행하지 않았다). 파일 경로 · 이벤트로 대조하면 이름 해석에 기대지 않고 잡을 구분할 수 있으므로 후속 개선 후보로 둔다.
- 여러 줄 표기 검사(N1 · P3)는 YAML 파서가 아니라 한 줄 단위의 토큰 판정이다. 기준은 YAML 1.2 명세와 PyYAML 6.0.3 의 스캐너이고, 둘이 갈리는 표기는 막는다. GitHub Actions 가 어떤 YAML 파서를 쓰는지는 확인하지 못했다 — 그 파서가 두 기준 모두와 다르게 토큰을 나누는 표기가 있다면 이 검사가 놓칠 수 있다. 무작위 차분은 PyYAML 하나와만 대조했다.
- 틀리는 쪽은 막는 쪽으로 정했다. 평범한 스칼라 속 `: ` 뒤의 따옴표(YAML 이 받아들이지 않는 줄)는 열린 표기로 보고, `_KEY_LINE` 으로 읽지 못하는 키(점이 든 키 등)에 붙은 블록 스칼라는 내용까지 검사해 막힐 수 있다. P3 이후로는 흐름 안의 공백 없는 `?` · 앵커 · 태그처럼 한 줄로 닫힌 유효한 표기도 막는다 — 같은 무작위 생성기의 한 줄 사례 22,512건 중 막히는 것이 23건 → 525건으로 늘었다(`?` 228 · `&` 145 · `!` 142 · `:` 10). 지금 워크플로우 4개에는 이런 줄이 없다(`REQUIRED_TODAY` 대조 통과).
- 중복 검사는 최상위 키 · `on:` 이벤트 키 · 잡 ID 만 본다. 잡 안의 키(`name:` 등)와 `pull_request:` 설정 안의 키가 겹치는 것은 보지 않는다. 잡 이름은 첫 값을 필수로 삼으므로 다른 이름이 보고되면 미보고로 막히는 쪽이다. 경로 필터 키는 어느 값을 읽어도 키가 있으면 제외라 결과가 같다. 대소문자를 구분하지 않는 비교는 리뷰가 확인한 공개 Actions 파서의 정규화를 따른 것이다. PyYAML 은 `jobs` 와 `JOBS` 를 다른 키로 읽으므로, 이 경우는 PyYAML 보다 엄하게 막는다.
- 체크 이름 중복 검사는 **서로 다른 잡**만 가린다. 같은 잡이 다른 이벤트로 같은 head 에 두 번 보고되는 것(예: PR 브랜치에서 `workflow_dispatch` 로 돌린 실행)은 구분하지 못한다 — 이 스크립트가 받는 보고에는 이벤트가 없다. 그런 실행이 PR 의 `statusCheckRollup` 에 따로 실리는지는 실제로 돌려 확인하지 않았다. 그 실행이 실패하면 ③이 막고, 성공이면 같은 잡 정의를 같은 head 에서 통과한 것이다(다만 `pull_request` 실행은 main 과의 병합 커밋을, `workflow_dispatch` 는 head 자체를 검사한다). 반대로 `push: branches: [main]` 처럼 PR head 에는 돌지 않는 워크플로우가 같은 쌍을 내도 막는다 — 막는 쪽으로 틀리며, 잡 이름을 고유하게 바꾸면 풀린다. 지금 워크플로우 4개의 쌍은 모두 고유하다(`REQUIRED_TODAY` 대조 통과).
- 표기 대조는 실제 Actions 실행이 아니라 사본 정의를 읽은 결과다. 어떤 GitHub 이벤트가 "필수 체크 미보고" 입력을 실제로 만드는지는 확인하지 않았다(리뷰 R4 의 검증 범위와 같다).
