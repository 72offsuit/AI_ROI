## 무엇을 정하는가

PRD NFR-04 는 `Python >= 3.10` 이고 SRS SYS-003 · 머리말(`Target Runtime: Python 3.10+`)도 같다. 그런데 의사결정 계층의 고정 의존성은 3.12 이상에서만 설치된다. 이 저장소가 **어느 판을 지원한다고 선언하고, 그 선언을 무엇으로 대조하는가**를 정한다.

## 정하지 않으면 무엇이 막히나

- Dockerfile 의 베이스 이미지를 고를 수 없다 — 지금 이 PR 의 초안과 다음 스프린트 compose(#231).
- README · TEAM_SETUP 이 "최소 3.10" 이라고 적으면, 3.10 으로 받은 사람은 `pip install -r requirements.txt` 단계에서 실패하고 이유를 모른다. 선언과 실제가 어긋난 상태다.
- `python-compat.yml`(3.10)이 무엇을 보증하는지 불분명해진다. 그 잡이 초록이면 "3.10 에서 다 된다" 로 읽히지만 실제로는 의존성 없이 도는 부분만 본다.

## 결정

**안 A.** `requirements.txt` 머리에 기계가 읽는 두 줄을 둔다.

```
# Supported runtime: Python 3.12          ← 전체 파이프라인 (Dockerfile · CI 전체 테스트)
# Measurement-layer floor: Python 3.10    ← 측정 계층 · 의존성 없는 스위트 (python-compat.yml)
```

- Dockerfile 은 `python:3.12.15-slim-trixie`(다이제스트 고정)다.
  - 빌드 컨텍스트에서 `.agent-team/_state/*.audit-key` · `*.lock` 을 뺀다 — `.gitignore` 와 같은 줄(PR #240 리뷰 R1). `.agent-team` 전체는 빼지 않는다: 이미지에 함께 들어가는 `tests/` 중 4개(`test_publish_contract` · `test_publish_pipeline` · `test_contract_enforcement` · `test_schema`)가 `.agent-team/04-architecture/` 의 스키마 · 예시를 읽는다. 런타임(대시보드 · 파이프라인 명령)은 쓰지 않는다. `tests/test_docker_context.py` 가 `.gitignore` 의 `_state` 줄이 `.dockerignore` 에 있는지 대조한다(Docker 매칭 자체는 위 합성 빌드로 1회 확인).
- README · TEAM_SETUP · AGENTS.md 에 "전체는 3.12, 3.10 은 측정 계층까지" 를 적는다.
- `docs/gate1_checklist.md` §5.1 의 실행 전 확인 명령도 `python3` 이 아니라 `python3.12` 로 적는다(#248). `python3` 이 가리키는 판은 기기마다 다르다 — `python3` 이 3.11 인 기기에서 ① 이 실패했다. `tests/test_runtime_declaration.py` 가 그 명령들을 `Supported runtime` 과 대조한다.
- `tests/test_runtime_declaration.py` 가 두 줄을 Dockerfile · CI 3종 · 설치된 패키지의 `Requires-Python` 과 대조한다. 선언 런타임이 "실제로 필요한 최소 판" 인지도 본다. 고정 의존성이 더 낮은 판을 허용하게 바뀌면 선언의 근거가 사라졌다고 실패한다.
  - `Requires-Python` 은 Dockerfile 의 **정확한 판**(3.12.15)으로 판정한다(PR #240 리뷰 R2). major.minor 하한 · 상한만 보던 이전 판정은 `>=3.12,!=3.12.*` · `~=3.10.0` · `>=3.12.16` 을 통과시켰다. 이제 절마다 PEP 440 의 정식 판 비교(크기 비교 4종 · `==` · `!=` · 와일드카드 `.*` · `~=`)로 보고, 하한은 실제로 만족하는 가장 낮은 판으로 찾는다(`>3.11` → 3.11). 그 밖의 절(`===` · 사전 배포판 · 환경 표지 등)은 **통과가 아니라 실패**다. 표준 파서(`packaging`)는 개발 의존성을 하나 늘리므로 택하지 않았다 — 지금 고정 9종의 조건은 전부 `>=X.Y` 다.

**근거:** NFR-04 는 문구상 하한이고 3.12 는 그 하한을 넘는다. 3.12 를 요구하는 것은 의사결정 계층 의존성 셋(조사 1행)뿐이다. 그 셋을 내리는 비용(조사 2행 — 메이저 하향과 결과 재생성)이 이미 지원이 끝난 판(조사 3행)을 지원하는 이득보다 크다. 3.10 잡을 유지하는 이유는 측정 계층 코드가 3.10 문법·표준 라이브러리로 깨지는 것(`#62` 의 `fromisoformat` 같은 것)을 계속 잡기 위해서다. 그 보증 범위를 이제 이름으로 적는다.

## 기각한 안과 기각 사유

| 안 | 왜 택하지 않았나 |
|---|---|
| B 고정 버전 하향 | pandas 3→2 메이저 하향이고 모델 수치가 바뀐다 — 스프린트 1 리포트와 MC 를 다시 만들어야 한다. 그렇게 얻는 것은 2026-10-01 에 지원이 끝난 3.10 이다. `src/decision/**` 는 같은 주에 다른 사람이 고치는 경로라 이 PR 에서 손댈 수도 없다 |
| C requirements 두 벌 | 판마다 라이브러리가 달라 결과가 두 벌이 된다. 한쪽은 아무 CI 도 돌리지 않아 조용히 썩는다 — 이 저장소가 계속 잡아 온 "대조되지 않는 선언" 모양이다 |
| D 모든 판 지원으로 해석 | 원문에 그렇게 읽을 근거가 없다(조사 4행). 그렇게 읽으면 결국 B 나 C 를 해야 한다 |
| 3.10 CI 잡 폐지 | 측정 계층의 3.10 호환은 실제로 깨졌던 적이 있고(`#62`) 그 잡이 잡았다. 보증 범위를 좁혀 적을 뿐 없애지 않는다 |

## 이 결정이 틀렸다면 어떻게 드러나나

- 평가자나 다른 기기 검증(#232)이 **3.10 · 3.11 에서 전체 파이프라인 실행**을 요구하면 이 해석이 틀린 것이다. 그때 B 나 C 로 번복한다. 이 DR 의 조사 2행이 내릴 판 목록이다.
- 고정 의존성을 올려 하한이 3.13 이 되면 `test_every_pin_installs_on_the_declared_runtime` 이 실패한다(의존성 설치 잡). 내려서 하한이 3.11 이 되면 `test_the_declared_runtime_is_actually_needed` 가 실패한다. 어느 쪽이든 선언을 다시 본다.
- 측정 계층에 3.11+ 전용 문법이 들어오면 `python-compat.yml` 이 실패한다.

## 민감도

판 하나 차이로 결론이 달라진다.

- 선언을 3.11 로 내리면 numpy · scipy · shap 이 설치되지 않는다.
- 3.13 으로 올리면 shap 0.54.1 이 cp313 휠을 내지 않아 소스 빌드로 떨어진다. PyPI 에 있는 휠 태그는 cp312 · cp314 · cp315 뿐이다.
- 3.14 는 휠이 다 있다. 하지만 고정 버전 해석 · CI · 스프린트 1 결과가 전부 3.12 에서 나왔다. 그래서 바꾸면 재현성(NFR-001)을 다시 확인해야 한다.

**3.12 는 지금 고정 버전 전부가 휠로 설치되는 가장 낮은 판이고, 결과가 실제로 나온 판이다.**

## 남은 불확실성

- NFR-04 를 평가하는 쪽이 하한으로 읽는지 확인하지 못했다. 과제 원문에 더 적힌 것이 없다.
- 3.11 은 어느 CI 잡도 돌리지 않는다. 하한(3.10)과 지원 런타임(3.12) 사이의 판에서만 다르게 동작하는 표준 라이브러리 차이는 잡히지 않는다 — #248(dataclass 가 `mappingproxy` 기본값을 3.11 에서만 거부한다)이 그 틈에서 나왔다. `python-compat.yml` 에 3.11 을 더할지는 #248 의 선택 항목으로 남겼다.
- 머리 주석의 Requires-Python 표는 2026-10-23 PyPI 조회 결과다. 의존성 설치 CI 잡이 설치된 메타데이터와 매번 대조하므로 고정 버전을 바꾸면 테스트가 알린다. 다만 의존성 없는 잡에서는 그 대조가 `BLOCKED` skip 이다.
