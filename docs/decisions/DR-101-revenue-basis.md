# DR-101-revenue-basis — 기여이익의 매출 기준을 순매출로 한다

|---|---|
| 태스크 | 이슈 101 (커머스 제보) · 관련 100 |
| 작성 | Paul(리드) · 2026-09-21 |

## 무엇을 정하는가

기여이익을 계산할 때 **매출을 할인 전(총매출)으로 잡고 할인을 비용으로 빼는가**, 아니면 **할인 후(순매출)로 잡고 다시 빼지 않는가**.

## 정하지 않으면 무엇이 막히나

지금 코드는 **둘을 섞어 쓴다.** 계약이 `order_amount = Σ(unit_price × quantity) − discount` 로 할인 후를 규정하는데(`schema.py:209`), `contribution_profit` 은 그 매출에서 `coupon_cost` 를 **또 뺀다**(`economics.py:548`).

제보자 예시로 검산: 소계 15,700 · 할인 1,570 · `order_amount` 14,130 · COGS 11,000 이면 기여이익은 3,130 이어야 하는데 1,570 을 또 빼 **1,560** 이 된다.

이 기준이 서지 않으면 이슈 100 의 교환 파일 계약(할인액을 실을지)도 정할 수 없다.

## 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A · 순매출 | 매출 = `order_amount` 그대로. 할인을 다시 빼지 않는다 | 계약 변경 없음. `order_amount` 안의 **실제 할인액**을 쓴다 | 매출 줄에 "얼마를 깎아 줬는지" 가 드러나지 않는다 |
| B · 총매출 | 매출 = `order_amount` + 할인. 할인을 비용으로 한 번 뺀다 | 매출과 할인이 분리돼 보인다. 커머스 이슈 24 의 선택과 같은 표시 방식 | **할인액을 알아야 한다.** 오늘 AI_ROI 가 가진 것은 실제 할인이 아니라 D-16 유도값이다 |

## 조사한 것

| 출처 | 무엇을 말하나 | 우리 맥락에 얼마나 맞나 |
|---|---|---|
| `src/measurement/schema.py:209` · `docs/event_schema.md:37` | `order_amount` 는 **할인 후** 금액이다 | 정본이다. 이 값의 의미는 이미 확정돼 있다 |
| `src/measurement/economics.py:548` | 기여이익 = 매출 − COGS − 쿠폰 − 배송보조 − 메시지 − 캠페인 고정비 | 쿠폰 항이 위 정의와 겹친다 |
| `src/measurement/economics.py:260` `coupon_cost()` | 실제 할인액이 아니라 `treatment_cost` 에서 **유도**한다 (D-16 · T2=3,000 · T3=7,000) | ★ 커머스 실제 할인 1,570 과 **금액 자체가 다르다** |
| 커머스 이슈 24 (제보자 인용) | 할인 전 소계와 할인 1회 차감을 확정했다 | 표시 방식은 B 이지만, **두 기준은 같은 기여이익을 낸다** |
| `src/measurement/economics.py` `cogs()` | `items` 가 비어 `NO_COST_BASIS` 를 낸다 | 그래서 `contribution_profit` 이 오늘 거의 항상 `unavailable` 이다 — 이 결함은 **잠복 상태**다 |

산술 확인: `15,700 − 11,000 − 1,570 = 3,130` 이고 `14,130 − 11,000 = 3,130` 이다. **A 와 B 는 같은 값을 낸다.** 같은 할인액을 쓸 때에 한해서다.

## 결정

**A · 순매출.**

```
revenue             = Σ order_amount                       할인 후. 계약 그대로
contribution_profit = revenue − COGS − 배송보조 − 메시지 − 캠페인 고정비
                      쿠폰 할인을 다시 빼지 않는다
marketing_cost      = 쿠폰 + 메시지 + 캠페인 고정비          ROI 분모 — 유지
```

**근거:** A 와 B 가 같은 값을 내는 것은 **같은 할인액을 쓸 때뿐이다.** 오늘 AI_ROI 가 가진 할인액은 실제 금액이 아니라 D-16 유도값(T2=3,000 · T3=7,000)이고, 커머스 실제 할인은 1,570 이다. B 로 가면 유도값으로 빼게 되어 **커머스와 숫자가 어긋난다.** A 는 `order_amount` 안에 이미 들어 있는 **실제 할인**을 쓰므로 자동으로 일치하고, 가정 A-DISCOUNT 가 기여이익에서 빠진다.

부수 효과로 `schema.py` 를 건드리지 않아 이 결정만으로는 봉인 재기록이 없다.

쿠폰이 `marketing_cost` 에 남는 것은 중복이 아니다. 분자(이익)와 분모(지출)는 다른 것이고, 할인의 이익 영향은 이미 매출 감소로 들어가 있다.

## 기각한 안과 기각 사유

| 안 | 왜 택하지 않았나 |
|---|---|
| B · 총매출 | 실제 할인액을 요구하는데 오늘 가진 것은 유도값이다. 유도값으로 총매출을 복원하면 **커머스와 다른 매출·다른 할인**을 보고하게 된다. 이슈 100 의 교환 파일이 실제 할인액을 실어 오면 B 도 가능해지지만, 그때도 A 와 **같은 기여이익**을 내므로 바꿀 이유가 생기지 않는다 |
| 쿠폰 항을 조용히 0 으로 | 이 저장소의 규율 위반이다. 빼지 않는 이유가 산출물에서 사라진다. 항목은 남기되 "이미 매출에 반영됨" 을 사유로 실어야 한다 |
| 계약을 고쳐 `order_amount` 를 할인 전으로 | `schema.py` 는 GATE 1 정본이고 커머스가 이미 할인 후를 내보내고 있다. 양쪽 다 바꾸는 비용을 치를 이유가 없다 |

## 이 결정이 틀렸다면 어떻게 드러나나

- 커머스가 같은 주문에 대해 산출한 기여이익과 AI_ROI 의 값이 **다르면** 기준이 어긋난 것이다. 이슈 100 의 종단 검사가 이것을 본다
- 쿠폰 사용 주문과 미사용 주문의 기여이익률 차이가 **할인율만큼 정확히** 벌어지면 여전히 이중 차감이 남아 있다는 뜻이다
- ROI 분모에서 쿠폰이 빠져 버리면 반대 방향의 실수다 — 분모는 유지되어야 한다

## 민감도

할인율이 커질수록 이중 차감의 절대 오차가 커진다. 예시 주문(할인율 10%)에서 기여이익이 3,130 대 1,560 으로 **약 절반**이 된다. `T3`(7,000원 쿠폰, 최소주문 50,000원) 이면 할인율 14% 이고 오차는 더 크다.

반대로 이 결정 자체의 민감도는 낮다 — A 와 B 는 같은 할인액에서 같은 값을 내므로, 나중에 표시 방식을 B 로 바꿔도 **기여이익 수치는 변하지 않는다.**

## 남은 불확실성

- **ROI 분모의 쿠폰 금액은 여전히 D-16 유도값이다.** 커머스 주문에서는 실제 할인과 다르다. 이 오차는 기여이익에서는 빠졌지만 ROI 분모에 남는다. 이슈 100 의 교환 파일이 실제 할인액을 실어 오면 해소된다
- 커머스 이슈 24 가 택한 표시 방식(총매출)과 우리 표시 방식(순매출)이 다르다. **수치는 같지만 리포트의 줄 구성이 다르므로** 양쪽 문서에 기준을 명시해야 읽는 사람이 헷갈리지 않는다
- 배송보조가 `order_amount` 밖에 있다는 전제에 기대고 있다. 스키마에 배송비 필드가 없어 오늘은 참이지만, 커머스가 배송비를 `order_amount` 에 포함시키기 시작하면 같은 종류의 이중 차감이 배송 쪽에서 생긴다
