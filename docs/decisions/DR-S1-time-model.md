## 무엇을 정하는가

시뮬레이터의 시간이 **어떤 단위로 어떻게 진행하나**(하루 틱 · 이산사건 · 혼합). 함께 정하는 것:

- 시계의 표현(정수 ms · 시간대), 시작일
- 같은 시각 사건의 순서(정렬 키)
- `advance(days)` 의 창 정의와 인자 규칙
- 타임스탬프 문자열과 `session_id` 를 만드는 방식
- 분할 불변성 `advance(a) + advance(b) ≡ advance(a+b)` 을 **무엇으로** 보장하나

## 결정

**안 C — 일 단위 결정 + 일중 밀리초 이산사건.** (2026-10-04 사용자 확인 결과에 따라 확정)

- **시계.** 정수 epoch ms 하나. 실시간 시계를 읽지 않는다. 시작일은 profile 의 `calendar_start`(KST 날짜, 기본 2025-01-01 → `1735657200000`). KST 일 번호 `day = (time_ms − start_ms) // 86_400_000`.
- **사건 큐.** `heapq` 하나. 정렬 키 `(time_ms, customer_id, seq)`. `customer_id` 는 고정 폭 `C` + 8자리라 문자열 비교가 숫자 순서와 같다. `seq` 는 고객별 단조 순번(상태). 키가 유일하므로 동률이 없고 꺼내는 순서가 넣은 순서와 무관하다.
- **일 단위 결정.** 매일 KST 00:00:00.000 에 고객마다 "하루 시작" 사건(내보내지 않는다)이 있고, 여기서 `data_spec` §3.4 의 일 단위 확률(방문 여부 등)을 평가한다. 방문이면 그날 안의 세션 시작 시각을 ms 로 뽑아 큐에 넣는다. 세션 안의 다음 행동은 **처리될 때** 다음 지연을 뽑아 예약한다(지연은 1 ms 이상). 하루 중 시각 분포는 S1 에서 검증용 균등이며 근거 없음 — S4 가 정한다. 일 단위 확률은 정수 분수로 두고 `DR-S1-rng` 의 정수 비교로 판정한다.
- **창.** `advance(days)` 는 `[now, now + days × 86_400_000)` 을 처리한다. 키의 `time_ms` 가 끝 미만인 사건만 처리하고 나머지는 큐에 남는다. `days` 가 정수이므로 **창 경계는 언제나 KST 자정**이다. 창 끝은 생성 규칙의 입력이 아니다 — 멈춤 조건으로만 쓴다.
- **인자.** `days` 는 `int` 이고 `bool` 이 아니며 0 이상. 어기면 `TypeError`/`ValueError`. `advance(0)` 은 아무것도 하지 않는다 — Sink 실행 기록도 만들지 않는다.
- **시각 상한 (2026-10-04 리뷰 반영 — Thomas L6).** 창 끝이 `MAX_TIME_MS = 10¹³` ms(2286-11-20, `session_id` 의 13자리 epoch ms 한계)를 넘으면 **쓰기 전에** `ValueError` 다(`src/simulator/_internal/world.py:17`, `src/simulator/api.py:163-164`). 상한이 없으면 아주 큰 `days` 에서 `session_id` 패턴이 깨지고, 그 전에 플러시가 일어나면 중단된 쓰기 흔적이 남는다. 앞서 적은 "13자리는 2286-11-20 까지 성립"을 검사로 옮긴 것이고 결정을 바꾸지 않는다.
- **정수 시간 (사용자 결정 2026-10-04: Python 3.10 이상 모든 판에서 바이트 동일).** 시각·지연·세션 길이·만료 기간은 전부 정수 ms 다. 지연은 정수 구간 `[lo, hi)` 의 거부 표집이나 정수 분위수 표에서 뽑고, `math.exp`/`log`/`pow`·float `sum()`·부동소수 나눗셈을 결과 경로에 쓰지 않는다 — `sum()` 은 3.12 에서 알고리즘이 바뀌었고 `math` 는 플랫폼 libm 의 얇은 포장이라 정확 반올림을 보증하지 않는다(근거는 `DR-S1-rng` 조사표). 날 번호·시각 분해는 `//`·`divmod` 정수 연산만 쓴다.
- **타임스탬프.** 정수 산술(`timedelta(milliseconds=…)`, 부동소수 나눗셈 없음)로 `YYYY-MM-DDTHH:MM:SS.mmm+09:00` 을 직접 만든다. Sink 정규화 결과와 문자 단위로 같아 저장 시 바뀌지 않는다. `datetime.fromisoformat` 을 부르지 않는다(`AGENTS.md:93`). `datetime.UTC`(3.11+) 대신 `timezone.utc`.
- **세션.** `session_id = S-{customer_id}-{세션 시작 epoch ms}`. 직전 활동에서 30분 이상 지나면 새 세션. **진행 중 세션은 상태다** — 자정이나 창 경계에서 자르지 않는다. #78 의 질문에 대한 S1 의 답: 23:50 에 시작한 세션은 자정을 넘어 이어지고, 그 이후 사건은 다음 날 파티션에 저장되며 다음 날 열쇠의 난수로 만들어진다.
- **분할 불변성 보장 장치.** ① 대기 사건 전부를 상태에 싣는다(`DR-S1-world-state`) ② 난수 열쇠가 창이 아니라 날에 묶인다(`DR-S1-rng`) ③ 창 끝을 읽는 생성 규칙이 없다 ④ 시간에 따른 상태 변화(장바구니 만료)는 읽는 시점에 시각으로 판정한다(`DR-S1-cart-lifetime`) ⑤ 창이 자정에 끊기므로 한 날짜 파티션을 두 `advance` 가 나눠 쓰지 않는다. 시험: 무작위 분할 (a, b) 여러 쌍에 대해 `advance(a+b)` 와 `advance(a)` → `advance(b)` 의 정준 이벤트 다이제스트와 **끝 상태 다이제스트**가 모두 같다.

**`data_spec` §3.4 "Tick = 1일"과의 관계.** 일 단위 확률식은 바꾸지 않고 "하루 시작" 사건에서 그대로 평가한다. 바뀌는 것은 하루 안의 행동에 밀리초 시각과 순서를 주는 것뿐이다. 문구를 "결정 단위 1일, 이벤트 시각 밀리초"로 고칠지는 리드가 정한다(후속).

**근거:** 일 단위 결정은 정본(§3.4)이고, 하루 안 시각은 같은 정본의 다른 절(09:00 · 23:59:59)과 측정 계약(ms · 30분 세션)이 이미 요구한다. 두 요구를 함께 만족하는 가장 작은 모델이 C 다. 순수 이산사건(B)과 구현 기구는 같고, §3.4 를 어디서 평가하는지를 고정한 것이 차이다.

## 이 결정이 틀렸다면 어떻게 드러나나

- 분할 불변성 시험이 실패한다 → 창 경계가 생성 규칙에 새고 있거나 상태가 빠졌다. 정준 이벤트 diff 가 첫 어긋난 사건을 짚는다.
- 정확히 KST 00:00:00.000 시각의 이벤트가 눈에 띄게 많다 → "하루 시작" 사건이 이벤트를 흘리고 있다. 이 시각 이벤트 수는 0 에 가까워야 한다.
- 창 경계(자정) 전후 1시간의 이벤트 밀도가 다른 자정과 다르다 → 경계 아티팩트. #78 의 "창 경계 불연속 검사"와 같은 시험을 S1 에서 먼저 돌린다.
- SIM-013 성능 목표(20,000명 × 30일 ≤ 수 분, `SRS:682`)를 S1 검증 시나리오에서 넘긴다 → 큐 처리 비용 가정이 틀렸다.
- 골든 해시(`DR-S1-rng`)가 3.10 잡과 3.12 잡에서 갈린다 → 시간 계산 어딘가에 부동소수가 남아 있다.

## 민감도

- "하루 시작" 사건은 고객 × 일수만큼이다. 26,000명 × 640일 ≈ 1,660만 회. `heapq` 넣기·꺼내기를 각 1 µs 로 보면 약 30 초 — **측정값이 아니라 가정이다.** 고객 수 ±20% 에 정비례한다. 부담이 되면 "하루 시작"을 큐 밖의 고객 순회로 바꿔도 정렬 키·결과는 같다.
- 시각 해상도를 초로 낮추면 같은 초에 여러 사건이 몰려 `seq` 가 순서를 정하게 되고, 측정 계약의 ms 표기와도 어긋난다. ms 가 계약 값이다.
- 하루 길이는 상수다(고정 오프셋, 서머타임 없음). 바뀔 여지가 없다.

## 남은 불확실성

- 하루 중 시각 분포(아침·저녁 피크)는 S4 가 정한다. S1 의 균등 분포는 검증용이고 근거가 없다. S4 가 비균등 분포를 넣을 때도 정수 분위수 표로 표현해야 한다.
- 판 간 동일은 로컬에서 3.14 하나로만 보았다. 3.10 은 CI(`python-compat.yml`)가 처음 확인한다.
