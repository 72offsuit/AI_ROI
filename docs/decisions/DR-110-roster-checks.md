# DR-110-roster-checks — 커머스 명부로 DQ-02·DQ-03·DQ-05 를 연다

## 무엇을 정하는가

커머스 교환 파일(#100)의 명부(`customers`·`catalog`·`orders`)로 `data_spec` §9 의 세 검사를 열 때 — ① `DQ-03` 이 어떤 이벤트를 대조하는가 ② 명부 스냅샷 이후의 이벤트를 어떻게 다루는가 ③ `DQ-05` 를 어떤 단위로 비교하는가 ④ `DQ-02` 를 여는가.

## 정하지 않으면 무엇이 막히나

세 검사가 `not_run` 으로 남고, 그 사유 문구("customers·products 테이블이 미구현")가 사실이 아니게 된다 — 명부는 교환 파일에 있다. `customers.jsonl`·`catalog.jsonl` 은 읽고 형식만 검사할 뿐 어떤 검사도 소비하지 않는 "읽는 곳 없는 파일"이 된다(#63 이 경계한 모양).

## 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| ① ⓐ 교환 파일 안 참조만 | `orders.customer_id`→`customers`, `order_items.product_id`→`catalog` | 가장 단순 | 이벤트의 고아라는 원래 정의를 덮지 못한다 |
| ① ⓑ 커머스 이벤트 ↔ 커머스 명부 | `publish` 가 커머스 분할만 넘긴다 | 원래 정의에 가장 가깝다. 출처 판별은 여전히 `publish` 한 곳 | 품질 리포트는 출처별로 나뉘지 않으므로 `scope` 가 범위를 말해야 한다 |
| ① ⓒ 이번엔 열지 않음 | 시뮬레이터 명부가 생기면 함께 | 한 번에 연다 | 커머스 명부를 아무도 쓰지 않는다 |
| ② 스냅샷 이후 제외 + 건수 | `generated_at` 이후 이벤트는 대조하지 않고 사유에 건수 | 거짓 고아가 없다 | 오래된 스냅샷이면 대조 범위가 줄어든다 |
| ② 스냅샷 이후도 위반 | — | 낡은 스냅샷이 실패로 드러난다 | 스냅샷 시각 이후 가입은 명부가 모르는 것이 정상인데 품질 게이트가 fail 이 된다 |
| ③ 날짜 단위 | `signup_date`(KST 날짜)와 이벤트 KST 날짜 비교 | 계약 변경 없음 | 가입 당일 가입 시각 이전 이벤트를 못 잡는다 |
| ③ 계약 v2 `signup_at` | 커머스가 가입 시각을 싣는다 | 정확하다 | 두 저장소 계약·코드 변경 |
| ④ 열되 로더 거부 유지 | 로더가 중복을 거부하므로 읽힌 명부는 통과 | `not_run` 보다 사실에 가깝다 | 이 검사 스스로는 실패할 수 없다 |
| ④ 거부를 검사로 옮김 | 로더는 중복을 받고 `DQ-02` 가 fail | 검사가 실패할 수 있다 | 중복 주문의 품목 귀속이 모호해져 COGS 에 별도 처리가 필요하다 |

## 조사한 것

| 출처 | 무엇을 말하나 | 우리 맥락에 얼마나 맞나 |
|---|---|---|
| `docs/data_spec.html` §9 | "모든 customer_id 는 customers 에, product_id 는 products 에 존재한다. 고아 행 0건", "timestamp < signup_date 인 행 0건" | 출처를 가르지 않는다 — 시뮬레이터 하나를 전제로 쓴 문서다. 커머스 전용 명부로는 커머스 이벤트까지만 성립한다 |
| `publish.partition_by_source` · KPI `by_source` | 출처별 결과는 분기가 아니라 **입력 분할**로 얻는다 (N-3) | ⓑ 가 같은 방식이다 — `validate.py` 는 출처를 모른 채 받은 이벤트만 본다 |
| `Ecommerce_Service` `exchange-export.ts` `listExchangeCustomers` | 가입 시각(`users.signup_date`)을 KST 로 정규화한 뒤 날짜로 잘라 낸다 | ③ 의 한계는 계약의 결과다. KST 로 자르므로 날짜 경계 자체의 오차는 없다 |
| `src/measurement/exchange.py` (#100) | `orders.jsonl` 의 중복 `order_id` 는 묶음 전체 거부 | ④ 를 열어도 이 검사는 로더를 통과한 명부만 본다 |
| 실제 커머스 표본 `tests/fixtures/commerce_exchange_v1/` | 커머스 이벤트 26건, 고객 6명, 상품 41종, 주문 3건 | 세 검사가 모두 통과한다. 표본에는 상품 이벤트가 없어 상품 쪽 대조는 합성 이벤트로만 확인했다 |

## 결정

**① ⓑ · ② 제외 + 건수 · ③ 날짜 단위 · ④ 열되 로더 거부 유지.**

```
DQ-02   교환 파일 orders 전 행 — 로더가 중복을 거부하므로 읽힌 명부는 pass (examined = 주문 수)
DQ-03   exchange_scope(= publish 가 넘긴 커머스 이벤트) 중 generated_at 이전 이벤트의
        customer_id ∉ customers  또는  product_id ∉ catalog  → 위반
DQ-05   같은 범위에서 명부에 있는 고객의 이벤트 — KST 날짜 < signup_date → 위반
공통    generated_at 이후 이벤트 N건은 대조하지 않고 reason_detail 에 싣는다
        교환 파일 없음 → not_run · 교환 파일은 있는데 범위가 없음 → not_run
```

**근거:** 명부는 커머스 것이므로 대조 범위도 커머스 이벤트다. 그 범위를 고르는 일은 출처를 아는 `publish` 에 두어, 검사 모듈이 출처를 모른다는 설계를 지킨다. 스냅샷 이후 가입은 명부가 모르는 것이 정상이라 위반으로 두면 정상 운영이 품질 실패가 된다. 날짜 단위 한계는 계약 결과이며, 두 저장소를 다시 바꿀 만큼의 효용이 아직 없다.

## 기각한 안과 기각 사유

| 안 | 왜 택하지 않았나 |
|---|---|
| ① ⓐ 교환 파일 안 참조만 | 이벤트의 고아(원래 정의)를 보지 않는다. 교환 파일 내부 결합 중 품목→주문은 로더가 이미 막는다(모르는 주문의 품목 거부). `orders.customer_id`→`customers` 는 막지 않지만, 그 주문의 `purchase` 이벤트 고객은 ⓑ 가 대조한다 |
| ① ⓒ 열지 않음 | 명부가 "읽는 곳 없는 파일"로 남는다 |
| ② 스냅샷 이후도 위반 | 스냅샷 이후 가입은 정상이다. 품질 게이트 fail 은 파이프라인을 멈추는 판정이라(`--fail-on-quality`) 정상 운영을 멈추게 된다 |
| ③ `signup_at` 추가 | 두 저장소 계약·코드 변경이 필요한데, 당일 선행 이벤트가 문제된 사례가 아직 없다. 한계는 `scope` 와 테스트(`test_earlier_on_the_signup_day_is_not_caught`)로 고정했다 |
| ④ 거부를 검사로 옮김 | 중복 주문이 있으면 품목·원가를 어느 주문에 붙일지 정해야 하고, COGS 가 모호해진다. 로더 거부가 더 안전하다 |

## 이 결정이 틀렸다면 어떻게 드러나나

- 시뮬레이터 이벤트가 `DQ-03` 위반으로 잡히면 범위가 새고 있는 것이다 — `test_publish_scopes_to_the_commerce_split` 가 막는다
- 스냅샷 직후 가입한 실제 고객이 고아로 잡히면 ② 가 적용되지 않은 것이다 — `test_event_after_the_snapshot_is_skipped_and_counted`
- `reason_detail` 의 "스냅샷 이후 N건"이 계속 커지면 교환 파일 갱신 주기가 이벤트 수집보다 느린 것이다 — 그때는 증분 갱신(v2)을 검토한다
- 가입 당일 가입 시각 이전 이벤트가 실제로 문제가 되면 ③ 을 다시 연다

## 민감도

실제 표본에서 세 검사 모두 통과하므로 게이트 판정은 바뀌지 않는다(`incomplete` 유지 — 다른 검사가 아직 `not_run`). 스냅샷 시각이 이벤트 수집보다 늦을수록 대조 범위가 넓어지고, 이를수록 "스냅샷 이후" 건수가 커진다.

## 남은 불확실성

- 표본에 상품 이벤트가 없어 상품 쪽 대조는 합성 이벤트로만 확인했다. 커머스 상품 조회·장바구니 이벤트가 포함된 표본으로 다시 확인하면 해소된다
- 위반 표본의 게시 형식이 계약과 달랐던 결함(#113)을 이 작업 중 발견해 같은 PR 에서 고쳤다 — 새 검사가 그 경로로 위반을 내보내기 때문이다
