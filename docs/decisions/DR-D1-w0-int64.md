## 무엇을 정하는가

W0 검토용 Schema 세 개의 정수 상한 9223372036854776000을 정확한 signed Int64 최댓값 9223372036854775807로 정정한다. 기존 TLV 규칙·타입·의미 hash를 변경하지 않는다.

## 정하지 않으면 무엇이 막히나

Schema가 2의 63승을 수용하는데 TLV가 거부하여 형식 검증과 의미 검증이 어긋난다. 정식 계약 채택 전 일관된 경계와 실제 실행 증거가 필요하다.

## 선택지

| 안 | 장점 | 한계 |
|---|---|---|
| 정확한 정수 literal로 상한 정정 | 기존 Int64 계약과 일치, 정상 값 유지 | 생성/재직렬화 시 다시 반올림되지 않는 검사 필요 |
| TLV에서만 거부 | 기존 제품 변경 없음 | Schema의 잘못된 수용을 남기므로 기각 |
| Int64 범위를 확대 | 기존 Schema 수용 유지 | 승인된 직렬화 규칙을 바꾸므로 기각 |

## 조사한 것

W0 Schema는 Git 제외 plans의 제안 문서다. 앞선 대조에서 HistoryClaim.lifetime_unique_order_count=9223372036854775808을 Schema는 수용하고 기존 TLV는 integer outside Int64로 거부했다. 세 문서의 같은 상한 46곳을 확인했다. literal 검색에서 동일 기록 이슈는 찾지 못했으며 이번 사용자는 GitHub 쓰기를 제외했다. 제공 예시 93건의 형식 검증과 제품 의미 검증은 구분한다.

## 결정

세 Schema에서 해당 상한 literal만 정정한다. 타입·하한·required·enum·URN은 유지한다. 새 tests/test_feature_d1_w0_contracts.py에서 모든 해당 정수 필드의 max-1/max 수용 및 max+1 거부, JSON 정수 literal 정확성, 기존 93개 예시, 의미 검사 계획의 미실행 상태를 검증한다. jsonschema/referencing가 없거나 Git 제외 W0 문서가 없는 환경은 해당 형식 시험을 명시적으로 skip한다.

**근거:** 값 범위를 새로 선택하는 일이 아니라 기존 Int64 명세의 오기 정정이다. 검증 전에 이 기록을 작성했다. 새 plans/D1-W0-int64-revalidation-20261022.log에 실제 실행을 남기며 과거 미생성 로그를 소급 생성하지 않는다.

## 기각한 안과 기각 사유

| 안 | 사유 |
|---|---|
| 과거 로그를 이번 결과로 채우기 | 실행 시점·환경·SHA의 증거를 혼동 |
| 공유 계약이나 기존 TLV 수정 | 이번 허용 범위 밖이며 올바른 기존 거부를 약화 |

## 이 결정이 틀렸다면 어떻게 드러나나

max+1의 형식 수용, max의 형식 거부, 관련 없는 Schema 필드 변경, 정상 TLV/golden 변경이면 실패다. 형식 예시 통과를 실제 제공자 수락·의미 검사 통과로 쓰는 것도 실패다.

## 민감도

경계 1 차이가 인수 여부를 바꾼다. JSON 정수를 float나 JavaScript Number를 경유해 저장하지 않고 Python 정수 또는 원문 literal을 사용한다.

## 남은 불확실성

2026-10-22 실제 재검증은 새 로그에 보존했다. 최초6개는 의존성6 PASS / 무의존2 PASS·4 SKIP였고, 이후 I03/SequenceRow shape 교차 시험을 추가한 최종 W0 7개는 의존성7 PASS / 무의존2 PASS·5 SKIP다. 수정 전 92개 실패는 두 시험 메서드의46+46 하위 사례이며 실행된 메서드 수6과 혼용하지 않는다. 기존 예시93건·semantic plan의 NOT_RUN 기록은 유지했다.

공유 계약 수락·실제 입력 인수·#126은 별도다. SD1–SD8·Q1–Q5 선택을 유지한다. 커밋·푸시·GitHub 쓰기·소유표 수정은 하지 않는다. 새 시험 경로의 소유 등록은 리드 인계다.
