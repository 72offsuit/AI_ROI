## 무엇을 정하는가

T0 에 Eligible 고객을 Treatment(T3)·Control(T0)으로 **어떤 방식으로, 누가, 어떤 층으로** 나누는가. 그리고 배정이 의도대로 됐는지 보는 **SRM·공변량 균형 검사의 기준과 기록 위치**를 정한다. 규모는 `DR-S3-sample-size`(확정)를 따른다.

## 정하지 않으면 무엇이 막히나

- S6(#80) — 처치 반응과 `ground_truth`(Y(1)·Y(0))는 배정이 정해진 고객에게만 계산된다.
- D4(#86) — 시스템 팀의 Uplift 학습 데이터가 이 배정에서 나온다. 배정이 편향되면 CATE 추정 전체가 틀어진다.
- D9(#91) — 지금 `apply_treatment` 는 호출자(오케스트레이션)가 배정 표를 넘긴다. 실험 배정을 누가 만드는지 정하지 않으면 D9 의 루프 모양이 정해지지 않는다.

## 선택지

**배정 방식**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 단순 무작위 — 고객별 Bernoulli(0.5) | 가장 단순. 고객별 독립이라 고객 추가에 안정 | 군 크기가 흔들린다(군당 10K 에서 ±1σ ≈ 71명). 페르소나·recency 구성이 우연히 어긋날 수 있다 |
| B | 층화 무작위 1:1 — 층 안에서 정확히 반반 (data_spec §4.2) | 층 변수의 균형이 설계로 보장된다. ATE 분산이 줄거나 같다 | 층 변수가 숨김 값(페르소나)이면 그것을 읽는 쪽이 배정해야 한다 |
| C | Propensity Score Matching (SRS SIM-010 의 대안) | 관측 연구에서 쓰는 방법 | 시뮬레이터는 무작위 배정을 직접 할 수 있다 — PSM 이 풀려는 문제(비무작위 처치)가 없다. data_spec §16.4 도 쓰지 않기로 했다 |

**층 기준 (B 일 때)**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| B1 | 페르소나(6) × recency(4) = 24층 (data_spec §4.2) | Balance Check 항목(페르소나·recency)이 설계로 맞는다 | 시스템 팀은 페르소나를 볼 수 없어 층별 분석을 못 한다 |
| B2 | recency(4)만 — 관측값만 | 시스템 팀이 같은 층으로 분석할 수 있다 | 페르소나 균형은 우연에 맡긴다(군당 10K 면 대개 작지만 보장은 없다) |

**층 안 1:1 을 만드는 법**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| R1 | 층 전체를 한 난수열로 섞기(순열) | 단순 | 고객 1명이 늘면 층 전체 배정이 바뀐다 — S1 의 "고객 1명 변경 → 다른 고객 궤적 불변" 성질이 깨진다 |
| R2 | 고객마다 고유 열쇠(`Stream(seed, customer_id, "assignment", T0일)`)로 정렬 점수를 뽑고, 층 안에서 점수 순 앞 절반을 Treatment | 고객 추가 시 경계 근처 고객만 바뀐다. 기존 `rng.Stream` 그대로 | 홀수 층에 1명이 남는다 |
| R3 | data_spec 문구 그대로 "Bernoulli(0.5)" | 문서와 같다 | **정확한 1:1 이 아니다** — data_spec §4.2 는 "층 내에서 정확히 1:1"과 "Bernoulli(0.5)"를 동시에 적어 서로 어긋난다 |

**누가 배정하나**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| W1 | 시뮬레이터가 내부에서 — 새 공개 함수(예: `assign_experiment(...)`)가 Eligible 판정·층화·배정을 하고 관측 가능한 배정 표(`customer_id → treatment_id`)만 돌려준다 | 숨김 값(페르소나·이탈 성향)을 시뮬레이터 밖으로 내지 않는다. SIM-010 이 시뮬레이터 요구사항이다 | `api.py` 공개 표면이 늘어난다 → `DR-S1-api-surface` 번복 + `docs/simulator_api.md`(시스템 팀 계약) 변경 |
| W2 | 오케스트레이션이 — 관측값으로 층화해 `apply_treatment` 로 넘긴다 | API 변경 없음 | 페르소나 층화 불가(B2 강제). 실험 배정이 시스템 팀 코드에 들어가 SIM-010 소유가 흐려진다 |

| data_spec §4.2 | stratified_random 1:1, 페르소나 6 × recency 4(14–27·28–41·42–89·90+일), 배정 T0 09:00, T3 vs T0, no crossover | 설계 정본. 단 난수기를 `PCG64 ⊕ hash()` 로 적었는데 `DR-S1-rng` 가 기각한 방식이다(`hash()` 는 프로세스마다 솔트) — `rng.Stream` 으로 바꿔 읽는다 |
| data_spec §4.2 Balance Check | 페르소나 χ² p > 0.05, 나머지 |SMD| < 0.1, Recency 는 KS 도. 실패 시 seed 바꿔 재배정, **결과를 본 뒤에는 재배정하지 않는다**. 결과는 `results/assignment_balance.json` | ★ `results/` 는 **시스템 팀 소유이고 시뮬레이터 팀은 읽지도 않는다**(TEAM_SETUP §1·§2). 게다가 페르소나·Baseline Churn Risk 는 숨김 값이라 시스템 팀이 보면 안 된다. 이 경로는 쓸 수 없다 |
| Imbens & Rubin (2015) *Causal Inference for Statistics, Social, and Biomedical Sciences* 9장 — 층화 무작위 실험 | 층 안 배정 확률이 모두 같으면 층을 무시한 평균 차도 불편이고, 층별 추정은 분산이 같거나 작다 | 우리 배정 확률은 모든 층에서 0.5 다 → 시스템 팀이 층(페르소나)을 몰라도 ATE·CATE 추정이 편향되지 않는다. 층을 무시하면 분산이 약간 과대평가될 뿐이다(보수적) |
| Morgan & Rubin (2012) "Rerandomization to improve covariate balance in experiments", *Annals of Statistics* 40(2) | 균형 기준을 **배정 전에** 정해 두고 통과할 때까지 다시 뽑는 것은 정당하다. 단 분석이 그 사실을 알아야 한다 | data_spec 의 "실패 시 seed 변경 후 재배정"이 이것이다. 기준·최대 시도 수·실제 시도 수를 기록해야 한다 |

## 결정

**사용자 결정 (2026-10-22): U5~U9 를 제안대로 확정한다.**

| # | 결정 (제안) |
|---|---|
| U5 | **층화 무작위 1:1 (B), 층 = 페르소나 6 × recency 4 = 24층 (B1)**. data_spec §4.2 그대로 |
| U6 | **층 안 정확 1:1 은 R2** — 고객별 열쇠 `Stream(seed, customer_id, "assignment", T0일)` 로 정렬 점수를 뽑아 점수 순 앞 ⌊n/2⌋ 명을 Treatment, 다음 ⌊n/2⌋ 명을 Control. 홀수 층의 남는 1명은 같은 열쇠의 `bernoulli(1, 2)` 로 정한다. data_spec 의 `PCG64 ⊕ hash()` 와 `Bernoulli(0.5)` 문구는 쓰지 않는다(정정은 리드 몫) |
| U7 | **시뮬레이터가 내부에서 배정한다 (W1)**. 공개 함수 하나를 더한다. 반환값은 `customer_id → treatment_id`(`T3`/`T0`)뿐이고 층·페르소나·균형 수치는 담지 않는다. 이벤트에는 측정 계약 그대로 `treatment_id`·`treatment_group`·`experiment_id` 를 싣는다. `DR-S1-api-surface` 를 번복(부분)하고 `docs/simulator_api.md` 를 고친다 — **시스템 팀 계약이 바뀌므로 PR 전에 시스템 팀(D9 담당 광진)에게 알린다** |
| U8 | **균형 검사** — SRS 다섯 항목, data_spec 기준(페르소나 χ² p > 0.05, 나머지 |SMD| < 0.1, Recency 는 KS 도). 실패하면 `experiment_seed` 를 정해진 규칙(+1)으로 바꿔 다시 배정하고 **최대 20회**까지. 시도 횟수와 매 시도 결과를 기록한다. 20회 안에 통과 못 하면 배정하지 않고 오류. SRM 은 전체·층별 χ², p < 0.001 이면 오류(구현 결함 탐지용) |
| U9 | **균형 기록은 시뮬레이터 숨김 영역에** — `data/hidden/` 아래 시뮬레이터 소유 경로에 쓴다. `results/` 에 쓰지 않는다. 관측값 항목(누적 구매 수·AOV·Recency)만 따로 공개할지는 시스템 팀과 리드가 정할 일로 남긴다 |

**근거:**
- 배정 확률이 모든 층에서 0.5 이므로 처치 여부 W 는 페르소나와 **독립**이다. 페르소나로 층화해도 배정 결과에서 페르소나를 역추론할 수 없고, D4 의 CATE 추정은 편향되지 않는다(Imbens & Rubin 9장). 이슈의 질문 "페르소나가 배정에 들어가면 D4 에 어떤 영향?"에 대한 답이다 — 편향은 없고, 시스템 팀이 층을 모르면 분산이 약간 보수적으로 잡힐 뿐이다.
- 층화는 페르소나·recency 균형을 우연이 아니라 설계로 맞춘다. 숨김 층 변수를 쓰려면 숨김 값을 가진 쪽, 곧 시뮬레이터가 배정해야 한다.
- R2 는 S1 이 지킨 "고객별 독립 난수" 성질을 가장 덜 깬다 — 고객 1명이 늘면 그 층에서 경계 근처 1명만 바뀔 수 있다.

## 이 결정이 틀렸다면 어떻게 드러나나

- **SRM 검사 실패** (p < 0.001) → 배정 구현 결함. 정확 1:1 설계에서는 나오면 안 된다.
- **20회 재배정으로도 균형 기준을 못 넘음** → 기준이 군 크기에 비해 너무 엄격하거나 층 설계가 틀렸다. 군당 10K 에서 |SMD| < 0.1 은 거의 항상 통과해야 한다(SMD 표준오차 ≈ √(2/10000) ≈ 0.014).
- **같은 seed 두 번 → 배정이 바이트 단위로 다름** → 재현성 결함(SIM-011).
- **배정 결과·오류 메시지·반환값에 페르소나 id 가 나옴** → `tests/test_isolation.py` 가 잡는다.
- **D4 가 층을 모른 채 추정한 ATE 가 ground truth 와 체계적으로 어긋남** → 위 독립성 주장이 틀렸다는 뜻. 이 대조는 S8 이 두 GATE 뒤에 한다 — 시뮬레이터 팀이 그 전에 보지 않는다.

## 민감도

| 바뀌는 값 | 변화 | 무엇이 달라지나 |
|---|---|---|
| 층 수 24 | recency 4 → 3·5 | 층이 늘수록 홀수 층 잔여(최대 층당 1명)가 늘지만 24~30명 수준이라 군 크기 차는 ±15명 이내 |
| 균형 기준 |SMD| < 0.1 | 0.08 ~ 0.12 | 군당 10K 의 SMD 표준오차 0.014 대비 5.7σ 이상 — 재배정 확률은 사실상 0. 기준이 결과를 좌우하지 않는다 |
| 최대 재배정 20회 | 16 ~ 24 | 위 이유로 실제로는 1회에 통과할 것이 예상된다. 상한은 무한 반복을 막는 장치다 |
| small 규모 (군당 ≈ 1,950) | — | SMD 표준오차 ≈ 0.032. 그래도 0.1 은 3σ — 재배정이 드물게 생길 수 있다 |

## 남은 불확실성

- **Eligible·recency 는 구매 이력에 걸려 있다.** S4 가 구매를 만들기 전에는 실제 배정 대상이 0명이다. S3 는 배정 로직을 구현하고 **합성 상태(구매 이력을 직접 넣은 테스트용 세계)** 로 검증한다. 실제 규모의 SRM·균형 실측은 S4 이후로 `BLOCKED`.
- **배정 시각과 이벤트** — 배정 자체가 이벤트를 남기는지(`campaign_exposed`·`coupon_exposed` 는 S6 의 처치 반응 몫), `experiment_id`·`campaign_id` 를 어떤 규칙으로 만들지는 구현 때 이 DR 에 보완한다.
- **새 공개 함수의 이름·인자** — `DR-S1-api-surface` 번복 때 정한다. D9 가 이 함수를 언제 부르는지(T0 마다, 분기 전)는 시스템 팀과 맞춰야 한다.
- **다중 T0(rolling)** — 같은 고객이 여러 T0 에 Eligible 이면 매번 다시 배정하는가. 열쇠에 T0일이 들어가 있어 매번 독립이다. 이전 처치의 이월 효과는 S6 몫이다.
- **data_spec 정정** — §4.2 의 `PCG64 ⊕ hash()`·`Bernoulli(0.5)` 문구와 `results/assignment_balance.json` 경로. 리드 몫이다.
