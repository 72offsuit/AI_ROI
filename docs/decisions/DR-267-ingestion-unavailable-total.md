# DR-267-ingestion-unavailable-total — 수집 리포트의 "계산 불가 지표 수" 합계는 두 출처를 합친 입력으로 센다

| | |
|---|---|
| 태스크 | 리드 · #267 (#256 반영 ③ 조사에서 발견) |
| 작성 | 인성(Danto7632, 에이전트 구현) · 2026-11-08 |
| 상태 | 확정 — 집계 범위는 리드 결정(2026-11-08) |

## 무엇을 정하는가

`ingestion_report.totals.unavailable_metric_count` 가 **어느 입력**에서 "계산할 수 없는 Observable 지표 수"를 세는가. 커머스 · 시뮬레이터 두 출처가 함께 들어올 때의 범위를 정한다.

## 정하지 않으면 무엇이 막히나

- **지금 값이 입력이 아니라 코드 순서에 따라 정해진다.** `build_ingestion_report()` 가 출처 반복문(`for name, events in split.items()`)이 끝난 뒤 남은 `events` 로 이 값을 계산했다. `SourceSplit.items()` 의 마지막이 시뮬레이터라 **시뮬레이터 묶음만** 반영됐다. 커머스만 들어온 입력에서 16(전부 계산 불가)이 나왔다(#267 재현: 기대 12 → 실제 16, 섞인 입력 12 → 14).
- 이 값은 수집 대시보드의 "수집 건전성" 카드(`dashboard/src/app/(observability)/ingestion/page.tsx`)에 그대로 나간다. 같은 카드 묶음의 다른 값(거부 수 · 거부율 · 타입 커버리지)은 전체 기준이라, 이 카드만 다른 범위를 말하고 있었다.

## 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 합친 입력** | `all_events`(커머스 + 시뮬레이터)의 타입 근거로 센다 | 이름("합계") · 같은 묶음의 다른 값 · `all_events` 를 이미 만들어 둔 구조와 맞는다. 계약 스키마(`metric_value`)와 화면이 그대로다 | 출처별로 무엇이 빠졌는지는 이 값으로 알 수 없다 |
| B. 출처별로 나눔 | `events_ingested` 처럼 `by_source` + `combined` 로 낸다 | 출처별 누락이 보인다 | 계약 스키마(`ingestion_report.schema.json`)와 대시보드 카드 형식이 바뀐다 — 공유 계약 변경이다 |
| C. 시뮬레이터 전용으로 명시 | 지금 동작을 정책으로 굳히고 이름 · 설명을 바꾼다 | 코드 변경 최소 | 커머스만 있는 운영에서 "전부 계산 불가"를 말한다. 이 동작을 의도했다는 기록이 없다 — 반복 변수에 기댄 우연이다 |
| D. 출처별 계산 불가 수를 더함 | 커머스 수 + 시뮬레이터 수 | — | 16을 넘을 수 있고, 근거 타입이 두 출처에 나뉘면 합친 입력에서는 계산 가능한 지표를 두 번 계산 불가로 센다 |

## 조사한 것

| 출처 | 무엇을 말하나 | 우리 맥락에 얼마나 맞나 |
|---|---|---|
| `src/measurement/publish.py` `build_ingestion_report()` | `all_events` 를 만들어 `events_ingested.combined` 에 쓰고, 거부 수 · 거부율 · 타입 커버리지는 전체 manifest 로 계산한다 | 같은 `totals` 안에서 이 값만 마지막 출처를 썼다 — 의도된 차이라는 주석 · 기록이 없다 |
| `_split_with_combined()` 주석 | 계층 0 은 `combined` 가 허용되는 유일한 계층이다(R-7) | 합친 범위가 계층 0 에서 허용된 해석이다 |
| `src/measurement/coverage.py` `unavailable_metrics()` | 지표의 근거 이벤트 **타입이 있는지**로 계산 불가 목록을 만든다(값 · 필드 결측은 따로 센다) | 타입 존재는 합집합이라, 합친 입력의 계산 불가 목록은 각 출처 목록의 교집합 이하다 — 출처별 수를 더하면 안 되는 이유다 |
| #256 반영 ③ 조사(광진, 2026-11-07) · #267 본문 | 합성 입력 재현 2건: 12 → 16, 12 → 14 | 이 PR 의 회귀 검사가 같은 입력을 실제 `build_ingestion_report()` 경로로 다시 센다 |
| `#99` · PR `#102` | 예전에 manifest(마지막 실행분)를 데이터셋 사실로 쓴 문제 | 원인이 다르다(마지막 **실행** vs 마지막 **출처 반복 변수**). 그래서 manifest 의 `event_type_counts` 가 아니라 실제 이벤트에서 센다 |

## 결정

**A — 합친 입력으로 센다.** `Counter(event_type for e in all_events)` 를 `coverage.unavailable_metrics()` 에 넣는다(타입 근거 규칙은 정본을 그대로 쓴다).

- 반복 변수 이름을 `source_events` 로 바꿔, 반복 뒤에 `events` 를 다시 집어 쓰는 실수가 생기지 않게 한다.
- 계약 스키마 · 대시보드 · `session_duration` 근거 매핑(#256)은 바꾸지 않는다.
- 회귀 검사: `tests/test_publish_pipeline.py` `TestIngestionTotalsUseAllSources` 7건 — 커머스만 12, 섞인 입력 12(#267 재현 두 건), 시뮬레이터만, 두 출처 모두 빈 입력 16, 타입을 출처 사이에서 맞바꾼 입력이 같은 값, 출처별 수의 합이 아님, 출처별 타입 수의 실측 0 유지.

## 기각한 안과 기각 사유

| 안 | 왜 택하지 않았나 |
|---|---|
| B | 출처별 누락을 보려면 `by_event_type` 의 출처별 타입 수(이미 게시됨)로 볼 수 있다. 이 값까지 나누면 공유 계약 스키마와 화면을 바꿔야 하는데, 결함 수정에 계약 변경을 섞지 않는다(#267 수용 기준). 필요하면 별도 이슈로 다룬다 |
| C | 지금 동작은 반복 변수에 기댄 우연이고, 커머스 단독 운영에서 사실과 다른 "전부 계산 불가"를 말한다 |
| D | 위 조사 — 근거 타입이 출처에 나뉘면 틀린 값을 낸다. 회귀 검사 `test_total_is_not_the_sum_of_per_source_counts` 가 막는다 |

## 이 결정이 틀렸다면 어떻게 드러나나

- **출처 순서가 다시 값에 끼어든다:** 같은 이벤트를 출처 사이에서 맞바꿨는데 합계가 달라진다 → `test_swapping_types_between_sources_gives_the_same_total` 실패.
- **합친 범위가 맞지 않는 소비처가 있다:** 이 카드를 "시뮬레이터 데이터의 누락"으로 읽는 화면 · 문서가 나온다. 지금 대시보드 · 계약 스키마에는 그런 설명이 없다(조사). 나오면 B 로 옮긴다.

## 민감도

정의 선택이라 수치 모수가 없다. 값이 달라지는 경우는 **커머스에만 있는 근거 타입이 있을 때**뿐이다 — 그때 이 값이 줄어든다(더 정확해진다). 두 출처의 타입 구성이 같으면 수정 전후 값이 같다.

## 남은 불확실성

- 이미 게시된 수집 리포트는 다시 만들지 않는다. 다음 게시부터 바뀐다.
- sink manifest 는 별도 생산 경로이고 이 결함이 manifest 를 오염시킨다는 재현은 없다(#267 본문). 이 기록은 manifest 를 다루지 않는다.
- `session_duration` 근거 타입의 비대칭(`return_visit` 만 있는 부분 창에서 계산 불가로 남음)은 #256 · DR-256 의 유보 사항이고 이 결정과 원인이 다르다.
