## 무엇을 정하는가

calendar_date 문자열의 허용 문자 집합과 정규화 책임을 정한다. 날짜의 논리 값과 tag 06의 ASCII 출력 payload는 기존 규칙을 유지한다. 출력이 ASCII라는 사실만으로 입력의 비ASCII 십진 숫자까지 거부하도록 승인됐다고 추론하지 않는다. #131의 시간 문자열 선택을 날짜 입력 정책으로 자동 확대하지 않는다.

## 정하지 않으면 무엇이 막히나

문자열 index_date의 엄격한 입력 guard와 Date 스키마의 최종 수용 기준을 확정할 수 없다. 로컬 key()/split 경로는 날짜 문자열을 calendar_date로 해석한다. 어떤 출처·버전에서 기존 비ASCII 날짜를 거부할지 또는 정규화할지 합의해야 한다. 이 보류는 #133 오류 처리나 다른 독립 D1 수정의 진행을 막지 않는다.

## 선택지

| 안 | 제안하는 문자열 허용 범위 | 장점 | 한계 |
|---|---|---|---|
| A — 권고 | ASCII 숫자만 사용한 정확한 YYYY-MM-DD. ASCII 하이픈, 4-2-2자리, trim·Unicode 정규화 없음 | 시간 문자열과 W0 제안 패턴에 일관됨. 입력 허용 집합이 단순하고 명시적 | 기존 아랍·전각·혼합 숫자 수용이 거부로 바뀜. 호환 범위·정책 버전 필요 |
| B — 비교용 구체화 | Unicode 십진 숫자(Nd) 4-2-2와 ASCII 하이픈을 허용하고 값이 유효하면 date로 정규화. 혼합 Nd도 허용하는 안 | 현재 관측한 아랍·전각·혼합 수용과 호환 | Nd 범위·혼합 허용·정규화 경계를 명시하고 ASCII 제안 스키마와의 차이를 해결해야 함 |

B는 모든 숫자처럼 보이는 문자나 모든 Unicode numeric 문자를 허용하는 안이 아니다. 제곱 숫자·로마 숫자·문자 변환까지 확장하지 않는다. B의 Nd·혼합 허용 구체화도 비교용 제안이며 사용자 선택이 아니다.

두 안 모두 정확한 date 객체를 그대로 허용하고 datetime 객체·date subclass·다른 타입은 기존처럼 거부하는 방향을 제안한다. datetime에서 날짜를 추출하거나 정수 20261020을 날짜로 추정하지 않는다.

## 결정

**미결정이다. A를 권고하며, 광진의 명시적 선택 전에는 calendar_date의 입력 허용 동작을 바꾸지 않는다.** 권고 이유는 현행 시간 문법·제안 Date 스키마와의 일관성 및 좁은 입력 허용 집합이다. 기존 비ASCII 입력을 잘못된 날짜나 잘못된 hash라고 단정하는 선택이 아니다.

다음은 정상/반례의 기대 결과 제안이다. 현재 열은 코드 및 명시한 합성 재현 기준이고 A/B 열은 선택 후 고정할 명세다. A/B 제품 시험 통과를 뜻하지 않는다.

| 입력 | 현재 | A 선택 후 기대 | B 선택 후 기대 |
|---|---|---|---|
| ASCII `2026-10-20` | date(2026,10,20) | 동일 수용 | 동일 수용 |
| 아랍 `٢٠٢٦-١٠-٢٠` | 같은 date 수용 | 문법 거부 | 같은 date로 정규화 |

| 앞/뒤 공백 ` 2026-10-20`, `2026-10-20 ` | 문법 거부 | 거부, trim 없음 | 거부, trim 없음 |

### 광진의 선택 문안

A 선택 문안:

> X-2는 A안을 선택한다. 날짜 문자열은 ASCII YYYY-MM-DD만 허용하고, 정확한 date 객체 허용과 datetime/다른 타입 거부는 유지한다. 기존 비ASCII 문자열의 수용 변경과 적용 버전·호환 범위를 기록한 뒤 최소 수정안을 진행한다. 날짜 TLV와 정상 의미값은 유지한다.

B 선택 문안:

> X-2는 B안을 선택한다. Unicode 십진 숫자의 허용 집합·혼합 표기·정규화 책임과 Date 스키마 정합성을 먼저 명시하고 검토한다. 그 명세가 확인되기 전에는 허용 범위를 추가 확대하지 않는다.

문안은 선택용 초안이다. 이 문서의 커밋이나 권고 자체가 문안의 사용자 제출/승인은 아니다.

### 선택 후 최소 구현 범위

A라면 calendar_date 문자열 패턴을 ASCII 숫자로 제한하고 기존 serialization 시험에 기대표 반례·정상 대조를 추가한다. 날짜/date 타입 경계·잘못된 달력·윤년·TLV·key()/split 경로·fixture R/S/V 및 기존 회귀를 대조한다. int 변환·출력 payload와 정상 날짜 의미를 이유 없이 바꾸지 않는다.

B라면 Nd·혼합 표기·정규화 위치를 명세에 고정한 후 현행 수용이 그 범위와 일치하는지 확인하고 필요한 최소 코드/시험만 변경한다. W0 Date의 ASCII 패턴과 다르므로 해당 스키마/입력 계약 담당자에게 정합성 선택을 요청한다. 공개 계약이나 W0 스키마를 D1이 단독 수정하지 않는다.

두 안 모두 적용할 입력 정책 버전·과거 파일 처리·실제 제공자 사용 범위를 기록해야 한다. A는 수용 집합을 줄이므로 기존 Unicode 문자열 파일이 거부될 수 있다. 과거 정상 ASCII/date 산출물과 논리 값의 hash는 유지돼야 한다. 입력 파일을 별도 변환하면 정확한 file hash는 달라질 수 있으므로 기존 외부 pin을 조용히 바꾸거나 legacy fallback을 넣지 않는다. 필요한 마이그레이션은 별도 승인 범위다. 입력 정책의 버전 처리와 공유 계약 반영 범위는 선택 시 확정하고, tag 06 규칙 변경으로 자동 확대하지 않는다.

## 기각한 안과 기각 사유

아래는 현재 권고에서 제외한 이유이며 사용자 최종 기각을 뜻하지 않는다.

| 안 | 현재 권고에서 제외한 이유 |
|---|---|
| B를 우선 채택 | 실제 Unicode 사용 근거가 없고 제안 스키마와의 정합성·허용 집합을 더 정해야 함. 호환성이 필요하다고 확인되면 재검토 가능 |
| payload가 ASCII이므로 입력도 이미 ASCII 전용 승인됐다고 처리 | 출력과 입력 계약의 근거가 다름 |
| 공백 trim·NFKC 등 자동 정규화 | 현재 승인 범위를 넘어 허용 집합을 바꾸며 다른 문자까지 변환할 수 있음 |
| Unicode 입력이면 ASCII로 몰래 고쳐 로더 통과 | 정확한 파일·요청 pin과 입력 정책을 숨김 |
| #133과 날짜 정책을 묶어 즉시 구현 | 독립 결함 수정에 미승인 입력 정책을 끼워 넣음 |

## 이 결정이 틀렸다면 어떻게 드러나나

실제 소비자 계약이 Unicode 날짜를 요구하거나 기존 파일에서 의미 있는 사용이 확인돼 A의 호환성 계획 없이 수용을 중단할 수 없다면 권고 A의 근거가 부족하다. B를 선택하고도 허용 집합 밖 문자를 받거나 제안 스키마와 달리 받는 이유를 설명하지 못하면 명세가 부족하다.

선택 후 기대표와 다른 수용/거부, 윤년/달력 판정 변화, date와 datetime 혼용, 정상 날짜의 TLV·fixture R/S/V 변경, 정확한 입력 pin의 자동 교체는 구현 실패다. 현재 제안만으로 이 시험이 실행/통과됐다고 보고하면 상태 기록 실패다.

## 민감도

수치 임계값보다 허용 문자 집합의 선택이다. 숫자 한 글자만 ASCII에서 비ASCII로 바뀌어도 A의 수용 여부가 달라진다. B는 문법이 달라도 같은 날짜 의미로 정규화될 수 있다. 실제 입력 중 영향 비율은 조사하지 않았으므로 임의의 사용률·마이그레이션 비용을 만들지 않는다.

## 남은 불확실성

광진의 A/B 선택, 적용 입력 정책 버전, 실제 Unicode 사용 여부, 과거 파일의 거부/마이그레이션 범위, W0/공유 Date 계약 담당자의 수락이 남는다. 실제 근거가 없다는 사실을 A 승인이나 B 필요성으로 대신하지 않는다.

현재 calendar_date는 그대로이며 문서만 추가한다. SD1–SD8·Q1–Q5 선택은 유지한다. #126·제공자 수락·실제 입력 인수·final_refit·Store·모델·CURRENT·D1 전체 완료는 이 제안 범위 밖이다. 소유 등록과 Python 3.10 실행의 기존 제한도 해결됐다고 표시하지 않는다.
