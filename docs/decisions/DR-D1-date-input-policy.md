## 무엇을 정하는가

calendar_date 문자열을 ASCII 숫자와 ASCII 하이픈의 정확한 YYYY-MM-DD로 제한한다. 근거는 광진의 2026-10-22 A안 선택이다. 날짜의 논리 값과 tag 06의 ASCII 출력 payload는 기존 규칙을 유지한다. 출력이 ASCII라는 사실이나 #131 시간 문자열 선택만으로 날짜 입력 정책까지 승인됐다고 추론한 것이 아니다.

## 정하지 않으면 무엇이 막히나

승인 전에는 문자열 index_date의 엄격한 입력 guard를 확정할 수 없었다. 이번 선택으로 로컬 calendar_date와 이를 사용하는 key()/split/로더 입력 guard는 진행한다. 공유 Date 계약의 수락·실제 제공자의 사용 범위·과거 파일 재발행은 별도이며, 그 미확인을 이유로 로컬 구현 전체를 보류하지 않는다.

## 선택지

| 안 | 제안하는 문자열 허용 범위 | 장점 | 한계 |
|---|---|---|---|
| A — 선택 | ASCII 숫자만 사용한 정확한 YYYY-MM-DD. ASCII 하이픈, 4-2-2자리, trim·Unicode 정규화 없음 | 시간 문자열과 W0 제안 패턴에 일관됨. Unicode DB 판과 무관한 허용 집합 | 기존 아랍·전각·혼합 숫자 수용이 거부로 바뀜. 호환 범위·정책 버전 기록 필요 |
| B — 기각, 재검토 조건부 | Unicode 십진 숫자(Nd) 4-2-2와 ASCII 하이픈을 허용하고 값이 유효하면 date로 정규화. 혼합 Nd도 허용하는 비교안 | 승인 전 아랍·전각·혼합 수용과 호환 | Unicode DB 버전 또는 허용 문자 목록 고정, 혼합 허용·정규화 경계 및 ASCII 제안 스키마와의 차이 해결 필요 |

B는 모든 숫자처럼 보이는 문자나 모든 Unicode numeric 문자를 허용하는 안이 아니다. 제곱 숫자·로마 숫자·문자 변환까지 확장하지 않는다. B의 Nd·혼합 허용 구체화도 비교용 제안이며 사용자 선택이 아니다.

선택한 A안은 정확한 date 객체를 그대로 허용하고 datetime 객체·date subclass·다른 타입은 기존처럼 거부한다. datetime에서 날짜를 추출하거나 정수 20261020을 날짜로 추정하지 않는다. 문자열 subclass의 기존 isinstance 경계는 넓히거나 좁히지 않으며 내용에는 같은 ASCII 검사를 적용한다.

승인 전 네 날짜 표현의 TLV는 모두 `06000000000000000a323032362d31302d3230`이었다. 그 수용만으로 날짜 payload 위반이 입증되지는 않는다. #133 당시 calendar_date는 변경하지 않았으며, 이번 #134에서 문자열 허용 범위만 축소한다. B를 향후 재검토하려면 Unicode 버전 또는 명시 허용 문자 목록을 고정하고 실행기 간 동일 판정을 검증해야 한다. A안은 비ASCII를 int 변환 전에 거부하므로 이 Unicode DB 의존성을 제거한다.

## 결정

**2026-10-22 광진이 A안을 선택했다.** 정확한 ASCII `[0-9]{4}-[0-9]{2}-[0-9]{2}` 전체 일치 후 실제 달력을 검사한다. 비ASCII 숫자는 int 변환 전에 `invalid date syntax`로 거부하고 trim·Unicode 정규화·치환을 하지 않는다. 정확한 date 객체의 값·동일성은 유지한다. 부적합 타입은 `date requires YYYY-MM-DD text or an exact date object`로 구분하여 int·None·bytes를 시각 포함으로 잘못 설명하지 않는다(C-2).

**근거:** 시간 문법·제안 Date 스키마와의 일관성, 좁고 실행기 독립적인 허용 문자 집합 및 광진의 명시적 선택이다. 기존 비ASCII가 잘못된 논리 날짜나 잘못된 hash였다는 판단은 아니다.

다음 표의 과거 열은 HEAD 08b4a2f의 동작이고 A 열은 승인 후 기대다. 구현·검증 통과는 별도 실행 기록으로 남긴다. B 열은 향후 재검토할 때의 비교안일 뿐이다.

### 승인 전 선택 문안 (제안 커밋의 이력)

A 선택 문안:

> X-2는 A안을 선택한다. 날짜 문자열은 ASCII YYYY-MM-DD만 허용하고, 정확한 date 객체 허용과 datetime/다른 타입 거부는 유지한다. 기존 비ASCII 문자열의 수용 변경과 적용 버전·호환 범위를 기록한 뒤 최소 수정안을 진행한다. 날짜 TLV와 정상 의미값은 유지한다.

B 선택 문안:

> X-2는 B안을 선택한다. Unicode 십진 숫자의 허용 집합·혼합 표기·정규화 책임과 Date 스키마 정합성을 먼저 명시하고 검토한다. 그 명세가 확인되기 전에는 허용 범위를 추가 확대하지 않는다.

위 두 문안은 승인 전 선택용 초안이었다. 2026-10-22의 별도 사용자 지시문이 A를 실제 승인했으며 B는 선택하지 않았다. 제안 커밋 자체를 승인 근거로 소급 해석하지 않는다.

### 적용 버전·최소 구현·호환성

A안 구현은 calendar_date 패턴과 부적합 타입 문구만 변경한다. 기존 serialization·semantics·loader 시험에 날짜/date 타입 경계·잘못된 달력·윤년·독립 TLV/hash·key()/split 경로 및 정확한 pin을 갱신한 로더 반례를 추가한다. #133의 UTC 예외·시간 정규화·int 변환·출력 payload는 변경하지 않는다.

B는 미채택이다. 재검토 시 Nd의 Unicode 버전/허용 목록·혼합 표기·정규화 위치를 먼저 고정하고 W0 Date와의 정합성을 계약 담당자가 수락해야 한다. 이번에는 공개 계약이나 W0 스키마를 수정하지 않는다.

로컬 입력 정책 버전은 `d1-date-input/1-ascii`다. 적용 구현은 이번 #134 커밋의 calendar_date이며 커밋 SHA와 파일 hash를 새 검토 보고서에 남긴다. 현행 구조에 입력 정책 전용 manifest 필드는 없으므로 새 공유 필드를 넣지 않는다. 날짜 값·타입·tag 06·의미 투영은 같으므로 `d1-semantic/2-proposed`, bundle/view/descriptor 버전 및 정상 의미 hash를 바꾸지 않는다. 이 식별자는 다른 실행기의 정책 협상이나 W0 전체 승인을 뜻하지 않는다.

기존 ASCII 문자열·정확한 date 및 이미 date32로 저장된 날짜의 의미·TLV는 유지한다. date 객체에 원래 문자열 표기가 남아 있다고 가정하지 않으므로 과거 Unicode에서 변환됐는지 역판정하지 않는다. 기존 비ASCII 문자열이 남은 split 등의 입력 파일은 새 guard에서 거부한다. 자동 변환·원본 수정·정확한 pin 교체·legacy fallback을 하지 않는다. 변환이 필요하면 담당자 승인 아래 원본을 보존한 별도 버전으로 재발행하고 관련 의미/물리 hash·부모·객체 연결 및 외부 Expected를 재검증하는 절차를 별도 제안한다. 이번에 마이그레이션을 실행하지 않는다. 실제 제공자의 Unicode 사용 여부와 공유 계약 적용 범위는 미확인이다.

### 구현·검증 상태

정책 선택은 승인됐다. 선택·입출력·버전·호환성 기록을 제품 수정 전에 먼저 작성했다. 이번 신규 9개 시험의 수정 전 상태는 설치 3.12에서 FAIL 22건(하위 사례 포함)·ERROR 0이었다. 수정 후 설치 3.12는 9 PASS, 무의존 3.12·3.13·3.14는 각각 7 PASS·2 SKIP(pyarrow 미설치), FAIL/ERROR 0이다. 이 수는 메서드 수와 하위 실패 건수를 구분하며 과거 실행을 승계하지 않는다.

2026-10-22 이번 실행: 3.12.13 의존성 환경의 hash·semantics·loader는 93 PASS, 계산·세션·시퀀스·품질은 81 PASS, 격리·팀·DR은 39 PASS다. 전체 discover는 969개 중 966 PASS·3 SKIP, 무의존 3.12 전체는 805 PASS·164 SKIP, 무의존 3.13.13 및 3.14.6의 D1 7모듈은 각각 112 PASS·62 SKIP이다. 모든 이번 수정 후 시험에서 FAIL/ERROR 0이며 SKIP은 PASS에 합산하지 않는다. 3.13·3.14 결과를 전체 저장소 또는 3.10 실행으로 확대하지 않는다.

정상 ASCII 로더 수용 후 split의 index_date만 비ASCII로 바꾸고 정확한 파일 pin을 재계산한 반례는 `invalid date syntax`에서 거부된다. 의미 요청·고정 객체 바이트를 바꾸지 않았으며 guard 호출도 확인했다. 독립 tag 06/TLV envelope·정상 fixture R/S/V·features/quality/sequence 의미 hash는 기존 기준과 같다. #133·#131 시간 함수와 기존 시험 본문은 그대로다. 실제 제공자 입력은 시험하지 않았다.

소유 검사는 기존 미등록 10건으로 FAIL(exit 1), 새 미등록 0이며 Python 3.10은 실행기 부재로 BLOCKED다. 출하 게이트 통과·독립 재검토 완료·#134 이슈 종료를 뜻하지 않는다. 상세 명령·원시 로그·코드/문서 hash·로컬 커밋 참조는 새 plans/D1-date-input-policy-134-review-20261022.md 및 plans/D1-date-input-policy-134-verification-20261022.log에 남긴다. plans는 Git 제외 로컬 참고 자료로 보존한다.

|---|---|
| B를 우선 채택 | 실제 Unicode 사용 근거가 없고 Python Unicode DB 판에 따라 수용이 달라짐. 고정 버전/허용 목록·스키마 정합성 근거가 없으며 광진이 A를 선택함. Unicode 요구가 확인되면 별도 재검토 |

| 공백 trim·NFKC 등 자동 정규화 | 현재 승인 범위를 넘어 허용 집합을 바꾸며 다른 문자까지 변환할 수 있음 |
| Unicode 입력이면 ASCII로 몰래 고쳐 로더 통과 | 정확한 파일·요청 pin과 입력 정책을 숨김 |

## 이 결정이 틀렸다면 어떻게 드러나나

실제 소비자 계약이 Unicode 날짜를 요구하거나 기존 파일에서 의미 있는 사용이 확인돼 호환성 계획 없이 수용을 중단할 수 없다면 A의 적용 범위를 재검토해야 한다. 미채택 B를 나중에 선택하고도 Unicode 버전/허용 집합을 고정하지 않으면 실행기 간 재현성 명세가 부족하다.

승인된 기대표와 다른 수용/거부, 윤년/달력 판정 변화, date와 datetime 혼용, 정상 날짜의 TLV·fixture R/S/V 변경, 정확한 입력 pin의 자동 교체는 구현 실패다. 정책 승인만으로 시험 통과·공유 계약 수락을 보고하면 상태 기록 실패다.

## 민감도

수치 임계값보다 허용 문자 집합의 선택이다. 숫자 한 글자만 ASCII에서 비ASCII로 바뀌어도 A의 수용 여부가 달라진다. B는 문법이 달라도 같은 날짜 의미로 정규화될 수 있다. 실제 입력 중 영향 비율은 조사하지 않았으므로 임의의 사용률·마이그레이션 비용을 만들지 않는다.

## 남은 불확실성

로컬 A안 선택과 위 입력 정책 버전은 정해졌다. 실제 Unicode 사용 여부, 과거 파일별 영향·별도 마이그레이션 실행 승인, W0/공유 Date 계약 담당자의 수락은 남는다. 로컬 구현이 제공자 수락·실제 입력 인수를 입증하지 않는다. B는 미결정 목록이 아니라 기각한 대안이며 새 근거가 있으면 재검토한다.

SD1–SD8·Q1–Q5 선택은 유지한다. #126·제공자 수락·실제 입력 인수·final_refit·Store·모델·CURRENT·D1 전체 완료는 이번 범위 밖이다. 소유 등록과 Python 3.10 실행의 기존 제한도 해결됐다고 표시하지 않는다. 검증 후 현재 브랜치에 이번 작업만 커밋하며 푸시·PR·GitHub 쓰기·이슈 종료는 하지 않는다.
