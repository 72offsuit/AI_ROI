## 0. 무엇을 막으려는 것인가

이 프로젝트가 끝났을 때 나올 수 있는 최악의 결과는 **작동하는데 왜 작동하는지 아무도 모르는 것**이다.

```
"페르소나를 왜 6종으로 했나요?"          "…PRD 에 그렇게 적혀 있어서요"
"쿠폰 민감도 분포는 어떻게 정했나요?"     "…적당히 그럴듯해 보여서요"
"AUC 0.82 는 믿을 만한가요?"            "…모델이 그렇게 냈어요"
"Test 를 보면서 튜닝하지 않았나요?"       "…아마도요?"
```

네 답 모두 **결과물은 멀쩡한데 근거가 없다.** 이것이 블랙박스다. 그리고 블랙박스는 틀렸을 때 **어디가 틀렸는지 짚을 수 없다** — 그래서 고칠 수도 없다.

이슈는 태스크 목록이 아니다. **무엇을 정해야 하고, 무엇을 조사해야 하고, 무엇을 증거로 남겨야 하는지의 안내서**다. 체크박스를 다 채워도 결정 기록이 없으면 그 태스크는 끝난 것이 아니다.

## 2. DR — 설계 결정 기록

### 이 문서의 절반은 "기각한 안"이다

택한 이유만 적힌 문서는 **다른 것을 생각해 보지 않은 것**과 구분되지 않는다. 무엇을 검토했고 왜 버렸는지가 있어야, 나중에 상황이 바뀌었을 때 **버린 안을 다시 꺼낼 수 있다.**

### 근거를 못 찾았으면 못 찾았다고 적는다

```
❌  "이커머스 표준 이탈 기준인 60일을 채택했다"        ← 그런 표준은 없다
✅  "60일을 찾아봤지만 업종·객단가별로 28~120일까지
     갈리고 우리 맥락(식품 커머스, 주 1회 구매 주기)에
     맞는 출처를 찾지 못했다. 구매 주기 중앙값의 6배인
     42일로 두되, 민감도 분석을 남긴다"
```

**"근거 없음"은 유효한 조사 결과다.** 근거 있는 척하는 것보다 낫고, 실제로 훨씬 쓸모 있다 — 다음 사람이 어디를 다시 파야 하는지 알게 된다.

이 저장소는 이미 그렇게 하고 있다. `config/economic_config.yaml` 의 AI 투자 비용 블록은 **`is_estimate: true` 와 함께 "외부 출처가 없다"고 적혀 있고**, 그 사실이 게시물 `notices` 로 실려 나간다.

### 반증 조건을 적는다

> **이 결정이 틀렸다면 어떻게 드러나나?**

여기에 아무것도 못 적으면, 그 결정은 **검증 불가능**하다. 그것도 결과다 — 그렇게 적는다. 검증 불가능한 결정을 검증 가능한 척하는 것이 문제다.

## 3. MC — 모델 카드

### "AUC 0.82" 한 줄로는 아무것도 말하지 못한다

같은 0.82 라도 이 셋은 전혀 다르다.

```
① 고객 단위로 나눈 Test, 튜닝은 Validation 에서만          → 믿을 만하다
② 무작위 분할이라 같은 고객이 Train·Test 양쪽에 있음        → 낙관 편향, 실전에서 무너진다
③ Test 를 보며 하이퍼파라미터를 40번 돌림                   → Test 가 사실상 Validation 이다
```

모델 카드는 **이 셋을 구분할 수 있게 하는 최소한의 기록**이다.

### 가장 중요한 두 칸

**`Final Holdout 을 무엇에 쓰지 않았나`** — 하이퍼파라미터 선택 · 임계값 선택 · 모델 선택 · 전략 선택 · 예산 정책. 하나라도 썼다면 그 수치는 낙관 편향이고, **그렇게 적는다.** 적는 것 자체는 감점이 아니다. 감추는 것이 감점이다.

**`누수 점검`** — 확인한 항목마다 *어떻게* 확인했는지 쓴다. "확인했음"은 확인이 아니다.

### 성능이 너무 좋으면 멈춘다

`days_since_last_purchase >= 42` 같은 Feature 가 라벨을 거의 결정하면 **AUC 는 0.99 지만 학습된 것은 없다** (PRD §80 Risk 7 — Churn Label Leakage). 운영 상태(`churn` · `at_risk` · `inactive`)를 Feature 로 쓰면 정확히 그렇게 된다.

**AUC 가 0.95 를 넘으면 축하할 일이 아니라 조사할 일이다.**

## 4. 언제 쓰나

```
착수  →  이슈의 "정해야 하는 것" 을 읽는다
      →  DR 을 **먼저** 연다. 선택지와 조사 칸을 채우며 결정한다
      →  구현
      →  모델이면 MC 를 채운다
      →  PR 에 DR·MC 링크
```

★ **DR 을 구현 뒤에 쓰면 그것은 결정 기록이 아니라 변명이다.** 이미 만든 것을 정당화하는 글이 되고, 기각한 안 칸이 비게 된다. 선택지를 적는 시점은 아직 고르지 않았을 때다.

다만 구현하다 보면 결정이 바뀐다. 그때는 **DR 을 고치고 상태를 `번복` 으로 바꾼 뒤 왜 바뀌었는지 적는다.** 번복은 정상이다. 조용히 바꾸는 것이 문제다.

## 5. 검사

```bash
python3 -m unittest tests.test_decision_records
```

검사하는 것:

- 템플릿 2종이 있는가
- `docs/decisions/` 의 각 기록이 **필수 섹션을 전부 갖는가**
- **채우지 않은 자리(`<...>`)가 남아 있지 않은가** ← 템플릿만 복사하고 안 채운 것을 잡는다
- 파일 이름이 `DR-`/`MC-` 규칙을 따르는가
- 태스크 번호가 실재하는가

검사하지 **않는** 것: **내용이 좋은가.** 기계는 근거의 질을 볼 수 없다. 그것은 리뷰가 본다. 이 검사는 *"빈 칸을 남긴 채 끝났다고 하지 않는다"* 까지만 보장한다.

## 6. 리뷰에서 받는 질문

PR 을 올리면 이 질문들이 온다. **미리 답할 수 있게 만드는 것이 결정 기록의 목적이다.**

### 시뮬레이터 팀

- 이 값이 아니라 저 값이면 무엇이 달라지나?
- 이 분포를 고른 근거가 우리 맥락에 맞나, 아니면 남의 업종 숫자인가?
- 생성한 데이터가 실제 커머스 데이터와 **어디가 다른가?** (같다고 주장하지 말고 차이를 말한다)
- 이 파라미터를 AI 성능을 보고 고친 적이 있나? — **없어야 한다**

### 시스템 팀

- 이 Feature 가 T0 이후 정보를 담고 있지 않다고 어떻게 확신하나?
- Test 성능을 몇 번 봤나?
- 같은 고객이 Train 과 Test 양쪽에 있지 않다고 확인했나?
- 이 모델이 틀리는 고객군은 어디인가?
- 성능이 이렇게 좋은 이유를 설명할 수 있나?

---

## 7. 이 제도 자체의 한계

결정 기록은 **나쁜 결정을 막지 못한다.** 근거를 적었어도 근거가 틀릴 수 있다.

막는 것은 **근거 없는 결정이 근거 있는 결정처럼 보이는 것**이다. 틀린 근거는 반박할 수 있지만, 없는 근거는 반박할 수조차 없다.
